The main aim of this thesis is to provide a comprehensive study and development of compilation techniques for high-level linear-typed (multiparadigm) languages, focusing on CLASS, a session typed language strongly motivated by a propositions-as-types interpretation of classical linear logic introduced by Rocha and Caires~\cite{Rocha:2021,Rocha:2023}. While the principles and meta-theory behind such linear logic based session languages are well known~\cite{CPT,Wadler}, associated implementation techniques for such languages, in particular compilation to native code, are still poorly understood. In this work we thus propose the design of multi-stage compilation scheme from CLASS to C, implement a prototype compiler based on it, and  validate it in terms of coverage, correctness and performance. 

\section{Linear Types in Programming Languages}

Type systems are a powerful tool which can be used to ensure the absence of some runtime errors, which would otherwise require extensive testing or program analysis. Essentially, type systems form a set of rules which limit the programs that can be written in a given language. Most traditional compiled imperative languages, such as C and Java, have type systems that avoid some common programming errors, such as passing a string to a function that expects an integer. Although such programs in a weakly or dynamically typed language such as Python or JavaScript would compile and run, they would likely fail at runtime, whereas in a strongly typed language, the compiler would catch the error at compile time. Strongly typed languages can additionally make use of their types to provide more information about the behavior of the code to the compiler, opening up new optimization paths.

\LC{More recently, substructural types have been proposed to statically ensure even stronger properties of the code, namely resource-usage properties related to memory manipulation, and protocol compliance, namely via linear types and session types~\cite{}. In fact, linear and affine types are becoming more and more relevant in practice, as witnessed by the
 adoption of programming languages such as Rust \cite{Matsakis:2014}, for general systems programming,
Move [32], for smart contracts, Linear Haskell \cite{Bernardy:2017}, and others [17, 1, 12, 11, 21] for general purpose programming}.
For example, Rust uses an affine type system to enforce memory safety, absence of data races and dangling pointers, which are common source of bugs in C and C++ programs, without the need for a garbage collector. However, Rust still does not guarantee that concurrent programs are deadlock-free, as it does not have a type system that enforces communication protocols.
%
Session types \cite{Honda:1993,Honda:1998} have been used to enforce correctness in communication protocols, namely in languages based on process calculus, which model concurrent systems \cite{Milner:1980,Milner:1992:1,Milner:1992:2}. By coupling session types with linear logic \cite{Girard:1987,Caires:2010}, it has been possible to additionally guarantee deadlock freedom. 

\ac{CLASS} \cite{Rocha:2022} is a proof-of-concept general purpose linear programming language based on linear / session types.
\ac{CLASS} supports many realistic concurrent programming idioms, and is the first language to simultaneously guarantee memory safety and the absence of dead-locks.
%
However, the \ac{CLASS} interpreter implemented by \LC{Rocha and Caires} \cite{Rocha:2021:artifact} served as a proof-of-concept for the language, and was not at all optimized for performance, and thus, wasn't suitable for real-world applications --- such  fully concurrent implementation spawn threads for all concurrent processes, based on the ``default'' concurrent interpretation of session-based programs (e.g., ~\cite{FreeST,RustST,other}).
%

%
As a first step, the \acf{SAM}  was introduced by Caires and Toninho \cite{Caires:2024} to provide a formal model for sequentially executing the processes of session-typed languages, allowing for orders of magnitude better runtime performance.
However, although the \ac{SAM} design opens the way for the mechanical sequential execution of CLASS programs, it is still a formal abstract machine model, in the spirit of ~\cite{SECD,LafontLAM}. Therefore, the prototype implementation of the SAM\cite{Caires:2024:artifact} was of course expected to still introduce a heavy performance overhead, compared to a potential, still to be developed, version of the language implementation based on compilation to native code.

During this work, a compilation scheme was designed and implemented which translates \ac{CLASS} programs into efficient C code, while maintaining all of the safety and liveness guarantees of \ac{CLASS}. This approach allows a two orders of magnitude more efficient execution of \ac{CLASS} programs than the \ac{SAM} interpreter, as the compiler can make use of the extensive knowledge of the compiled programs. Moreover, the developed compiler supports all of \ac{CLASS}, including affine sessions and shared state.

The base \ac{CLASS} language was slightly extended, with features such as an input extraction construct, allowing programs to read input from the standard input, which was necessary to measure the real-world performance of the compiled programs. The performance of the compiled programs was compared with the original \ac{CLASS} interpreter, the \ac{SAM} interpreter, and with equivalent programs written in Haskell. The results show that the compiled programs are orders of magnitude faster than the interpreted ones, and, in some cases, outperform equivalent Haskell programs compiled with GHC.


\section{A Glimpse into CLASS Compilation}

\ac{CLASS} programs are linearly typed session-based programs. Programs are constructed by composing processes which communicate through channels. Channels are first-class citizens of the language, replacing variables from traditional imperative languages. Communication through channels is regulated by the channel's session type, which describes the communication protocol followed by the channel. The linearity of the type system ensures that all communication is carried out exactly once, preventing leakage of resources, and guaranteeing memory safety.

An example \ac{CLASS} program is shown in \Cref{fig:CLASSIntroExample}. This program defines a process called \texttt{main} which will be executed when the program is run. Within it, the $\cutp$ process creates a new channel $x$ through which both sides of the cut communicate. On the right hand side of the cut, $x$ is typed by $\colintt$, and on the left hand side of the cut, by its dual type, $\lintt$. Semantically, the left hand side of the cut must produce an integer, which the right hand side must then consume. In this case, the left hand side produces the integer 1, through the $\letp$ process, and the right hand side consumes it by printing it to the standard output, through the $\printp$ process. The $\printp$ process requires a continuation, which in this case is the unit process $\emptyp$, which represents end of computation.

On the first prototype of the developed compiler, the compilation was performed in a single step, directly translating \ac{CLASS} programs into C code. However, as the supported feature set was expanded, and optimizations were implemented, the complexity of the compiler increased significantly. Thus, an \acf{IR} for session-based languages was developed to simplify the compilation process. This \ac{IR} is based on the \ac{SAM} execution model, sequentially executing the processes of the \ac{CLASS} program with buffered communication. The final compilation scheme is divided into three main phases: the translation from \ac{CLASS} to \ac{IR}, optimization of the \ac{IR}, and generation of C code from the optimized \ac{IR}.

The unoptimized \ac{IR} generated from the example \ac{CLASS} program is shown in \Cref{fig:IRBaseIntroExample}. The process $\texttt{main}$ is translated into an \ac{IR} process of the same name, composed of an header, and a set of blocks of instructions. This header defines multiple properties necessary for the execution of the process. In this example, the number of exit points, i.e., the number of exit instructions that must run for the process to finish, is $2$, one for each side of the cut. Additionally, the process is defined as having no type parameters, a single continuation $c_0$, which is used to implement session $x$, and a single data variable $d_0$, used to store the integer written to $x$.

The \texttt{entry} block of the \ac{IR} process is generated from the $\cutp$ process. It starts by initializing the continuation $c_0$, indicating that data written to it (the integer) should be stored at $d_0$, and setting the return address of $c_0$ to block \texttt{cut\_0}. The writing side is always executed first, so the next instructions are generated from the $\letp$ process, writing the integer $1$ to the continuation $c_0$ (and thus to $d_0$), and finishing the session, passing control to the block \texttt{cut\_0}, as specified earlier.

The \texttt{cut\_0} block is generated from the right hand side of the cut. The $\printp$ process generates a \texttt{print} instructions, which reads the integer from $d_0$ and prints it to the standard output. Finally, the $\emptyp$ process generates a \texttt{popTask} instruction, which passes control to the next task, if any, or ends the program if there are no more tasks to execute, as is the case here.

Before the C generation phase, a set of optimizations are applied to the \ac{IR} program to improve its performance. The final optimized version of the \ac{IR} is shown in \Cref{fig:IROptimizedIntroExample}. In this case, through analysis of the \ac{IR} program, optimizations were able to remove the continuation $c_0$ entirely, leaving only the data variable $d_0$. This is possible in this example due to the continuation's state being completely known at compile time. For example, the \texttt{finish} must pass control to the \texttt{cut\_0} block, and thus, it can be removed and the blocks concatenated. Additionally, the writing location of $c_0$ is known to be $d_0$, and thus \texttt{writeExpression} can write directly to it.

Finally, the optimized \ac{IR} program is compiled into C code. A segment of the generated code is shown in \Cref{fig:CIntroExample}. Due to the continuation-based nature of the \ac{SAM} execution model, processes are not represented as functions, but instead as code blocks within a single function, with control being transferred between them through the use of \texttt{goto} statements. Stack frames are replaced by heap-allocated environments, linked together to form a spaghetti stack, and which contain all local variables and state used by the process. A set of variables are used as registers to keep the current execution state, such as a pointer \texttt{task} to the next task, and a pointer \texttt{env} to the active environment.

The \texttt{main\_entry} label represents the \texttt{entry} block of the \ac{IR} \texttt{main} process. At the start of the program, an environment \texttt{env} is allocated and control is passed to this label. The \texttt{writeExpression} instruction is compiled into a simple assignment to the location of $d_0$ in the environment, which in this case is at offset $0$. The \texttt{print} instruction is compiled into a call to the C \texttt{printf} function, reading the integer from the same location. Finally, the \texttt{popTask} instruction is compiled into code which frees the current environment, and, in this case, ends the program.

\section{Alternative Compilation Schemes}
}

During this work, several alternative compilation schemes were considered and partially explored. Particularly, a different \ac{IR} model was considered and fully implemented, but ultimately abandoned in favor of the current scheme due to its inferior performance. This alternative implementation is available in the project's repository\footnote{\url{https://github.com/RiscadoA/class}}, through the tag \texttt{old-impl}.

On this alternative model, each session was represented as a heap-allocated object, separate from process environments. This meant allocating and deallocating sessions on the heap very frequently, which introduced a significant overhead. The \ac{IR} was much similar to the source language \ac{CLASS}, containing, for example, instructions for pushing and popping data from buffered communication channels, instead of direct reads and writes. This shifted a lot of complexity to the C generation phase, and additionally, made it harder to implement multiple optimizations.
