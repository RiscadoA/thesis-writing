The compiler has been fully implemented in Java, within the existing \ac{CLASS} and \ac{SAM} interpreters code base. The implementation follows the architecture described in \Cref{chap:architecture}, and includes all the optimizations described in \Cref{chap:optimizations}.

The implementation has been extensively tested through a bench of more than 180 incremental unit tests written in the \ac{CLASS} language, which cover all features of the language. Additionally, many of the existing \ac{CLASS} programs used to test the \ac{CLASS} and \ac{SAM} interpreters have also been compiled and executed using the developed compiler, or incorporated into the test suite.

The performance of the generated code has been evaluated through a benchmark program and the results compared with different compiler configurations, the interpreted execution of the same program using both the \ac{CLASS} and \ac{SAM} interpreters, and an equivalent implementation in Haskell.

In the first section of this chapter, an overview of the implementation is given, including the structure of the code and the main classes. The second section describes the testing testing strategy used to ensure the correctness of the generated code. The third section describes the performance evaluation strategy, including the benchmarks used and the metrics measured.

\section{Implementation}

The compiler is contained within a new \texttt{compiler} namespace within the existing \ac{CLASS} and \ac{SAM} interpreters Java code base. The main class of the compiler is \texttt{Compiler}, which provides a method to orchestrate the different compilation phases. This compiler is invoked through a bash script, which also invokes the \texttt{gcc} C compiler to generate the final executable.

The compilation method starts by parsing a number of flags and options from the command line. Each of the optimizations described in \Cref{chap:optimizations} is toggled by a flag, making it possible to easily benchmark the impact of each optimization. It is also possible to configure the target architecture (e.g., 32-bits or 64-bits), enable trace logs on generated programs, enable the printing of the \ac{IR} program at different stages, among other options.

The input \ac{CLASS} source code is parsed using the original parser, generating an \ac{AST}. The \ac{AST} is then type-checked, and visited by the \texttt{IRGenerator} visitor, which generates the initial \ac{IR} program, as described in \Cref{section:IRGeneration}. The enabled optimizations are then applied in sequence, and finally, the optimized \ac{IR} program is translated to C code through the \texttt{CGenerator} visitor, as described in \Cref{section:IRtoC}.

The \ac{IR} is modeled as a set of classes representing the different instructions, expressions, and slots, following the model described in \Cref{section:IR}. Each instruction class provides methods to accept visitors, as well methods to easily transform the instructions during the optimization phases. While \texttt{IRExpression} objects occur as fields of \texttt{IRInstruction} objects, the latter are stored within \texttt{IRBlock} objects. An \texttt{IRProcess} object contains a description of the process header, and a set of labeled \texttt{IRBlock} objects, one of them being the entry block. Finally, an \texttt{IRProgram} object contains a set of \texttt{IRProcess} objects.

On the C generation phase, a number of helper classes are used to make both the compiler code more readable and maintainable, as well as to generate simpler C code. The \texttt{CSize} and \texttt{CAlignment} classes represent a size and alignment in bytes, respectively, and provide methods to perform arithmetic operations. The results of these operations are simplified as much as possible automatically, making the generated code easier to read. The memory layouts of various data structures are represented by classes such as \texttt{CProcessLayout}, which hold the offsets and alignments of each field, as well as the total size and alignment of the structure. Memory layouts are generated by visiting the slot trees generated during the \ac{IR} generation phase, which themselves were generated by visiting the \ac{AST} types.

\section{Testing the compiler}

The project repository includes a comprehensive suite of more than 180 unit tests written in the \ac{CLASS} language, which cover all features of the language, including edge cases relevant to the implemented optimizations. Each test is composed of a \ac{CLASS} source file, and optionally, a number of input and expected output files. Tests are categorized into folders based on the language feature they are testing, such as exponentials, polymorphism, or process calls.

In order to easily find memory errors, a compiler flag \texttt{--profiling} can be enabled to compile the programs with counters for keeping track of how many allocations and deallocations have been performed for each type of structure (e.g., processes, tasks, exponentials) and report any memory leaks when the program finishes execution. Additionally, the compilation script provides flags to enable the address and thread sanitizers of \texttt{gcc}, helping troubleshoot memory access errors and data races.

Tests are executed through a bash script \texttt{test\_compiler.sh} which runs each test in the suite, with an optional filter to select specific tests. The script compiles each test using the flags above. If successfully compiled, and if input files are provided, the generated executable is run for each input file and the output is compared with the expected output file (if provided). If there are no input files, the executable is simply run to check for runtime errors. The script reports the results of each test, including compilation errors, runtime errors, memory leaks, and output mismatches.

Complex \ac{CLASS} programs, both newly written (such as game of life and merge sort) and existing ones were also integrated into the test suite, in addition to the smaller unit tests, in order to further validate the correctness of the generate code when many features are combined.
