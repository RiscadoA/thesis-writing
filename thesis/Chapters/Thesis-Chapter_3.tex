This chapter presents the base compilation scheme developed on this thesis. This scheme generates native code which executes in a sequential and deterministic manner, closely resembling the execution of the \ac{SAM}, implementing continuation-based coroutining. Associated to each process is a block of data called an environment, similar to a stack frame of traditional imperative languages. This environment stores the continuations of each session, as well as any data received through them. Whenever a process finishes writing data to a session, a jump is made to its other end point, which will read the data and continue execution.

At a high-level, the compilation scheme is divided into four phases. First, the source \ac{CLASS} program is parsed and type-checked. This phase is not discussed in this report, as its implementation has been reused from the previous work \cite{Rocha:2023, Caires:2024} on the \ac{SAM} and \ac{CLASS} interpreters. Then, the program is compiled to an \acf{IR} which abstracts some details of the target language. Next, the \ac{IR} is analyzed and optimized by a series of passes. Finally, the optimized \ac{IR} is translated to C code, which is then compiled to native code using the \acf{GCC}.

In the first section of this chapter, the \ac{IR}'s constructs and its abstract machine are defined. In the second section, the compilation of \ac{CLASS} to the \ac{IR} is described. Finally, in the third section,
an overview is given on how the \ac{IR} is translated to C code.

\section{Abstractions for the Intermediate Representation} \label{section:IR}

One of the main contributions of this work is the design and implementation of the first \acf{IR} for session-based languages which can be translated to efficient C code. Multiple abstractions were developed to model the execution of session-based programs in a low-level imperative language. This section starts by both describing the structure of \ac{IR} programs and introducing the abstract machine which executes them. Then, an example execution is covered step by step. Finally, an overview is given on various aspects of the \ac{IR} which were not covered in the example. The full syntax and instruction set of the \ac{IR} are provided in \Cref{chapter:appendixIR}.

The \ac{IR} is an imperative stateful language, inspired by the execution model of the \ac{SAM}, sequentially executing session-based programs through buffered communication. The concept of sessions is split into two parts: \textit{continuations}, which model the flow of control between two end points of a session, and \textit{data sections}, which store data received in sessions. A continuation can be seen as a representation of a session end point which stores the necessary information to communicate with and pass control to the opposite end point.

A continuation is composed of a return address, a writing location, and a reference to another continuation. The return address is a code address, which is jumped to when passing control to the opposite end point. The writing location is a data location where data to be read by the opposite end point should be written to. Finally, the continuation reference is a reference to the continuation which the opposite end point will use to pass control back to this point. The purpose of this reference will become clear in the example execution covered by the next section.

Data sections and continuations bring the representation of sessions much closer to variables and function calls in languages such as C. For example, for a given session end point $x: \lintt$, a continuation is stored which holds the return address to jump to after producing an integer to $x$. In the other end point of $x$, $y: \colintt$, a data section is stored to hold the integer which will be written to $x$.

\subsection{Programs and the IR Abstract Machine}

An \ac{IR} program is a set of named process definitions, each consisting of a header and a body. The header declares properties and resources used by the process, such as continuations, data sections and any type parameters, while the body is a set of named instruction blocks, each consisting of a list of instructions to be executed sequentially. A full specification of the \ac{IR}'s syntax is provided in \Cref{lst:IRsyntax}.

During execution, whenever a process is called, an \textit{environment} is created. An \textit{environment} is a data structure which holds the state of the process, similar to a stack frame in languages such as C. An environment holds the states of the continuations and data sections described in the header of its process. Additionally, the environment also stores the number of remaining exit points of the process. An exit point is an instruction through which control leaves the scope of the current environment, without a guarantee of coming back. When all exit points of a called process have been reached, its environment can be safely destroyed. Essentially, exit points are used as a reference counting mechanism for environments.

The execution of an \ac{IR} program is described by an abstract machine with state $\langle E, T, C \rangle$, where $E$ is the environment of the process being executed, $T$ is the stack of pending tasks, and $C$ is the program counter. The stack $T$ of pending tasks is used to model the $\parp$ process of \ac{CLASS}. Each task stores a code address and an environment, on which execution should resume when the task is popped from the stack.

To introduce the \ac{IR} and its abstractions, the execution of an example program will be covered step by step on the next section.

\subsection{Example Execution}

The example \ac{CLASS} program shown in \Cref{fig:IRProcessExample} consists of two process definitions, \texttt{main} and \texttt{p}. When executed, the two processes communicate through session $x$. Process \texttt{p} sends the integer $17$ over $x$, which, on \texttt{main}, is received and used to produce a string. This string is sent back to \texttt{p}, which prints it to the standard output and terminates.

The \ac{IR} program translated from the source \ac{CLASS} program is also shown in \Cref{fig:IRProcessExample}. It consists of two processes with the same names as in the source program. Before delving into the inner workings of the execution, a brief overview of the execution trace is given. The execution starts at the \texttt{entry} block of the \texttt{main} process. The steps of the execution are as follows:

\begin{enumerate}[leftmargin=*, label=\textbf{Step \arabic*:}, itemsep=1pt, parsep=0pt]
  \item \texttt{initContinuation(c0, rhs, d0)} --- initializes continuation $c_0$ in \texttt{main}.
  \item \texttt{callProcess(p, exit point, c2 <- c0)} --- calls process \texttt{p}, passing $c_0$ as an argument.
  \item \texttt{initContinuation(c3, send, d3)} --- initializes continuation $c_3$ in \texttt{p}.
  \item \texttt{writeContinuation(c2, c3)} --- writes $c_3$ to the writing location of $c_2$, which is $d_0$.
  \item \texttt{continue(c2, ret)} --- yields control to $c_2$, jumping to \texttt{rhs} in \texttt{main}.
  \item \texttt{bindContinuation(d0, c1, d1)} --- reads $c_3$ from $d_0$, binding it to $c_1$ and pointing $c_3$ to $d_1$.
  \item \texttt{continue(c1, ret)} --- yields control to $c_1$, jumping to \texttt{send} in \texttt{p}.
  \item \texttt{writeExpression(c3, 17)} --- writes $17$ to the writing location of $c_3$, which is $d_1$.
  \item \texttt{finish(c3, exit point)} --- jumps to \texttt{ret} .in \texttt{main}.
  \item \texttt{writeExpression(c0, "Res:\ " + move(d1, int))} --- reads $17$ from $d_1$ and writes the string \texttt{"Res:\ 17"} to the writing location of $c_0$, which is $d_2$.
  \item \texttt{finish(c0, exit point)} --- jumps to \texttt{ret} in \texttt{p}.
  \item \texttt{printLine(move(d2, string))} --- reads \texttt{"Res:\ 17"} from $d_2$ and prints it.
  \item \texttt{popTask(exit point)} --- finishes execution.
\end{enumerate}

\subsection{Forwarding Continuations}

To model the forwarding of sessions in \ac{CLASS}, it is necessary to be able to link two continuations together, detaching them from the active environment. This is done through the \texttt{forward} instruction. This instruction takes two continuations as arguments, links their remote end points together, and passes control to the continuation of the second argument. An example snippet using this instruction is shown below:
\begin{lstlisting}[language=IR,frame=bottom]
entry:
    initContinuation(c0, lhs, d0) // 1
    initContinuation(c1, rhs, d1) // 2
    forward(c0, c1)  // 3
lhs:
    ...                           // 5
rhs:
    finish(c1)                    // 4
\end{lstlisting}

In this example two continuations $c_0$ and $c_1$ are initialized as before. The \texttt{forward(c0, c1)} instruction is then executed, which makes $c_0$ the remote continuation of $c_1$ and vice-versa. Control then passes to $c_1$, and thus, to the block \texttt{rhs}. The instruction \texttt{finish(c1)} is finally executed, which as before, passes control to $c_1$, and thus to the block \texttt{lhs}, as $c_1$'s code location was set to $c_0$'s when forwarded.

\subsection{Data Representation} \label{subsection:IRSlots}

\ac{IR} programs are completely platform agnostic, and thus, data types and addresses are described through their composition of \textit{slots}, instead of concrete byte sizes and offsets. A slot $S$ is a unit of data in the \ac{IR}, and is defined as
\[
S ::= \ints \mid \bools \mid \strings \mid \tags \mid \conts \mid \cells{T} \mid \exponentials \mid \types \mid \vars{i}\]
where $\ints$, $\bools$ and $\strings$ represent the basic data types, $\tags$ represents a \ac{CLASS} choice, $\conts$ a continuation reference, $\cells{T}$ a reference to a shared state cell with contents described by the slot tree $T$ (introduced below), $\exponentials$ an exponential reference, $\types$ a stored type parameter, and $\vars{i}$ a type parameter declared in the current process header. 

In order to model branching data types (such as choices from \ac{CLASS}), data layouts are described through trees of slots, instead of plain sequences. A slot tree $T$ is defined recursively as
\[
T ::= \nilst \mid \seqst{S_1; \dots; S_n; T} \mid \tagst{T_1 \tagsepst \dots \tagsepst T_n}
\]
where $\nilst$ is the empty slot tree, $\seqst{S_1; \dots; S_n; T}$ is a sequence of a slots $S_1; \dots; S_n$ followed by a slot tree $T$, and $\tagst{T_1 \tagsepst \dots \tagsepst T_n}$ is a $\tags$ slot followed by a choice between the slot trees $T_1$ to $T_n$. For example, $\seqst{\ints; \tagst{\seqst{\bools} \tagsepst \seqst{\strings}}}$ describes an integer followed by a tag, which, if $0$, is followed by a boolean, or if $1$, is followed by a string.

Data sections are described within process headers by a sum of slot trees describing the possible layouts of data that can be stored on them. For example, $\texttt{data d0:}\ \combst{\seqst{\ints; \bools} + \seqst{\strings}}$ describes a data section $d_0$ which can either store an $\ints$ followed by a $\bools$, or a $\strings$.

\subsubsection{Addressing Data} \label{subsection:DataAddressing}

A \textit{data location} is denoted as $\dataol{b}{o}$, where $b$ is a base address and $o$ an offset. A base address can be either a local data section (e.g., $d_0$), a writing location given by a continuation (e.g., $c_0$), or a cell location (e.g., $c(d_0)$). An offset is defined by two slot trees, written as $\offs{P}{F}$, $P$ describing the data being skipped (named \textit{past}), and $F$ describing the data that may come next (named \textit{future}). The future tree is necessary to determine the alignment of the data being accessed. For example, $\offs{\seqst{\ints; \bools}}{\seqst{\strings}}$ is an offset which skips an integer followed by a boolean, and expects a string to come next. When the past slot tree is empty, the future slot tree is unnecessary, and the offset is simply written as $0$. 

To exemplify, the location $\datal{d_0}{\seqst{\ints}}{\seqst{\ints}}$ refers to the second integer stored in $d_0$, while the location $\datal{c_0}{\seqst{\bools}}{\seqst{\strings}}$ refers to a string stored in the writing location of the continuation $c_0$, after a boolean. When the offset is zero, it is omitted for brevity. For example, $d_0$ as a data location is equivalent to $\datal{d_0}{\nilst}{\nilst}$ or just $d_0.0$ - the future slot trees are unnecessary for empty past slot trees.

\subsection{Moving Data}

The \texttt{moveSlots} instruction allows moving data from one location to another. It takes as arguments a destination location, a source location and a slot tree describing the data to be moved. To exemplify, \texttt{moveSlots(c1, $\datal{d_0}{\seqst{\bools}}{\seqst{\strings; \ints}}, \seqst{\strings, \ints}$)} takes a string followed by an integer located after a boolean at the data section $d_0$, to the writing location of $c_1$. This instruction is used to implement the forwarding of sessions in \ac{CLASS}. 

The \texttt{cloneSlots} instruction is used to clone data from one location to another, taking the same arguments. This instruction is only defined for cloneable slots, which are $\ints$, $\bools$, $\strings$, $\tags$ and $\exponentials$. In addition to copying the memory, it also increments reference counts for exponentials and allocates new strings as necessary. It used to model the exponential part of \ac{CLASS}.

\subsection{Dropping Data} \label{subsection:IRDroppingData}

To model the affine and exponential parts of \ac{CLASS}, it is necessary to be able to drop some types of data if they are no longer needed. To this end, two instructions are provided: \texttt{dropSlots} and \texttt{deferDrop}.

The \texttt{dropSlots} instruction takes as arguments a data location and a slot tree, and immediately drops the passed data. The $\conts$ slot requires special care. The remote end point of the stored continuation is expected to follow the affine protocol, defined as follows: when the continuation is to be dropped, a tag with value $0$ is written to indicate the drop, and control is yielded to the continuation. Control should then be returned, at which point the continuation is considered dropped.

The \texttt{deferDrop} instruction takes as argument a \textit{drop bit identifier}, and sets the respective bit. Drop bits are declared in the process header, and indicate a data location and a slot tree to be dropped when the process terminates, if the bit is set. Drop bits are identified by an \texttt{e} followed by a number (e.g., \texttt{e0}).

Below is an example of dropping data directly and through a drop bit:
\begin{lstlisting}[language=IR,frame=bottom]
main:
    data d0: <[string; string]>
    drop e0: [string] at d0.[string]~[string]
entry:
    ... // something that initializes both strings at d0
    deferDrop(e0) // the second string will be dropped on environment cleanup
    dropSlots(d0, [string]) // the first string is dropped immediately
\end{lstlisting}

\subsection{Expressions}

Expressions are tree-like structure which compute basic values ($\ints$, $\bools$ or $\strings$) without side effects. \ac{IR} expressions are defined exactly as the expressions of \ac{CLASS}, with the difference that session names are replaced by \texttt{move(d, S)} and \texttt{clone(d, S)} expressions. Move and clone expressions read a slot $S$ from a data location $d$, with the difference that move consumes the data (cannot be read again) while clone leaves the data intact. For example, an integer clone is equivalent to a move, as integers are trivially copyable, but a string clone must allocate a new string and copy the contents.

While expressions do not occur as instructions, they are used as arguments to some instructions, such as \texttt{writeExpression}, \texttt{branchExpr} and \texttt{print}. An example of an expression is \texttt{(move(d0, int) + 3) + clone(d1, string)}. This expression reads an integer from $d_0$, adds $3$ to it, then reads a cloned string from $d_1$ and finally concatenates the two. 

\subsection{Input and Output}

Output is modeled through the \texttt{print} and \texttt{printLine} instructions. They take a single argument expression, which is evaluated and printed to the standard output. The \texttt{printLine} instruction additionally appends a new line after printing the value. Input is modeled through the \texttt{writeScan} instruction, which reads values from the standard input. It takes as arguments a data location to store the read value to and a slot describing the type of data to be read. Below is an example program, which reads two integers and prints their sum.
\begin{lstlisting}[language=IR,frame=bottom]
main:
    data d0: <[int; int]>
entry:
    writeScan(d0, int)
    writeScan(d0.[int]~[int], int)
    printLine(move(d0, int) + move(d0.[int]~[int], int))
\end{lstlisting}

\subsection{Tags and Branching} \label{subsection:Branching}

Branching is done through the \texttt{branchTag} and \texttt{branchExpr} instructions. The first instruction branches on a tag stored a data location, similarly to a switch statement in C, and the second instruction branches on the result of a boolean expression, similarly to an if statement in C. Each possible branch is defined by a code location (block label) and an integer indicating how many exit points are behind that branch. This number is used to adjust the exit point count of the environment when branching.

Tags are written to data locations through the \texttt{writeTag} instruction, which takes as arguments a data location and a constant tag value. Below is an example of writing a tag and then branching on it.

\begin{lstlisting}[language=IR,frame=bottom]
main:
    data d0: <tag[[int] | [string]]>
entry:
    writeTag(d0, 1)
    branchTag(d0, if_int:1, if_string:1)
if_int: // ...
if_string: // ...
\end{lstlisting}

\subsection{Tasks}

As mentioned before, tasks are a control flow mechanism completely separate from environments and continuations, and are used to model the $\parp$ construct from \ac{CLASS}. The abstract machine maintains a stack of tasks, where each task stores a continuation to be executed when the current task is finished.

Tasks can be pushed to the stack through the \texttt{pushTask} instruction, which takes a code location as argument. To finish the current task and jump to the continuation of the topmost task, the \texttt{popTask} instruction is used.

When execution begins, the task stack is initialized with a single task responsible for terminating the program. Thus, the last instruction to be executed in a program is always \texttt{popTask}.

\subsection{Concurrency} \label{subsection:IRThreads}

New threads of execution can be launched through the \texttt{launchThread} instruction, which takes as arguments a code location to start executing at. Each thread functions as a separate instance of the abstract machine, with its own stack of tasks and active environment. When a thread is launched, it inherits the current thread's active environment.

Accesses to the environment are not synchronized except for reference and exit point counting, which are done atomically. When generating \ac{IR} programs from \ac{CLASS}, its type system guarantees that no two threads will access the same data concurrently other than through cells, which are synchronized.

\subsection{Cells} \label{subsection:Cells}

Cells are used to model the shared state part of \ac{CLASS}. They're mutable memory locations which can be safely shared between multiple threads of execution. Cells are referenced through $\cells{T}$ slots, and maintain a mutex to ensure safe concurrent access, as well as a reference count to guarantee proper deallocation.

A new cell can be created through the \texttt{writeCell} instruction, which takes as arguments a data location to write the $\cells{T}$ slot to, and a slot tree $T$ describing the data that will be stored in the cell. The reference count of a cell can be incremented and decremented through the \texttt{acquireCell} and \texttt{releaseCell} instructions, respectively. Finally, the mutex of a cell can be locked and unlocked through the \texttt{lockCell} and \texttt{unlockCell} instructions, respectively. The data stored in a cell can be accessed through any data location, by using a cell location as the base address, as explained in \Cref{subsection:DataAddressing}.

Below is an example of creating a cell, writing data to it, acquiring and releasing references to it, and finally deallocating it:
\begin{lstlisting}[language=IR, frame=bottom]
main:
    data d0: <cell[int]>
entry:
    writeCell(d0, [int]) // create a cell with space for an integer
    lockCell(c(d0)) // lock the cell's mutex
    writeExpression(c(d0), 42) // write 42 to the cell
    unlockCell(c(d0)) // unlock the cell's mutex
    acquireCell(c(d0)) // increase reference count to 2
    releaseCell(c(d0)) // decrease reference count to 1
    releaseCell(c(d0)) // decrease reference count to 0, deallocating the cell
\end{lstlisting}

\subsection{Polymorphism}

Processes in the \ac{IR} may be type parametrized. These type parameters are identified by names which start with \texttt{t} followed by a number, such as $t_0$ and $t_1$, and are assigned when the process is called. Within the process, types parameters may be used directly as slots in slot trees (e.g.: $\seqst{t_2; \ints; t_0}$).

To model the \ac{CLASS} $\sendtyp$ and $\recvtyp$ constructs, it is necessary to send type information dynamically through sessions. To achieve this, the \texttt{writeType} instruction takes as arguments a target data location and a slot tree describing the data layout of the type. This instruction writes the necessary type information to the data location, producing a $\types$ slot. For example, \texttt{writeType(d0, [int; t1])} writes information to $d_0$ describing the slot tree $\seqst{\ints; t_1}$. The written $\types$ slot can then later be used as a type parameter when calling a process, as explained in the next section.

\subsection{Process Calls}

On the example execution shown earlier, a process call instruction was shown, but only a continuation was passed as argument. In order to model the full \ac{CLASS} process call semantics, it is necessary to also be able to pass both type parameters and data arguments to the new process.

The \texttt{callProcess} instruction thus takes as arguments the name of the process to invoke, a list of type parameters, and a list of continuation and data arguments to initialize the new process environment.

A type parameter is described by the target type parameter identifier on the new process, and by either a data location containing a $\types$ slot, or by a slot tree directly. For example, \texttt{t0 <- [int]} initializes the type parameter $t_0$ of the new process to be a type which stores an integer, while \texttt{t1 <- d3.[int]$\mathtt{\sim}$[type]} initializes $t_1$ to the type parameter stored after an integer at $d_3$.

A continuation argument is described by the target continuation identifier on the new process, by either a source continuation identifier or a data location containing a $\conts$ slot, and finally, by a data offset to apply to the writing location of the continuation. For example, \texttt{c0 <- c1+[int]$\mathtt{\sim}$[int]} initializes the continuation parameter $c_0$ of the new process to be the same as continuation $c_1$ of the current process, but with its writing location pointing at $\datal{c_1}{\seqst{\ints}}{\seqst{\ints}}$. If the offset is zero, it is omitted for brevity.

Finally, a data argument is described by the target data identifier on the new process, by a source data location, by a slot tree describing the data, and by a flag indicating whether to clone the data or not. For example, \texttt{d0 =[string] d1} writes to $d_0$ a clone of the string stored at $d_1$, while \texttt{d1 <-[string] d2} moves to $d_1$ the string stored at $d_2$ without cloning it.

An example of calling a process with type, session and data arguments is shown below.
\begin{lstlisting}[language=IR, frame=bottom]
foo:
    types: t0
    continuations: c0
    data d0: <[t0]>
entry:
    moveSlots(c0, d0, [t0]) // 4
    finish(c0)              // 5

main:
    continuations: c0
    data d0: <[int]>
entry:
    initContinuation(c0, d0, rhs)                          // 1
    writeExpression(c0, 42)                                // 2
    callProcess(foo, t0 <- [int], c0 <- c0, d0 <-[int] d0) // 3
rhs:
    printLine(move(d0, int)) // 6
\end{lstlisting}
First, the continuation $c_0$ is initialized, with its writing location being $d_0$ and code location being the block \texttt{rhs}. Then, the integer \texttt{42} is written to $c_0$ (which is $d_0$). Next, the process \texttt{foo} is called, with its type parameter $t_0$ being set to an integer, its continuation $c_0$ being set to the local $c_0$, and its data section $d_0$ being initialized by a move of the data section $d_0$. Inside \texttt{foo}, the integer stored at its data section $d_0$ (received from \texttt{main}) is moved to the writing location of its continuation $c_0$ (which is still $d_0$ from the \texttt{main} process), and then, the session is finished, passing control back to the block \texttt{rhs} of the calling process. Finally, the integer stored at $d_0$ is printed.

\subsection{Exponentials}

Exponentials in \ac{CLASS} can be modeled through the $\exponentials$ slot, which stores the necessary data to dynamically call a process closure, along with any captured data arguments. Exponentials are created through the \texttt{writeExponential} instruction, which takes the same arguments as \texttt{callProcess}, with the exception that continuation arguments are not allowed, and that passed data must be cloneable. Additionally, the referenced process is expected to follow the exponential process convention.

The convention for exponential processes is simply that they must take a single continuation argument, $c_0$, which will be used to communicate with the caller. This continuation is initialized by the \texttt{callExponential} instruction, which invokes the process. This instruction takes as arguments a data location containing an $\exponentials$ slot, a continuation identifier to bind the exponential process continuation to, and a data location to set as the writing location on the exponential process.

One important detail is that exponentials are reference counted data, and the $\exponentials$ slot must be dropped when no longer needed, or at the end of the process, if it was not moved. This is done through the \texttt{dropSlots} or \texttt{deferDrop} instructions, as explained in the \Cref{subsection:IRDroppingData} section. Drops of exponentials decrement this reference count, while clones increment it. Below is an example of creating and calling an exponential.
\begin{lstlisting}[language=IR, frame=bottom]
foo:
    types: t0
    continuations: c0
    data d0: <[t0]>
entry:
    moveSlots(c0, d0, [t0]) // 6, 10
    finish(c0)              // 7, 11

main:
    continuations: c0 c1
    data d0: <[string]>
    data d1: <[exponential]>
    data d2: <[string]>
    data d3: <[string]>
    drop e0: [exponential] at d1
entry:
    writeExpression(d0, "Hello, World!")                        // 1
    writeExponential(d1, foo, t0 <- [string], d0 <-[string] d0) // 2
    deferDrop(e0)               // 3
    callExponential(d1, c0, d2) // 4
    callExponential(d1, c1, d3) // 4
    continue(c0, rhs0)          // 5
rhs0:
    printLine(move(d2, string)) // 8
    continue(c1, rhs1)          // 9
rhs1:
    printLine(move(d3, string)) // 12
\end{lstlisting}

In this example, the process \texttt{foo} is a simple polymorphic process with a type parameter $t_0$, a continuation $c_0$ and a data section $d_0$. It moves data of type $\seqst{\strings}$ from $d_0$ to the writing location of $c_0$, and then finishes on $c_0$, passing control back to the caller.

The \texttt{main} process writes a new string to $d_0$, and then creates a new exponential at $d_1$ for the process \texttt{foo}, moving the just written string to it. This string will be cloned every time the exponential is called, and dropped when the exponential is freed. The exponential will be dropped at the end of the process through the drop bit \texttt{e0}, which is set by the \texttt{deferDrop(e0)} instruction.

The exponential is then called twice, first binding its argument continuation to $c_0$ and its writing location to $d_2$, and then binding its continuation to $c_1$ and its writing location to $d_3$. Each call will clone the string stored at $d_0$ and pass it to the exponential process. Control is not immediately passed to the exponential process. Instead, it is passed when the argument sessions, either $c_0$ or $c_1$, are continued, as their continuations were set by the \texttt{callExponential} instruction to be the entry block of the exponential process.

Finally, within the exponential process, the string is moved from $d_0$ to the remote data of $c_0$, which is either $d_2$ or $d_3$ of the caller, depending on which call was continued. Finally, the continuation is finished, passing control back to the caller, which prints the received string.

\section{Translating CLASS to the IR} \label{section:IRGeneration}

This section defines the base (unoptimized) translation from \ac{CLASS} to the \ac{IR} defined in the previous section. It starts by defining notation for representing and updating the state of the compiler. Then, it defines how session types are mapped to the slot trees introduced in \Cref{subsection:IRSlots}. Next, an overview of the instruction translation scheme is presented, and some important concepts are defined. Finally, the translation from \ac{CLASS} processes to \ac{IR} programs is incrementally defined, starting from simple processes and adding more constructs until the whole language is covered.

The presented compilation scheme assumes well-typed \ac{CLASS} processes are given as input, along with the required type information of free names in all processes. The notation $x: A$ is used to indicate that the type checker infers session end point $x$ to be a free name of type $A$ on some process.

\subsection{Compiler State}

Compilation of \ac{CLASS} processes into \ac{IR} programs always occurs within the context of a single \ac{IR} process. As \ac{CLASS} processes are compiled into \ac{IR} instructions, new information is added to the \ac{IR} process header, along with the new instructions and blocks. Changes to the header of the \ac{IR} process are denoted by the actions shown below.

\begin{minipage}{0.45\textwidth}\begin{equation}\makecont{c}\label{eq:makecont}\end{equation}\end{minipage}
\hfill
\begin{minipage}{0.45\textwidth}\begin{equation}\makedata{d}{T}\label{eq:makedata}\end{equation}\end{minipage}

\begin{minipage}{0.45\textwidth}\begin{equation}\makedrop{e}{L}{S}\label{eq:makedrop}\end{equation}\end{minipage}
\hfill
\begin{minipage}{0.45\textwidth}\begin{equation}\makeblock{l}\label{eq:makeblock}\end{equation}\end{minipage}

Action \Cref{eq:makecont} adds a new continuation to the process header, identified by $c$. Action \Cref{eq:makedata} creates a new data section with data layout $T$ identified by $d$. Action \Cref{eq:makedrop} creates a new drop bit pertaining to data location $L$ and slots $S$, identified by $e$. Action \Cref{eq:makeblock} generates a unique label $l$ for a new instruction block within the process body.

The compiler must keep track of information regarding the type parameters and the state of each session end point within the process being compiled. This state is referred to as the environment, and is represented by a tuple $(\theta, \Delta)$, where $\theta$ is the type environment and $\Delta$ is the session environment.

\subsubsection{Type Environments} \label{subsubsection:TypeEnvironments}

A type environment $\theta$ is a mapping from type variables to a tuple $(p, t)$ where $p$ is the polarity of the type variable ($+$ or $-$) and $t$ is its identifier (e.g, $t_0$, $t_1$) within the header of the process being compiled. $\polarityof{\theta}{X}$ and $\typeidof{\theta}{X}$ are defined as the polarity and identifier of type variable $X$ in the type environment $\theta$, respectively.

A type with positive polarity is one for which sessions of that type are used to write data, while a type with negative polarity is one for which sessions of that type are used to read data. The function $\polarityof{\theta}{A}$ is further extended to all session types $A$ through pattern matching, as shown in \Cref{fig:TypePolarity}. For the base case of type variables, the polarity is looked up in the type environment.

\begin{figure}
    \centering
    \[\begin{aligned}
        &\polarityof{\theta}{\lintt} = + && \polarityof{\theta}{\colintt} = - && \polarityof{\theta}{\lboolt} = + && \polarityof{\theta}{\colboolt} = - \\
        &\polarityof{\theta}{\lstringt} = + && \polarityof{\theta}{\colstringt} = - && \polarityof{\theta}{\closet} = + && \polarityof{\theta}{\waitt} = - \\
        &\polarityof{\theta}{\choicet{\dots}} = + && \polarityof{\theta}{\offert{\dots}} = - && \polarityof{\theta}{\sendt{A}{B}} = + && \polarityof{\theta}{\recvt{A}{B}} = - \\
        &\polarityof{\theta}{\bangt{A}} = + && \polarityof{\theta}{\whynott{A}} = - && \polarityof{\theta}{\sendtyt{X}{A}} = + && \polarityof{\theta}{\recvtyt{X}{A}} = - \\
        &\polarityof{\theta}{\coaffinet{A}} = + && \polarityof{\theta}{\affinet{A}} = - && \polarityof{\theta}{\statet{A}} = + && \polarityof{\theta}{\usaget{A}} = - \\
        &\polarityof{\theta}{\rect{X}{A}} = + && \polarityof{\theta}{\corect{X}{A}} = - && \polarityof{\theta}{\statelt{A}} = + && \polarityof{\theta}{\usagelt{A}} = - \\
    \end{aligned}\]
    \caption{Polarity of session types}
    \label{fig:TypePolarity}
\end{figure}

Note that due to affine types being implemented as a choice between using the data or dropping it, i.e., $\affinet{A} \equiv \offert{\labelt{use}{A}\ \labelt{discard}{\closet}}$, the polarity of $\affinet{A}$ is negative, while the polarity of $\coaffinet{A}$ is positive.

\subsubsection{Session Environments}

A session environment $\Delta$ is a mapping from session end point names to session states. Each session state is a tuple $(c, d, o)$, where $c$ is the continuation identifier associated with the session end point (or $0$ if there's no continuation), $d$ is the identifier of the data section from which data is read (or $0$ if there's no data section), and $o$ is the data offset to apply to the location of the next write or read operation on the session. The data offset is represented as a slot tree, as explained in \Cref{subsection:DataAddressing}.

Given a session environment $\Delta$, $\Delta[x \mapsto (c, d, o)]$ is defined as the updated mapping where session end point $x$ is mapped to the new session state $(c, d, o)$. Additionally $\continuationof{\Delta}{x}$, $\localdataof{\Delta}{x}$ and $\offsetof{\Delta}{x}$ are defined as the continuation identifier, local data identifier and data offset associated with session $x$ in the session environment $\Delta$, respectively.

During development, in the unfinished compiler, session data offsets were maintained as runtime state, being updated whenever a read or write operation was performed. This approach was later abandoned in favor of the current version, where offsets are known at compile time, greatly simplifying the generated code and reducing runtime overhead.

\subsubsection{Writing and Reading Locations}

For convenience, $\readlocof{\Delta}{x}$ and $\writelocof{\Delta}{x}$ are denoted as the current data location from which data of session end point $x$ is to be read, and the data location into which data for session $x$ is to be written, respectively. Both take into account the offset, and are defined as

\centerline{\vspace{2pt}
$\readlocof{\Delta}{x} = \dataol{\localdataof{\Delta}{x}}{\offsetof{\Delta}{x}} \hspace{5em} \writelocof{\Delta}{x} = \dataol{\continuationof{\Delta}{x}}{\offsetof{\Delta}{x}}$}

\subsubsection{Advancing Session Offsets} \label{subsubsection:AdvancingOffsets}

When more than one slot is read from or written to a session end point in succession, the session's offset must be advanced accordingly. To this end, the concatenation of offsets must be defined. Given two offsets $o_1 = \offs{P_1}{F_1}$ and $o_2 = \offs{P_2}{F_2}$, their concatenation is defined as $\concatst{o_1}{o_2} = \offs{(\concatst{P_1}{P_2})}{F_2}$, where $\concatst{P_1}{P_2}$ is the concatenation of the two slot trees. In other words, when two offsets are concatenated, the resulting offset has concatenates both past slot trees, and keeps the future slot tree of the second offset. Slot tree concatenation is defined as replacing every leaf of the first slot tree with the second tree.

To simplify the definitions in the next sections, $\advancech{\Delta}{x}{p}{\theta}{S}{A}$ denotes the session environment $\Delta$ where the offset of session $x$ is either reset, or advanced by the necessary offset to skip over the slots $S$. The decision is made based on whether the polarity $p$ (either $+$ or $-$) matches the polarity of the type $A$ in the type environment $\theta$. If they match, the new offset is computed as $\concatst{\offsetof{\Delta}{x}}{(\slotoffset{S}{\slots{\theta}{A}})}$, where $S$ is a slot tree describing the data which was just read or written, and $\slots{\theta}{A}$ is the slot tree corresponding to type $A$, which will be defined in the next section. Otherwise the new offset is $0$. Formally:
\[
\advancech{\Delta}{x}{p}{\theta}{S}{A} = \begin{cases}
    \Delta[x \mapsto (\continuationof{\Delta}{x}, \localdataof{\Delta}{x}, \concatst{\offsetof{\Delta}{x}}{(\slotoffset{S}{\slots{\theta}{A}})})] & \text{if } p = \polarityof{\theta}{A} \\
    \Delta[x \mapsto (\continuationof{\Delta}{x}, \localdataof{\Delta}{x}, 0)] & \text{otherwise}
\end{cases}
\]

\subsection{Mapping Session Types to Slot Trees} \label{subsection:MappingSessionTypesToSlots}

To translate \ac{CLASS} processes to \ac{IR} programs, we need to define which data is sent and received over sessions. As explained in \Cref{subsection:IRSlots}, in the \ac{IR} data types are represented through slot trees. Thus, we need to define how session types are mapped to slot trees.

We start by defining this mapping for session types $A$ which are strictly positive. Let $\slots{\theta}{A}$ be the slot tree corresponding to the data exchanged over a session type $A$ within type environment $\theta$. This function is defined through pattern matching on session types:
\[\begin{aligned}
        &\slots{\theta}{\closet} = \nilst && \slots{\theta}{\lintt} = \seqst{\ints} \\
        &\slots{\theta}{\lboolt} = \seqst{\bools} && \slots{\theta}{\lstringt} = \seqst{\strings} \\
        &\slots{\theta}{\sendt{A}{B}} = \seqst{\conts; \slots{\theta}{B}} && \slots{\theta}{\bangt{A}} = \seqst{\exponentials} \\
        &\slots{\theta}{\sendtyt{X}{A}} = \seqst{\types; \conts; \tags} && \slots{\theta}{\coaffinet A} = \tagst{\nilst\tagsepst\slots{\theta}{A}} \\
        &\slots{\theta}{\statet A} = \seqst{\cells{\conts}} && \slots{\theta}{\statelt A} = \seqst{\cells{\conts}} \\
        &\slots{\theta}{\choicet{\labelt a A\ \dots}} = \tagst{\slots{\theta}{A} \texttt{|}\ \dots} && \slots{\theta}{X} = \seqst{\typeidof{\theta}{X}} \text { s.t. } \polarityof{\theta}{X} = + \\
        &\slots{\theta}{A} = \nilst \text{ if } \polarityof{\theta}{A} = -
\end{aligned}\]

To exemplify, consider the session type $\sendt{\lintt}{\sendt{\closet}{\choicet{\labelt a \lstringt\ \labelt b \lboolt}}}$. Its slot tree is $\seqst{\conts; \conts; \tagst{\seqst{\strings}\tagsepst \seqst{\bools}}}$, as first a continuation is sent, then another continuation is sent, and finally, a tag is sent followed by either a string or a boolean, depending on the sent tag.

To extend this concept to all session types, we must consider that session types may have multiple segments of data exchange, separated by changes in polarity. We can separate a session type into its segments by replacing every continuation of a different polarity with the unit type of that polarity ($\closet$ or $\waitt$) on the current segment and starting a new segment with the continuation.

For example, we can split $\sendt{\lintt}{\recvt{\lstringt}{\closet}}$ into three segments: first $\sendt{\lintt}{\closet}$, then $\recvt{\lstringt}{\waitt}$ and finally  $\closet$. Each segment is either strictly positive or strictly negative. Strictly negative segments can be turned into strictly positive segments by computing their dual types. Thus, we can map each segment to a slot tree through the $\slots{\theta}{A}$ function defined above.

The slot tree corresponding to the first segment of a session type $A$ is designated as its \textit{active slot tree}  (denoted simply by $\slots{\theta}{A}$), and the slot trees corresponding to the remaining segments as its \textit{remainder slot trees}. Additionally, we denote positive segments as \textit{remote slot trees} and negative segments as \textit{local slot trees}, as positive segments correspond to data which is sent (and thus stored remotely), while negative segments correspond to data which is received (and thus stored locally). The local set of slot trees of a session type $A$ is denoted by $\alllocalslots{\theta}{A}$, and the total set of slot trees by $\allslots{\theta}{A}$. Sets of slot trees are termed \textit{layouts}, as they describe the full set of data that may be exchanged over a session.

\subsection{Instruction Translation}

The \ac{IR} instructions translated from a \ac{CLASS} process $P$ on a given environment $(\theta, \Delta)$ are denoted by $\getinstructions{\theta}{\Delta}{P}$. This function returns a sequence of \ac{IR} instructions, optionally followed by blocks with more instructions, and is defined incrementally in the following sections.

The translated code implements the write-to-read adjustment of the \ac{SAM} through the placement of \texttt{continue} instructions whenever the polarity of a session changes from positive to negative. To simplify the definition of the translation rules, a pseudo-instruction $\texttt{continueIfNegative}$ is defined as
\[
\texttt{continueIfNegative}(\theta, \Delta, x, A) \equiv \begin{cases}
    \begin{array}{l}
        \quad\textcolor{forestgreen}{\texttt{\% }\makeblock{\texttt{label}}} \\
        \quad\texttt{continue}(\continuationof{\Delta}{x}, \texttt{label}) \\
        \texttt{label:} \\
        \hline
    \end{array} & \text{ if } \polarityof{\theta}{A} = -\\
    \quad\ \ \textcolor{forestgreen}{\texttt{\%\ empty}} & \text{ otherwise}\\
\end{cases}
\]
which means that if and only if $\polarityof{\theta}{A} = -$, $\texttt{continueIfNegative}$ is replaced by a \texttt{continue} instruction, and the next instructions are placed in a new block. Otherwise, \texttt{continueIfNegative} is simply removed from the instruction sequence.

\subsection{Expression Translation}

Apart from translating \ac{CLASS} processes to instructions, \ac{CLASS} expressions must also be translated to \ac{IR} expressions. This is necessary for when translating processes such as $\printp$, $\letp$ and $\ifp$. To achieve this, the function $\getexpression{\Delta}{E}$ is defined, which takes a \ac{CLASS} expression $E$ and a session environment $\Delta$, and returns an equivalent \ac{IR} expression. This function is trivially defined recursively through pattern matching on \ac{CLASS} expressions, as they are exactly the same as \ac{IR} expressions, except for session names $x$, for which the translation is defined as
\[
\getexpression{\Delta}{x} = \texttt{move}(\readlocof{\Delta}{x}, S)
\]
where $S$ is the slot corresponding to the type of the session end point $x$, which is guaranteed be a basic type (e.g., $\ints$ for $\colintt$, $\strings$ for $\colstringt$).

\subsection{Exit Point Counting}

One other important aspect of the compilation is counting the number of exit points of the translated \ac{IR} code for a given \ac{CLASS} process. This is necessary to ensure that the translated code properly deallocates the process environment when and only when there's no more code left to execute within it.

The number of exit points in a process $P$ is denoted by $\getendpoints{\theta}{P}$, and is defined by pattern matching on processes. It will be incrementally defined along with the instruction translation function in the following sections.

\subsection{Process Definitions} \label{subsection:ProcessDefinitions}

A \ac{CLASS} program is a set of process definitions, each with a unique name. For each process definition, a set of resulting \ac{IR} processes is generated, one for each possible combination of polarities of its type parameters. This is necessary to ensure that the polarities of type parameters are always known at compile time, as they greatly affect the flow of control of the translated code.

For each resulting \ac{IR} process, an environment $(\theta, \Delta)$ is initialized. The type environment $\theta$ maps each type parameter name to a tuple $(p, t)$ such that $p$ is the polarity of the type parameter in the current combination, and $t$ is a unique identifier for the type parameter, which is inserted into the process header.

The session environment $\Delta$ maps each argument session name to a session state $(c, d, 0)$. If the argument is linear, $\makecont{c}$. Otherwise, $c = 0$, as exponential sessions don't have an associated continuation. In both cases, $\makedata{d}{\alllocalslots{\theta}{A}}$, where $A$ is the type of the argument session. The data layout of $d$ reserves space for all the data which will be received over the session. The offset is initialized to $0$, as no data has been read or written yet.

For each of the exponential arguments of the \ac{CLASS} process definition, a new drop bit is added through $\makedrop{e}{L}{S}$, where $L$ is the location of the exponential data, and $S$ is the slot tree describing the data. This bit $e$ is marked as always set, guaranteeing that the received exponential data is dropped when the process call finishes.

Finally, we generate the instructions for the process body $P$ on the \texttt{entry} block through $\getinstructions{\theta}{\Delta}{P}$, and set the number of exit points of the \ac{IR} process to $\getendpoints{\theta}{P}$.

\subsection{Cut, Parallel and Empty}

The compilation definitions for the $\cutc{P}{x:A}{Q}$ process on an environment $(\theta, \Delta)$ are shown below. It is assumed, without loss of generality, that $\polarityof{\theta}{A} = +$, and thus, that $P$ will be writing to $x$ before $Q$ executes - if $A$ were negative, $P$ and $Q$ could simply be swapped. Both the continuation $c$ and the data section $d$ are created to implement session $x$. The layout $\allslots{\theta}{A}$ is given to $d$, guaranteeing that enough space is allocated for all data received by both end points of $x$.
\begin{compilation}{\theta}{\Delta}{\cutc{P}{x: A}{Q}}
{\getendpoints{\theta}{P} + \getendpoints{\theta}{Q}}
    \commentline{\makecont{c}, \makedata{d}{\allslots{\theta}{A}}, \makeblock{\texttt{rhs}}}
    \initcontinuation{c}{\texttt{rhs}}{d}
    \recurse{\theta}{\Delta[x \mapsto (c, d, 0)]}{P}
    \labelir{rhs}
    \recurse{\theta}{\Delta[x \mapsto (c, d, 0)]}{Q}
\end{compilation}

The instructions initialize the continuation $c$ with a new block $\makeblock{\texttt{rhs}}$ as the return address and $d$ as a writing location. Both $P$ and $Q$ are recursively translated with a new environment where the name $x$ is bound to $(c, d, 0)$. $P$ is placed on the original block, and $Q$ placed on the new block \texttt{rhs}. The number of exit points of the instructions is the sum of the number of exit points of both $P$ and $Q$. 

The $\parc{P}{Q}$ process, contrary to the $\cutp$ process, does not link the two processes $P$ and $Q$ in any way. The \ac{SAM} implements this construct by executing $Q$ only after $P$ has finished executing. The compilation scheme achieves this through the task stack mechanism. $Q$ is compiled block \texttt{rhs}. A task for \texttt{rhs} is pushed to this stack through the \texttt{pushTask} instruction. Eventually, when $P$ finishes execution, \texttt{popTask} executes, and the program counter jumps to \texttt{rhs}, executing $Q$.
\begin{compilation}{\theta}{\Delta}{\parc{P}{Q}}
{\getendpoints{\theta}{P} + \getendpoints{\theta}{Q}}
    \pushtask{rhs} \comment{\makeblock{\texttt{rhs}}}
    \recurse{\theta}{\Delta}{P}
    \labelir{rhs}
    \recurse{\theta}{\Delta}{Q}
\end{compilation}

The $\emptyp$ process represents end of a computation of a process. In this case, control must be passed to the next task in the task stack, potentially terminating the execution. This is achieved through the \texttt{popTask} instruction. Since control might not return to the current \ac{IR} process call, the instruction is marked as an exit point.
\begin{compilation}{\theta}{\Delta}{\emptyc}{1}
    \poptask{\hasexitpoint}
\end{compilation}

\subsection{Close and Wait}

The $\closec{x}$ process indicates that communication over a session $x$ is finished. As on the \ac{SAM}, control is passed to the other end point of $x$, never returning back. This jump is performed with the \texttt{finish} instruction, taking as argument the continuation of session $x$, obtained from $\Delta$. As before, this instruction is marked as an exit point.
\begin{compilation}{\theta}{\Delta}{\closec{x}}{1}
    \finishcont{\continuationof{\Delta}{x}}{\hasexitpoint}
\end{compilation}

The $\waitp$ process is skipped during compilation: $\getendpoints{\theta}{\waitc{x}{P}} \equiv \getendpoints{\theta}{P}$, $\getinstructions{\theta}{\Delta}{\waitc{x}{P}} \equiv \getinstructions{\theta}{\Delta}{P}$. No instructions are generated for the wait action, as the action of waiting for the other side of the channel is already performed implicitly by the \ac{SAM} execution scheme.

\subsection{Let, Scan and Print}

The $\letc{x}{E}$ process is similar to a $\closep$ process, except that before passing control to the other end point of session $x$, an expression $E$ is evaluated and its result is sent over the session. The result is written to the writing location of the continuation of $x$, given by $\writelocof{\Delta}{x}$.

\begin{compilation}{\theta}{\Delta}{\letc{x}{E}}
{1}
    \writeexpr{\writelocof{\Delta}{x}}{\getexpression{\Delta}{E}}
    \finishcont{\continuationof{\Delta}{x}}{\hasexitpoint}
\end{compilation}

The $\scanc{x}$ process is near identical except that instead of computing an expression, the \texttt{writeScan} instruction is used to read from the standard input.

\begin{compilation}{\theta}{\Delta}{\scanc{x}}
{1}
    \writescan{\writelocof{\Delta}{x}}{\slots{\theta}{\tau}} \comment{\text{where } x:\tau}
    \finishcont{\continuationof{\Delta}{x}}{\hasexitpoint}
\end{compilation}

To compile the $\printc{E}P$ and $\printlnc{E}{P}$ processes, a single instruction is generated to print the result of the expression $E$ to the standard output. Compilation then recurses on $P$.

\begin{figure}[H]
    \begin{minipage}{0.45\textwidth}
    \begin{compilation}{\theta}{\Delta}{\printc{E}{P}}
    {\getendpoints{\theta}{P}}
        \print{\getexpression{\Delta}{E}}
        \recurse{\theta}{\Delta}{P}
    \end{compilation}
    \end{minipage}
    \hfill
    \begin{minipage}{0.45\textwidth}
    \begin{compilation}{\theta}{\Delta}{\printlnc{E}{P}}
    {\getendpoints{\theta}{P}}
        \printline{\getexpression{\Delta}{E}}
        \recurse{\theta}{\Delta}{P}
    \end{compilation}
    \end{minipage}
\end{figure}

\subsection{Choice and Branching}

The choice process $\choosec{a}{x}P$ selects the branch labeled \texttt{a} on the offer process at the other end point of session $x$, and then continues as $P$. This selection is implemented by writing a tag indicating the choice to the writing location of $x$, $\writelocof{\Delta}{x}$. This tag is represented by an integer, given by $i(\#a)$, where $i(\#a)$ is the index of the tag \texttt{a} in the alphabetically sorted list of tags in the choice type of $x$.

Since choice is a writing action, a write-to-read adjustment might need to be performed, as in the \ac{SAM}, if the next action on $x$ is a reading action. This is the case if the remainder type of $x$ in $P$ is negative. To implement the write-to-read adjustment, the previously introduced \texttt{continueIfNegative} pseudo-instruction is used.

Finally, instructions for the remainder process $P$ are generated within an environment where offset of channel $x$ is advanced to skip over the written tag. As covered in \Cref{subsubsection:AdvancingOffsets}, the type $A$ of $x$ in $P$ is used to determine whether the offset is advanced or reset to zero. In this case, the offset advances by $\seqst{\tags}$ if and only if the next action to be executed on $x$ is also a writing action, i.e., if $\polarityof{\theta}{A} = +$.
\begin{compilation}{\theta}{\Delta}{\choosec{a}{x}{P}}
{\getendpoints{\theta}{P}}
    \writetag{\writelocof{\Delta}{x}}{i(\#a)}
    \continueifneg{\theta}{\Delta}{x}{A} \comment{\text{where } x:A \text{ in }P}
    \recurse{\theta}{\advancech{\Delta}{x}{+}{\theta}{\seqst{\tags}}{A}}{P}
\end{compilation}

The compilation of a $\casec{x}{\dots}$ process is shown below. The compiler generates code which reads a tag from the local data of session $x$, jumps to the corresponding label and then recurses, generating code for each possible branch, preceded by the respective label. The labels are generated by their alphabetical order, matching the tag written by the \texttt{writeTag} instruction. As before, the offset of channel $x$ is advanced to skip over the read tag, but this time, only if the next action on $x$ is a reading action, i.e., if $\polarityof{\theta}{A} = -$ for the type $A$ of $x$ in each branch.
\begin{compilation}{\theta}{\Delta}{\casec{x}{\labelc{a}{A},\,\dots,\,\labelc{z}{Z}}}
    {\max(\getendpoints{\theta}{A},\,\dots,\,\getendpoints{\theta}{Z})}
    \branchtag{\readlocof{\Delta}{x}}{\texttt{a}:\getendpoints{\theta}{A},\,\dots,\,\texttt{z}:\getendpoints{\theta}{Z}}
    \labelir{a}
    \recurse{\theta}{\advancech{\Delta}{x}{-}{\theta}{\seqst{\tags}}{\tau_A}}{A} \comment{\text{where } x:\tau_A \text{ in }A}
    \beginir\dots
    \labelir{z}
    \recurse{\theta}{\advancech{\Delta}{x}{-}{\theta}{\seqst{\tags}}{\tau_Z}}{Z} \comment{\text{where } x:\tau_Z \text{ in }Z}
\end{compilation}

The number of exit points of branching processes is given by the maximum number of exit points across all branches. During execution, only one branch is executed, and the current exit point count is adjusted accordingly, as described in \Cref{subsection:Branching}.

\subsection{Send and Receive}

The $\sendc{x}{y}{P}Q$ process creates a new session $y$, sending one of its end points over session $x$. The other end point of $y$ is then used in process $P$, while process $Q$ continues using session $x$. To model this behavior, the continuation $c$ and and data section $d$ are created to implement session $y$, where $A$ is the type of session $y$. The layout $\alllocalslots{\theta}{A}$ is given to $d$, guaranteeing that enough space is allocated for all data which will be received by the local end point of $y$.

The continuation $c$ is initialized with a return address pointing to \texttt{lhs} and $d$ as a writing location. The continuation $c$ is then written to the writing location of session $x$, $\writelocof{\Delta}{x}$. As before, a write-to-read adjustment might be necessary, and thus, the \texttt{continueIfNegative} pseudo-instruction is used.

\begin{compilation}{\theta}{\Delta}{\sendc{x}{y}{P}{Q}}
{\getendpoints{\theta}{P} + \getendpoints{\theta}{Q}}
    \commentline{\makecont{c}, \makedata{d}{\alllocalslots{\theta}{A}}, \makeblock{\texttt{lhs}}}
    \initcontinuation{c}{\texttt{lhs}}{d}
    \writecontinuation{\writelocof{\Delta}{x}}{c}
    \continueifneg{\theta}{\Delta}{x}{A} \comment{\text{where } x:A \text{ in }Q}
    \recurse{\theta}{\advancech{\Delta}{x}{+}{\theta}{\seqst{\conts}}{A}}{Q}
    \labelir{lhs}
    \recurse{\theta}{\Delta[y \mapsto (c, d, 0)]}{P}
\end{compilation}

The $\recvc{x}{y}P$ process receives a session end point $y$ over session $x$, which then is used in process $P$. As on the \ac{SAM}, control must be passed to the other side of session end point $y$ if its type is negative, ensuring that the writing side of the session executes first. To receive data through $y$, a data section $d$ is created. A continuation $c$ is also created to bind $y$ to.
\begin{compilation}{\theta}{\Delta}{\recvc{x}{y: A}{P}}
{\getendpoints{\theta}{P}}
    \bindcontinuation{c}{\readlocof{\Delta}{x}}{d} \comment{\makecont{c}, \makedata{d}{\alllocalslots{\theta}{A}}}
    \continueifneg{\theta}{\Delta}{y}{A}
    \recurse{\theta}{\advancech{\Delta}{x}{-}{\theta}{\seqst{\conts}}{B}[y \mapsto (c, d, 0)]}{P} \comment{\text{where } x:B \text{ in }P}
\end{compilation}

\subsection{Forwarding}

Given a process $\fwdc{x}{y}$, it can be assumed without loss of generality that $x$ is of negative type and $y$ of positive type - if this is not the case, $x$ and $y$ can be swapped. Forwarding $x$ to $y$, as on the \ac{SAM}, requires moving any unread data which has already been received on $x$ to $y$. This data is described by $\slots{\theta}{A}$, where $y: A$. For example, if $A = \lintt$, then $\seqst{\ints}$ must be moved from $\readlocof{\Delta}{x}$ to the $\writelocof{\Delta}{y}$. Additionally, the continuations referenced by $x$ and $y$ are linked to each other through the \texttt{forward} instruction, ensuring that future communication happens directly between the other end points of $x$ and $y$. The \texttt{forward} instruction passes control directly to the other end point of $y$, which will not return, and thus, is marked as an exit point.
\begin{compilation}{\theta}{\Delta}{\fwdc{x}{y}}
{1}
    \moveslots{\writelocof{\Delta}{y}}{\readlocof{\Delta}{x}}{\slots{\theta}{A}}
    \forward{\continuationof{\Delta}{x}}{\continuationof{\Delta}{y}}{\hasexitpoint}
\end{compilation}

\subsection{Process Calls}

Process calls are compiled as shown below. The identifier $id$ of the \ac{IR} process to call is obtained from the identifier of the \ac{CLASS} process being called and the polarities of any passed type parameters, matching the scheme used to translate process definitions, covered in \Cref{subsection:ProcessDefinitions}.
\begin{compilation}{\theta}{\Delta}{\proccallgc{processId}{A_1,\,\dots,\,A_n}{x_1,\,\dots,\,x_m;\,y_1,\,\dots,y_k}}{1}
    \callprocess{id}{\hasexitpoint}{T, C, D}
\end{compilation}


The list of \ac{IR} type parameters $T_1,\,\dots,\,T_n$ is generated from the \ac{CLASS} type parameters $A_1,\,\dots,\,A_n$. Each $T_i$ is the active slot tree of type, given by $\slots{\theta}{A_i}$. 

Let $\Delta^*$ be the session environment used to compile the process definition being called, and $x^*_i$ the name of the $i$-th linear argument of the process definition. The list of continuation arguments $C_1,\,\dots,\,C_m$ is generated from the linear arguments $x_1,\,\dots,\,x_m$. Each $C_i$ is a tuple $(c_t, c_s, o)$, where $c_t = \continuationof{\Delta^*}{x^*_i}$ is target continuation, $c_s = \continuationof{\Delta}{x_i}$ is the source continuation, and $o = \offsetof{\Delta}{x_i}$ is the offset to apply to the writing location.

Finally, the list of data arguments $D_1,\,\dots,\,D_{m+k}$ is generated similarly to the continuation arguments, but with extra entries for the exponential arguments. Each $D_i$ is a tuple $(d_t, d_s, t, c)$. For each linear argument $x_i$, $d_t = \localdataof{\Delta^*}{x^*_i}$ is the target data section, $d_s = \readlocof{\Delta}{x}$, $t = \slots{\theta}{\tau}$ is the data slots to be moved, where $x_i: \tau$, and $c$ is the flag indicating whether the argument data should be cloned or moved, which in this case is always \texttt{move}, as $x_i$ is linear. For each exponential argument $y_j$, $d_t = \localdataof{\Delta^*}{y^*_j}$, where $y^*_j$ is the name of the $j$-th exponential argument of the process definition being called, $d_s = \readlocof{\Delta}{y_j}$, $t = \slots{\theta}{\whynott{\tau}}$ where $y_j: \tau$. In this case, $c$ is always \texttt{clone}, as $y_j$ is exponential.

\subsection{Creating and Calling Exponentials}

The right-hand-side $P$ of a $\bangc{x}{y}{P}$ process is compiled as a separate \ac{IR} process, with a unique identifier $id$ generated from the name of the process definition being compiled. This new process inherits the same type parameters as the current process. Session $y$ is bound to a continuation $\makecont{c}$ in the new process header, along with a data section $\makedata{d}{\alllocalslots{\theta}{A}}$, where $y: A$. The number of exit points of the new process is set to $\getendpoints{\theta}{P}$.

The type system of \ac{CLASS} guarantees that free names in $P$ other than $y$ are exponentials. For each free name $z_i \neq y$, a data section $\makedata{d_i}{\alllocalslots{\theta}{\whynott{\tau}}}$ is created in the new process header, where $z_i: \tau$. The environment used to compile $P$ is then $(\theta^*, \Delta^*) = (\theta, [y \mapsto (c, d, 0), z_1 \mapsto (0, d_1, 0), \dots, z_m \mapsto (0, d_m, 0)])$.

On the original process, a \texttt{writeExponential} instruction is generated referencing the new process identifier, passing any necessary arguments. After writing the exponential, control is passed to the continuation of session $x$, as in a $\closep$ process, and thus, the instruction is marked as an exit point.
\begin{compilation}{\theta}{\Delta}{\bangc{x}{y}{P}}
{1}
    \writeexp{\writelocof{\Delta}{x}}{id}{T, D}
    \finishcont{\continuationof{\Delta}{x}}{\hasexitpoint}
\end{compilation}

The list of type arguments $T_1,\,\dots,\,T_n$ is generated from the polarities and identifier of each type parameter in the current type environment $\theta$.

The list of data arguments $D_1,\,\dots,\,D_m$ is generated from the free names in $P$, excluding $y$. Each $D_i$ is a tuple $(d_t, d_s, t, c)$, where $d_t = \localdataof{\Delta^*}{z_i}$, $d_s = \readlocof{\Delta}{z_i}$, $t = \slots{\theta}{\whynott{\tau}}$ where $z_i: \tau$ and $c$ is the flag indicating whether the argument data should be cloned or moved, which in this case is always \texttt{clone}, as all free names in $P$ are exponentials.

The compilation of a $\whynotc{x}P$ process is shown below. A new drop bit $\makedrop{e}{L}{S}$ is created, associated to the slots $S = \slots{\theta}{A}$, where $x: A$, at the location $L = \readlocof{\Delta}{x}$. This drop bit $e$, which points to the received exponential data, is set by the \texttt{deferDrop} instruction, ensuring that the exponential data is dropped when the process call ends.

\begin{compilation}{\theta}{\Delta}{\whynotc{x}{P}}{\getendpoints{\theta}{P}}
    \deferdrop{e}
    \recurse{\theta}{\Delta}{P}
\end{compilation}

\subsection{Unfolding Recursive Sessions}

Unfold processes are compiled such that positive unfolds ($\unfoldmuc{x}P$) always pass control to the opposite end point of $x$, as on the \ac{SAM}. The rationale behind this is that, given $x: A$, if $A$is negative, i.e., the next action on $x$ is a reading action, then control must be passed back to the other end point so that it can write the data before this side reads it. If $A$ is positive, then the next action on $x$ is a writing action, and control must be passed to the other point so that it can read any data which had already been written before the unfold.

Negative unfolds ($\unfoldnuc{x}{P}$) only pass control to their continuation if $A$ is negative, as in this case, the positive end point must have already executed a positive unfold, and thus, given control to this side. Since the positive side must execute first, control must be surrendered back to the opposite end point. Otherwise, if the remainder type is positive, we can continue executing immediately.

In both cases, the process finishes by recursing on the right-hand-side $P$ of the unfold, with a new environment where $x$ is bound to a new channel state equal to its previous state, but with offset $0$, as a new segment of the session type starts. The compilation definitions of both processes are shown below:
\begin{minipage}{0.45\textwidth}
    \begin{compilation}{\theta}{\Delta}{\unfoldmuc{x}{P}}
    {\getendpoints{\theta}{P}}
        \continue{\continuationof{\Delta}{x},\,\texttt{cont}}
        \labelir{cont} 
        \recurse{\theta}{\Delta[x \mapsto (\continuationof{\Delta}{x}, \localdataof{\Delta}{x}, 0)]}{P}
    \end{compilation}
\end{minipage}
\hfill
\begin{minipage}{0.45\textwidth}
    \begin{compilation}{\theta}{\Delta}{\unfoldnuc{x}{P}}
    {\getendpoints{\theta}{P}}
        \commentline{\text{where } x:A \text{ in }P}
        \continueifneg{\theta}{\Delta}{x}{A}
        \recurse{\theta}{\Delta[x \mapsto (\continuationof{\Delta}{x}, \localdataof{\Delta}{x}, 0)]}{P}
    \end{compilation}
\end{minipage}

\subsection{Receiving and Sending Types}

Polymorphism in the \ac{IR} is modeled through process type parameters. Thus, to compile $\recvtyc{x}{X}P$, a new \ac{IR} process must be called in which $X$ is a type parameter. This mechanism is similar to the one used for exponentials, but in this case, the new process may have free linear names which must be passed as continuation arguments. Instead of just one, two \ac{IR} processes are generated: one for when $X$ is negative, another for when $X$ is positive, identified by $id^-$ and $id^+$ respectively.

The information sent by $\sendtyp$ and received by $\recvtyp$ consists of three slots $\seqst{\types; \conts; \tags}$, where $\types$ holds the type parameter information for $X$, $\conts$ holds a continuation to be used for the rest of the session, and $\tags$ indicates the polarity of $X$, with $0$ for negative types and $1$ for positive types. Thus, the $\recvtyp$ process is compiled as a branch on the received tag, calling either $id^-$ or $id^+$ depending on the tag value.
\begin{compilation}{\theta}{\Delta}{\recvtyc{x}{X}P}{1}
    \branchtag{\concatst{\readlocof{\Delta}{x}}{\slotoffset{\seqst{\types; \conts}}}{\seqst{\tags}}}{\texttt{neg:1},\,\texttt{pos:1}}
    \labelir{neg}
    \callprocess{id^-}{\hasexitpoint}{T, C, D}
    \labelir{pos}
    \callprocess{id^+}{\hasexitpoint}{T, C, D}
\end{compilation}

Type parameters $T$ are obtained from the current type environment $\theta$, with an extra entry for $X$, read from $\readlocof{\Delta}{x}$. Continuation arguments and data arguments $C$ and $D$ are generated in the same way as for process calls, from the free names in $P$ and their state in $\Delta$. The name $x$ on the right-hand-side $P$ has its continuation replaced by the continuation at $\concatst{\readlocof{\Delta}{x}}{\slotoffset{\seqst{\types}}{\seqst{\conts; \tags}}}$, and its offset reset to $0$.

On the other hand, the $\sendtyc{x}{A}{P}$ process is compiled in a more direct manner, as shown below. This is possible because the type variable has a concrete type $A$ at the point of sending, known at compile time. First, a new continuation $c$ is initialized with $\texttt{cont}$ as return address, and writing address pointing to a new data section $d$. Then, the type $A$ is written to $x$, along with a reference to $c$ and a $\tags$ indicating $A$'s polarity. Future communication over $x$ will happen through $c$, so the old continuation of $x$ is finished.
\begin{compilation}{\theta}{\Delta}{\sendtyc{x}{A}{P}}
{\getendpoints{\theta}{P}}
    \commentline{\makecont{c}, \makeblock{\texttt{cont}}, \makedata{d}{\alllocalslots{\theta}{B}}, \text{ where }x: B \text{ in }P}
    \initcontinuation{c}{\texttt{cont}}{d}
    \writetype{\writelocof{\Delta}{x}}{\slots{\theta}{A}}
    \writecontinuation{\concatst{\writelocof{\Delta}{x}}{\slotoffset{\seqst{\types}}}{\seqst{\conts; \tags}}}{c}
    \writetag{\concatst{\writelocof{\Delta}{x}}{\slotoffset{\seqst{\types; \conts}}{\seqst{\tags}}}}{p} \comment{\text{where } p = 0 \text{ if } \polarityof{\theta}{A} = - \text{ or } 1 \text{ otherwise}}
    \finishcont{\continuationof{\Delta}{x}}{\hasexitpoint}
    \labelir{cont}
    \recurse{\theta}{\Delta[x \mapsto (c, d, 0)]}{P}
\end{compilation}

\subsection{Affine, Use and Discard}

The compilation of the $\affinec{x}P$ process, shown below, implements the affine protocol mentioned in \Cref{subsection:IRDroppingData}: a $\tags$ indicating whether $x$ is being used or discarded is received on $x$. If $x$ is being used, the execution continues to $P$. If $x$ is discarded, any co-affine data free in $P$ is also discarded and the $x$ is finished, returning control to the end point which discarded $x$.
\begin{compilation}{\theta}{\Delta}{\affinec{x}{P}}
{\getendpoints{\theta}{P}}
    \branchtag{\localdataof{\Delta}{x}}{\texttt{use:}\getendpoints{\theta}{P},\,\texttt{discard:1}}
    \labelir{use}
    \recurse{\theta}{\advancech{\Delta}{x}{-}{\theta}{\seqst{\tags}}{A}}{P} \comment{\text{where } x:A \text{ in }P}
    \labelir{discard}
    \recurse{\theta}{\Delta}{\discardc{y_i}} \comment{\text{for each free co-affine name }y_i\text{ in }P}
    \finishcont{\continuationof{\Delta}{x}}{\hasexitpoint}
\end{compilation}

The process $\discardc{x}$ writes a discard tag to the writing location of $x$ and passes control to it. When control returns, the current task is finished, as the $\discardp$ process has no remainder process. However, if this discard was generated as part of the discard branch of an affine process, the \texttt{popTask} instruction is not generated, as control must return to the continuation of the affine process.

\begin{compilation}{\theta}{\Delta}{\discardc{x}}
{1}
    \writetag{\writelocof{\Delta}{x}}{1} \comment{\text{indicating discard}}
    \continue{\continuationof{\Delta}{x},\,\texttt{cont}}
    \labelir{cont}
    \poptask{\hasexitpoint} \comment{\text{unless part of an affine discard branch}}
\end{compilation}

Finally, the $\usec{x}{P}$ process is compiled as shown below. A tag is written to the remote data of channel $x$ indicating that the session is being used. Then, if the continuation is negative, the control is passed to the other side of the session. Otherwise, the process continues executing immediately.
\begin{compilation}{\theta}{\Delta}{\usec{x}{P}}
{\getendpoints{\theta}{P}}
    \writetag{\writelocof{\Delta}{x}}{0} \comment{\text{indicating use}}
    \continueifneg{\theta}{\Delta}{x}{A} \comment{\text{where } x:A \text{ in }P}
    \recurse{\theta}{\advancech{\Delta}{x}{+}{\theta}{\seqst{\tags}}{A}}{P}
\end{compilation}

\subsection{Shared State}

The process $\cellc{x}{y}{P}$ writes a new shared cell to channel $x$, initialized with a new session $y$ which is used in process $P$. Similarly to $\letc{x}{E}$, session $x$ is finished after writing the cell. A continuation $c$ and a data section $d$ are created to implement session $y$. The written cell is initialized with space for a single $\conts$ slot, to which a reference to $c$ is written. Continuation $c$ is initialized with \texttt{cont} as its return address, and $d$ as writing location.
\begin{compilation}{\theta}{\Delta}{\cellc{x}{y}{P}}
{\getendpoints{\theta}{P} + 1}
    \commentline{\makecont{c}, \makeblock{\texttt{cont}}, \makedata{d}{\alllocalslots{\theta}{A}} \text{ where } y:A \text{ in }P}
    \writecell{\writelocof{\Delta}{x}}{\seqst{\conts}}
    \initcontinuation{c}{\texttt{cont}}{d}
    \writecontinuation{c(\writelocof{\Delta}{x})}{c}
    \finishcont{\continuationof{\Delta}{x}}{\hasexitpoint}
    \labelir{cont}
    \recurse{\theta}{\Delta[y \mapsto (c, d, 0)]}{P}
\end{compilation}

The process $\takec{x}{y}P$ operates on a shared cell received on $x$. It starts by locking the cell through the \texttt{lockCell} instruction. Then, the continuation stored in the cell is read and bound to a new continuation $c$. The writing location of $c$ is set to a new data section $d$. Given $y: A$ in $P$, if $A$ is negative, control must be passed to the other end point of $y$, such that data is written to $d$.
\begin{compilation}{\theta}{\Delta}{\takec{x}{y}{P}}
{\getendpoints{\theta}{P}}
    \commentline{\makecont{c}, \makedata{d}{\alllocalslots{\theta}{A}}}
    \lockcell{\readlocof{\Delta}{x}}
    \bindcontinuation{c}{c(\readlocof{\Delta}{x})}{d}
    \continueifneg{\theta}{\Delta}{y}{A} \comment{\text{where } y:A \text{ in }P}
    \recurse{\theta}{\Delta[y \mapsto (c, d, 0)]}{P}
\end{compilation}

The process $\putc{x}{y}{P}Q$, similarly to the $\cellp$ process, initializes a new session $y$. In this case, the existing cell is written to, instead of creating a new cell. After writing to the cell, it is unlocked, and execution continues on process $Q$.
\begin{compilation}{\theta}{\Delta}{\putc{x}{y}{P}{Q}}
{\getendpoints{\theta}{P} + \getendpoints{\theta}{Q}}
    \commentline{\makecont{c}, \makeblock{\texttt{lhs}}, \makedata{d}{\alllocalslots{\theta}{A}} \text{ where } y:A \text{ in }P}
    \initcontinuation{c}{\texttt{lhs}}{d}
    \writecontinuation{c(\readlocof{\Delta}{x})}{c}
    \unlockcell{\readlocof{\Delta}{x}}
    \recurse{\theta}{\Delta}{Q}
    \labelir{lhs}
    \recurse{\theta}{\Delta[y \mapsto (c, d, 0)]}{P}
\end{compilation}

The process $\releasec{x}$ decrements the reference count of the cell at session $x$ through \texttt{releaseCell}. The responsibility of correctly dropping the cell's contents when the reference count reaches zero is abstracted away by the \ac{IR}. This process finishes the current task, similarly to $\discardc{x}$.
\begin{compilation}{\theta}{\Delta}{\releasec{x}}{1}
    \releasecell{\readlocof{\Delta}{x}}
    \poptask{\hasexitpoint}
\end{compilation}

Finally, the $\sharec{x}{P}{Q}$ process shares a cell $x$ between $P$ and $Q$, which are executed concurrently. Since the cell is going to be shared, its reference count is incremented through \texttt{acquireCell}. If concurrency is enabled, a new thread is launched to execute the right-hand-side $Q$ of the share process, as shown below. If concurrency is disabled, the right-hand-side is instead added as a new task to the task queue, which will be executed when the left-hand-side finishes.
\begin{compilation}{\theta}{\Delta}{\sharec{x}{P}{Q}}
{\getendpoints{\theta}{P} + \getendpoints{\theta}{Q}}
    \acquirecell{\readlocof{\Delta}{x}}
    \launchthread{\texttt{rhs}}
    \recurse{\theta}{\Delta}{P}
    \labelir{rhs}
    \recurse{\theta}{\Delta}{Q}
\end{compilation}

\section{Translating the IR to C} \label{section:IRtoC}

The last phase of the compilation pipeline is the translation from the \ac{IR} to C. This phase takes as input the \ac{IR} produced by the compilation scheme described in the previous section, and produces a C program which implements the semantics of the \ac{IR}. This C program can then be compiled with \ac{GCC} to produce an executable which runs a computation equivalent to the original \ac{CLASS} program. The translated code depends only on the standard C library and on \texttt{pthread}, if concurrency is enabled. Additionally, it makes extensive use of the \ac{GCC} extension for computed gotos, used to efficiently implement continuations.

This section starts by describing how the slot trees are translated to concrete data structures in C. Then, an overview of the the C representation of \ac{IR} environments is given. Next, the code layout of the translated C program is laid out. Finally, the implementation in C of the main instructions of the \ac{IR} abstract machine is described.

\subsection{Representing Slot Trees in C}

In the \ac{IR} abstract machine, the concept of data is abstracted away into slots, covered in \Cref{subsection:IRSlots}. A slot tree describes the possible sequences of slots which may be stored in a data section. A set of slot trees describes the multiple possible slot trees which may be stored in a data section, only one of them being active at any given time.

When translating \ac{IR} programs to C code, these slot trees must be translated to concrete, byte-addressed, memory layouts. To this end, a memory layout is defined as a tuple $L = (s, a)$, where $s$ is the size in bytes of the layout, and $a$ is the alignment in bytes the layout must have in memory. Both $s$ and $a$ are not constants, but C expressions which can be evaluated at runtime. This is necessary due to type parameters having layouts known only at runtime.

In order to satisfy the alignment requirements of the various C types used to implement the \ac{IR} abstract machine, a C macro \texttt{ALIGN(s, a)} is defined, which rounds up the size \texttt{s} to the nearest multiple of the alignment \texttt{a}. This macro is used extensively when computing memory layouts. Additionally, a C macro \texttt{MAX(a, b)} is defined, which computes the maximum of two integers \texttt{a} and \texttt{b}.

Two memory layouts $L_1 = (s_1, a_1), L_2 = (s_2, a_2)$ can be concatenated to form a new layout $L = L_1 + L_2$, where $L = (\texttt{ALIGN}(s_1, s_2) + s_2,\ \texttt{MAX}(a_1, a_2))$, such that $L_1$ is placed first in memory, followed by $L_2$, with padding added to ensure that $L_2$ starts at an address which is a multiple of $a_2$. Additionally, the maximum of two layouts $L = L_1 \vee L_2$ is defined as $L = (\texttt{MAX}(s_1, s_2),\ \texttt{MAX}(a_1, a_2))$.

The memory layout of a slot $S$ on a given target architecture $\arch$ is denoted by $\slotlayout{\sigma}{S}$, defined as
\[\begin{aligned}
    &\begin{aligned}
        &\slotlayout{\sigma}{\ints} = \archlayout{int} && \slotlayout{\sigma}{\bools} = \archlayout{unsigned char} \\
        &\slotlayout{\sigma}{\strings} = \archlayout{char*} && \slotlayout{\sigma}{\conts} = \archlayout{struct cont*} \\
        &\slotlayout{\sigma}{\tags} = \archlayout{unsigned char} && \slotlayout{\sigma}{\types} = \archlayout{struct type} \\
        &\slotlayout{\sigma}{\exponentials} = \archlayout{struct exponential*} && \slotlayout{\sigma}{\cells{\dots}} = \archlayout{struct cell*} \\
    \end{aligned}\\
    &\slotlayout{\sigma}{t_i} = \layoutofvar{\sigma}{t_i}\\
\end{aligned}\]
where $\sigma$ is a map between type parameters and their layouts. A target architecture $\arch$ is a mapping from C types to their memory layouts, such that $\archlayout{type} = (s, a)$ where $s$ and $a$ where, respectively, the size and alignment of \texttt{type} on the target architecture. A definition of $\sigma$ will be introduced in the next section.

The definition of $\slotlayout{\sigma}{s}$ is extended below to support both slot trees, and sets of slot trees. The layout of a slot tree is defined as the concatenation of the layouts of each of its slots, and maximum across any branches, while the layout of a set of slot trees is defined as the maximum layout among all its trees.
\[\begin{aligned}
    &\slotlayout{\sigma}{\nilst} = (0, 1) \quad & & \slotlayout{\sigma}{\seqst{S; T}} = \slotlayout{\sigma}{S} + \slotlayout{\sigma}{T}\\
    &\slotlayout{\sigma}{\tagst{T_1 \tagsepst \dots \tagsepst T_n}} = \bigvee_{i=1}^{n} \slotlayout{\sigma}{T_i} \quad & & \slotlayout{\sigma}{\left\{T_1,\,\dots,\,T_n\right\}} = \bigvee_{i=1}^{n} \slotlayout{\sigma}{T_i}
\end{aligned}\]

\subsection{Environment Memory Layout} \label{subsection:CEnvironments}

\ac{IR} environments store all state related to a process invocation. In the translated C programs, environments are represented as heap allocated byte buffers. The environment layout $\envlayout$ specifies at compile time how environment buffers will be indexed at runtime.

An environment layout $\envlayout$ is a compile-time data structure which describes the byte offsets at which each entry of the environment can be found. This layout is computed from the header of the \ac{IR} process being compiled. The address of the exit point counter (a C integer or atomic integer if concurrency is enabled) is given by $\envlayouteps{\texttt{env}}$ where \texttt{env} is a pointer to the environment. Drop bits are stored at $\envlayoutdrop{\texttt{env}}$, type information for type variable $t_i$ is stored at $\envlayouttype{\texttt{env}}{t_i}$, continuations $c_i$ are stored at $\envlayoutcont{\texttt{env}}{c_i}$, and data sections $d_i$ at $\envlayoutlocal{\texttt{env}}{d_i}$.

The layout of the environment is computed trivially by concatenating the layouts of each of its entries, in the order they appear in the process header. The layout for data sections is the most noteworthy, as it depends on the stored data type. This layout is computed from $\slotlayout{\sigma}{S}$, where $S$ is the set of slot trees of the data section, and $\sigma(t_i) = \texttt{access}(\envlayouttype{\texttt{env}}{t_i})$ is a mapping between type parameters and their layouts, fetched from the environment itself.

Continuations are stored in environments as instances of the C type \texttt{struct cont}, shown below. Continuations store a return address to jump to (\texttt{loc}), a pointer to the environment to switch to before jumping (\texttt{env}), a pointer to the writing location (\texttt{write}), and a pointer to the continuation pertaining to the other end point of the session (\texttt{remote}).

\begin{lstlisting}[language=C, frame=bottom]
struct cont {
  void* loc;
  char* env;
  char* write;
  struct cont* remote;
};
\end{lstlisting}

Type information is stored in the environment as instances of the C type \texttt{struct type}, shown below. This structure holds the \texttt{size} and \texttt{alignment} of the data described by the type. This structure is also used to store the value of $\types$ slots in the data sections.

\begin{lstlisting}[language=C, frame=bottom]
struct type {
    int size;
    int alignment;
};
\end{lstlisting}

\subsubsection{Environment Cleanup} \label{subsubsection:CEnvironmentCleanup}

Whenever an instruction decrements the exit point counter, it checks if it reached zero. If so, any drop bits set in the environment are processed, dropping their associated data. Then, the environment itself is freed. The following C snippet illustrates this cleanup code, where \texttt{env} points to the environment.

\begin{lstlisting}[language=C, frame=bottom]
if (atomic_fetch_sub(&(*(atomic_int*)(env)), 1) == 1) {
    if ((*(unsigned char*)(env + 4)) & (1 << 0)) {
        /* drop data associated to drop bit 0 */
    }
    /* other drop bit checks... */
    managed_free(env);
}
\end{lstlisting}

\subsection{Execution and Registers}

The \texttt{main} function of the generated C program initializes any required global state, such as the allocator, or profiling tools, and invokes a function named \texttt{executor} with a \texttt{NULL} argument. The \texttt{executor} function is the core of the \ac{IR} abstract machine implementation. Each thread of execution runs its own instance of this function, receiving as argument a pointer to its entry task.

At the start of the \texttt{executor} function, registers used to implement the \ac{IR} instructions are declared. The first two registers \texttt{task} and \texttt{env} respectively store pointers to the head of the task stack (introduced in the next subsection) and the current environment, which is state kept across \ac{IR} instructions. The rest of the registers are used to store temporary values used within the execution of each instruction. After declaring the registers, the thread state is initialized.

\begin{lstlisting}[language=C, frame=bottom]
void executor(struct task* entry) {
    /* Registers */
    register struct task* task;
    register char* env;
    register void* tmp_ptr1;
    register void* tmp_ptr2;
    register int tmp_int;
    struct cont tmp_cont;
    /* Initialize thread state (...) */
\end{lstlisting}

After initializing the thread state, control is passed to the entry task (received as argument), which contains a continuation address and environment. If the entry task is \texttt{NULL}, the main process is called instead, as shown below. To call the main process, a new environment is allocated with the size computed from its header, and a jump is performed to its entry block.

\begin{lstlisting}[language=C, frame=bottom]
    if (entry == NULL) {
        /* callProcess(main) */
        tmp_ptr1 = managed_alloc(144);
        env = ((char*)(tmp_ptr1));
        goto main_entry;
    } else {
        env = entry->env;
        tmp_ptr1 = entry->loc;
        managed_free(entry);
        goto *tmp_ptr1;
    }
\end{lstlisting}

After these instructions, still within the \texttt{executor} function, for each block of each process a unique C label is generated, followed by the C code generated from the \ac{IR} instructions in the block. Finally, a label named \texttt{end} is generated, which represents the end of the thread's execution.

\begin{lstlisting}[language=C, frame=bottom]
main_entry:
    /* instructions of main's entry block ... */
foo_cut_lhs_0:
    /* instructions of foo's cut_lhs_0 block ... */
    /* other blocks ... */
end:
    return 0;
}
\end{lstlisting}

\subsection{Tasks}

Tasks are stored in a linked list local to each thread of execution, where each node is of the type shown below. The \texttt{task} register points to the head node of this stack. The \texttt{next} field points to the next task to be executed, while the \texttt{loc} and \texttt{env} fields store the code address and environment to switch to when executing the task. 

\begin{lstlisting}[language=C, frame=bottom]
struct task {
    struct task* next;
    void* loc;
    char* env;
};
\end{lstlisting}

The \texttt{task} register is initialized at the start of the \texttt{executor} function with a dummy task which jumps to the \texttt{end} label, ending the thread's execution. This dummy task is necessary to ensure that the task stack is never empty, simplifying the implementation of the \texttt{popTask} instruction.

\begin{lstlisting}[language=C, frame=bottom]
task = managed_alloc(sizeof(struct task));
task->loc = &&end;
\end{lstlisting}

The two \ac{IR} instructions for manipulating tasks, \texttt{pushTask} and \texttt{popTask}, manipulate the linked list of tasks pointed to by the \texttt{task} register. The first instruction, \texttt{pushTask}, allocates a new task, sets its continuation to the C label of the chosen block, and inserts it at the head of the linked list. The generated C code for this instruction is shown below.

\begin{lstlisting}[language=C, frame=bottom]
/* pushTask(cont) */
tmp_ptr1 = task;
task = managed_alloc(sizeof(struct task));
task->next = ((struct task*)(tmp_ptr1));
task->loc = &&proc_cont; /* proc_cont is the C label of block 'cont' */
task->env = env;
\end{lstlisting}

The \texttt{popTask} instruction, whose generation is shown below, removes the first task from the linked list, changes the current environment and jumps to its continuation.

\begin{lstlisting}[language=C, frame=bottom]
/* popTask() */
tmp_ptr1 = task;
tmp_ptr2 = task->loc;
env = task->env;
task = task->next;
managed_free(tmp_ptr1);
goto *tmp_ptr2;
\end{lstlisting}

\subsection{Continuation Manipulation}

The \texttt{initContinuation} instruction is compiled as shown below. The continuation at $\envlayoutcont{\texttt{env}}{c_0}$ (in this example, $\texttt{env} + 8$) is initialized with the given program label, the current environment, the address $\envlayoutlocal{\texttt{env}}{d_0}$ (in this case, $\texttt{env} + 40$) as its writing location data, and a pointer to itself as its remote continuation.

\begin{lstlisting}[language=C, frame=bottom]
/* initContinuation(c0, cut_lhs_0, d0) */
(*(struct cont*)(env + 8)) = (struct cont){
    .loc=&&main_cut_lhs_0,
    .env=env,
    .write=env + 40,
    .remote=env + 8
};
\end{lstlisting}

The compilation of the \texttt{finish} instruction is shown below. First, the remote continuation of the finished continuation is unlinked from this continuation by setting its \texttt{remote} field to itself. This is necessary to avoid use after free errors in instructions such as \texttt{forward} and \texttt{callProcess}. Then, the target location and environment is stored on the registers and the environment's exit point counter is decremented atomically (when concurrency is disabled, a normal integer is used instead). If the counter reaches zero, the environment cleanup code described in \Cref{subsubsection:CEnvironmentCleanup} is executed. Finally, the environment and code address are switched to the continuation values, and a jump is performed.

\begin{lstlisting}[language=C, frame=bottom]
/* finish(c0, exit point) */
(struct cont*)(env + 8)->remote->remote = (struct cont*)(env + 8)->remote;
tmp_ptr1 = (*(struct cont*)(env + 8)).loc;
tmp_ptr2 = (*(struct cont*)(env + 8)).env;
if (atomic_fetch_sub((atomic_int*)(env), 1) == 1) {
    /* environment cleanup code */
}
env = ((char*)(tmp_ptr2));
goto *tmp_ptr1;
\end{lstlisting}

The \texttt{continue} instruction is compiled similarly to \texttt{finish}, as shown below, except that the exit point counter is not decremented, and that the remote continuation must instead be updated so that it eventually jumps back to the correct label.

\begin{lstlisting}[language=C, frame=bottom]
/* continue(c0, continue_12) */
tmp_ptr1 = (*(struct cont*)(env + 8)).loc;
(*(*(struct cont*)(env + 8)).remote).loc = &&main_continue_12;
env = (*(struct cont*)(env + 8)).env;
goto *tmp_ptr1;
\end{lstlisting}

The \texttt{forward} instruction first stores the continuation of its second argument in the temporary registers. Then, it sets the remotes of both argument continuations to point to each other, ensuring no references are left to the local continuations. A temporary variable is used to store the first argument continuation, as its value may be overwritten due to the possibility of a continuation being its own remote. Finally, the exit point counter is decremented, and control is passed to the location and environment stored in the temporary registers.

\begin{lstlisting}[language=C, frame=bottom]
/* forward(c0, c1, exit point) */
tmp_ptr1 = (*(struct cont*)(env + 40)).loc;
tmp_ptr2 = (*(struct cont*)(env + 40)).env;
tmp_cont = *(struct cont*)(env + 8);
*(*(struct cont*)(env + 8)).remote = *(struct cont*)(env + 40);
*(*(struct cont*)(env + 40)).remote = tmp_cont;
if (atomic_fetch_sub(*(atomic_int*)(env), 1) == 1) {
    /* environment cleanup code */
}
env = (char*)tmp_ptr2;
goto *tmp_ptr1;
\end{lstlisting}

\subsection{Exponentials}

Exponentials are reference counted, heap allocated structures, represented in C by the type shown below. Each exponential stores stores a template for the environments to be created when the exponential is called. The \texttt{entry\_cont\_offset} field stores the byte offset the argument continuation is stored at on the environment template, while the \texttt{entry\_data\_offset} field stores the byte offset the argument data is stored at. The \texttt{env\_size} field stores the size in bytes of the environment template, while the \texttt{manager} field stores a code location, known as the exponential's manager, which is responsible for cloning and dropping the exponential's template environment. Finally, the flexible array member \texttt{env} stores the actual environment template data.

\begin{lstlisting}[language=C, frame=bottom]
struct exponential {
    atomic_int ref_count;
    int entry_cont_offset;
    int entry_data_offset;
    int env_size;
    void* manager;
    char env[];
};
\end{lstlisting}

The \texttt{writeExponential} instruction is compiled as shown below. First, a new exponential structure is allocated with enough space to store the environment template, and its fields are initialized. The reference count is initialized to $1$, the offsets and size are computed from the environment layout of the exponential process, and the manager is set to a new unique C label. The environment template is initialized based on the exponential process header. The argument continuation is initialized to point to the entry block of the exponential process, and any argument types or data are written.

\begin{lstlisting}[language=C, frame=bottom]
/* writeExponential(d0, main_exp0) */
*(struct exponential**)(env + 64) = managed_alloc(60);
(*(struct exponential**)(env + 64))->ref_count = 1;
(*(struct exponential**)(env + 64))->entry_cont_offset = 0;
(*(struct exponential**)(env + 64))->entry_data_offset = 32;
(*(struct exponential**)(env + 64))->env_size = 36;
(*(struct exponential**)(env + 64))->manager = &&main_exp0_exp_manager;
tmp_ptr1 = (*(struct exponential**)(env + 64))->env;
(*(struct cont*)(((char*)(tmp_ptr1)) + 0)).loc = &&main_exp0_entry;
// (...) write argument types and data to environment tmp_ptr1 ...
\end{lstlisting}

The exponential manager is a block of code which when jumped to, branches on the value of \texttt{tmp\_int}, which is set to $0$ for cloning the exponential, and to $1$ for dropping it. If cloning, the current environment is assumed to be the newly allocated environment for the exponential call, while \texttt{tmp\_ptr1} is assumed to be the environment template stored in the exponential. If dropping, the current environment is assumed to be the environment template stored in the exponential. The cloning branch clones the argument data from the environment template into the new environment, while the dropping branch drops the argument data in the environment template. Finally, in both cases, control is passed to the argument continuation stored in the exponential environment.

\begin{lstlisting}[language=C, frame=bottom]
main_exp0_exp_manager:
    if (tmp_int == 0) {
        /* (...) clone argument data from environment tmp_ptr1 to env */
    } else {
        /* (...) drop argument data in environment env */
    }
    tmp_ptr2 = (*(struct cont*)(env + 0)).loc;
    env = (*(struct cont*)(env + 0)).env;
    goto *tmp_ptr2;
\end{lstlisting}

The \texttt{callExponential} instruction, compiled as shown below, first allocates a new environment for the exponential call with the size stored in the exponential structure. This environment is initialized through a memory copy from the exponential's template environment, and is set as the environment of the produced continuation. Then, the produced continuation and data is connected to the argument continuation in the new environment, and finally the exponential manager is jumped to, with \texttt{tmp\_int} set to $0$ to indicate a clone operation. When finished, control is passed back to the label \texttt{main\_exp\_call\_return\_0}.

\begin{lstlisting}[language=C, frame=bottom]
    /* callExponential(d0, c0, d1) */
#define exp (*(struct exponential**)(env + 64))
#define exp_env (*(struct cont*)(env + 0)).env
#define exp_session (*(struct cont*)(exp_env + exp->entry_cont_offset))
    exp_env = managed_alloc(exp->env_size);
    memcpy(exp_env, exp->env, exp->env_size);
    (*(struct cont*)(env + 0)).loc = exp_session.loc;
    ((env + 0)).write = exp_env + exp->entry_data_offset;
    (*(struct cont*)(env + 0)).remote = &exp_session;
    exp_session.env = env;
    exp_session.write = env + 72;
    exp_session.remote = env;
    exp_session.loc = &&main_exp_call_return_0;
    tmp_ptr1 = exp->env;
    tmp_ptr2 = exp->manager;
    tmp_int = 0;
    env = exp_env;
    goto *tmp_ptr2;
main_exp_call_return_0:

\end{lstlisting}

When the reference count of an exponential reaches zero, the control is passed to its manager with \texttt{tmp\_int} set to $1$, indicating a drop operation, and the current environment set to the exponential's template environment. Control is then returned to the drop caller and the exponential structure is freed.

\subsection{Data Manipulation}

The \texttt{moveSlots}, \texttt{cloneSlots} and \texttt{dropSlots} instructions are compiled using a \textit{slot traversal} utility function, which recursively generates C code to visit each slot address given a slot tree and a base address. This is necessary due to the complexity of slots trees, which may branch both due to the presence of tags (\ac{CLASS} choices) and due to polymorphic types.

For example, to move, clone or drop a slot tree $T = \tagst{\seqst{\strings}\tagsepst\seqst{\exponentials}}$, different code must be generated depending on whether the tag indicates that the first or second branch is active. Cloning a $\strings$ slot implies allocating a new string and copying the original string, while cloning an $\exponentials$ slot implies incrementing the reference count of the exponential value. Below is the generated C code for the \texttt{cloneSlots} instruction, operating on the slot tree $T$ described above, assuming $d_1$ is at $\texttt{env} + 32$, both $\datal{d_1}{\tags}{\strings}$ and $\datal{d_1}{\tags}{\exponentials}$ are at $\texttt{env} + 40$, $d_0$ at $\texttt{env} + 48$ and both $\datal{d_0}{\tags}{\strings}$ and $\datal{d_0}{\tags}{\exponentials}$ are at $\texttt{env} + 56$.

\begin{lstlisting}[language=C, frame=bottom]
/* cloneSlots(d1, d0, tag[string | exponential]) */
*(unsigned char*)(env + 32) = *(unsigned char*)(env + 48);
switch (*(unsigned char*)(env + 48)) {
    case 0: /* string */
        *(char**)(env + 40) = *(char**)(env + 56);
        *(char**)(env + 40) = string_clone(*(char**)(env + 40));
        break;
    case 1: /* exponential */
        *(struct exponential**)(env + 40) = *(struct exponential**)(env + 56);
        /* ... increment reference count */
        break;
}
\end{lstlisting}

Moves of slots $s$ are always generated as simple memory copies of size given by $\slotlayout{\sigma}{s}$. Clones and drops, on the other hand, are generated by pattern matching on the slot $s$, generating the appropriate code for each case. Cloning and dropping basic types such as $\ints$, $\bools$ and $\tags$ slots is a no-op, while cloning and dropping other slots may involve memory (de)allocation and reference count manipulation, as shown in the example above.

To clone or drop type parameter slots $t_i$, type information for each type parameter $t_i$ is stored alongside the environment buffer, describing, at run-time, the slots which must be cloned or dropped within the type parameter. This type information is generated when a new environment is created, or when type information is stored using the \texttt{writeType} instruction.

\subsection{Process Calls}

Process calls are performed through the \texttt{callProcess} instruction. This instruction receives the identifier of the process to be called, a list of type parameters, a list of continuation arguments and a list of data arguments. The generated C code for this instruction is shown below.

\begin{lstlisting}[language=C, frame=bottom]
/* callProcess(foo, exit point, c0 <- c0) */
tmp_ptr1 = managed_alloc(40);
(*(atomic_int*)(((char*)(tmp_ptr1)))) = 1; // setup exit points
/* (...) pass type, continuation and data arguments */
if (atomic_fetch_sub(&(*(atomic_int*)(env)), 1) == 1) {
    /* environment cleanup code */
}
env = ((char*)(tmp_ptr1));
goto foo_entry;
\end{lstlisting}

Type parameters are passed by writing their information to the appropriate offsets in the new environment. Continuation arguments are passed by initializing the continuations in the new environment, and connecting them to the local continuations passed as arguments. This implies updating the remote of the argument continuations to point to the continuations in the new environment. Finally, data arguments are passed by simply moving or cloning the data from the current environment to the new environment, in the same way as the \texttt{moveSlots} and \texttt{cloneSlots} instructions.

Before jumping to the entry block of the called process, the exit point counter of the current environment is decremented, and if it reaches zero, the current environment is cleaned up and freed, as described in \Cref{subsubsection:CEnvironmentCleanup}. Control is only then passed to the entry block of the called process.

\subsection{Cell Operations}

Cells are implemented in C as heap-allocated instances of the type shown below. The first three fields, \texttt{mutex}, \texttt{cond\_var} and \texttt{is\_free}, are used to implement the locking mechanism of the cell. The \texttt{ref\_count} field is an atomic integer which stores the reference count of the cell, while the flexible array member \texttt{data} stores the actual contents of the cell, similarly to a data section in an environment.

\begin{lstlisting}[language=C, frame=bottom]
struct cell {
    pthread_mutex_t mutex;
    pthread_cond_t cond_var;
    unsigned char is_free;
    atomic_int ref_count;
    char[] data;
};
\end{lstlisting}

The \texttt{writeCell} instruction is simply compiled as the allocation of a new \texttt{struct cell} with enough space to store its data section, and the initialization of its fields. The \texttt{acquireCell} and \texttt{releaseCell} instructions are compiled respectively as the atomic increment and decrement of the cell's reference count. If the reference count reaches zero, the cell's data is dropped, the cell's mutex and condition variable are destroyed, and finally the cell itself is freed.

The cell locking/unlocking operations cannot be implemented with a simple mutex lock/unlock pair, as it is possible for a locked cell to be passed to another thread, which must then be able to unlock it. This violates the requirement that \texttt{pthread} mutexes can only be unlocked by the thread which locked them. To workaround this, the \texttt{is\_free} flag indicates if the cell is locked or not, and the mutex and condition variable are used solely to synchronize access to this flag. The \texttt{lockCell} instruction thus compiled as shown below. First, the cell's mutex is locked. Then, while the cell is not free, the thread waits on the cell's condition variable, atomically releasing the mutex while waiting, and re-acquiring it when woken up. When the cell is free, it is marked as not free, and the mutex is unlocked.

\begin{lstlisting}[language=C, frame=bottom]
/* lockCell(d0) */
pthread_mutex_lock(&((*(struct cell**)(env + 16))->mutex));
while (!(*(struct cell**)(env + 16))->is_free) {
    pthread_cond_wait(&(*(struct cell**)(env + 16)->cond_var),
                      &(*(struct cell**)(env + 16))->mutex);
}
(*(struct cell**)(env + 16))->is_free = 0;
pthread_mutex_unlock(&((*(struct cell**)(env + 16))->mutex));
\end{lstlisting}

The \texttt{unlockCell}, shown below, locks the cell's mutex, marks the cell as free, signals one thread waiting on the cell's condition variable (if any), and finally unlocks the mutex.

\begin{lstlisting}[language=C, frame=bottom]
/* unlockCell(d0) */
pthread_mutex_lock(&(*(struct cell**)(env + 16))->mutex);
(*(struct cell**)(env + 0))->is_free = 1;
pthread_cond_signal(&(*(struct cell**)(env + 16))->cond_var);
pthread_mutex_unlock(&(*(struct cell**)(env + 16))->mutex);
\end{lstlisting}
