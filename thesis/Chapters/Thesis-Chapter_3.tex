\label{chap:architecture}

The solution developed on this thesis to the problem of compiling \ac{CLASS} programs to native code is a compilation scheme heavily based on the \ac{SAM} interpreter. Execution is done sequentially and deterministically, with the compiler generating code that closely resembles the execution of the \ac{SAM}, implementing continuation-based coroutining.
Associated to each process is a block of data called an environment, similar to a stack frame of traditional imperative languages. This environment stores the continuations of each session, as well as any data received through them. Whenever a process finishes writing data to a session, a jump is made to its other end point, which will read the data and continue execution.

At a high-level, the compilation scheme is divided into four phases. First, the source \ac{CLASS} program is parsed and type-checked. This phase is not discussed in this report, as its implementation has been reused from the previous work \cite{Rocha:2023, Caires:2024} on the \ac{SAM} and \ac{CLASS} interpreters. Then, the program is compiled to an intermediate representation (\ac{IR}) which abstracts some details of the target language. Next, the \ac{IR} is analyzed and optimized by a series of passes. Finally, the optimized \ac{IR} is translated to C code, which is then compiled to native code using the GNU Compiler Collection (GCC).

The \ac{IR} optimization phase is left for the next chapter, while this chapter focuses on presenting the base \ac{IR} and compilation scheme. This chapter is divided into five four. In the first section, the \ac{IR}'s constructs and its abstract machine are defined. In the second section, the compilation of \ac{CLASS} to the \ac{IR} is described. In the third section, an overview is given on how the \ac{IR} is translated to C code. Finally, in the fourth section, open problems and future work and listed.

\section{Intermediate Representation}

In this section, we introduce the intermediate representation (\ac{IR}) used by the compiler and its abstract machine. The \ac{IR} is an imperative stateful language meant to act as a bridge between the high-level session-based language \ac{CLASS} and the low-level imperative language C.

We start by describing the syntax and layout of \ac{IR} programs. Then, we define the data structures and other necessary concepts used by the abstract machine, as we go through the semantics of each \ac{IR} instruction.

A complete specification of the \ac{IR} can be found in \Cref{chapter:appendixIR}.

\subsection{Program Structure}

An \ac{IR} program is a set of named processes, each consisting of a header and a body. The header contains the number of end points of the process, the names of the type parameters, the names of the session parameters, the names of the data sections and their data layouts, and finally, the data to be dropped when the process finishes execution (see \Cref{fig:IRProcessExample} for an example).

\begin{figure}[H]
    \begin{lstlisting}[language=IR]
foo:
    end points: 1
    types: none
    sessions: s0
    data d0: <[]> (s0)
entry:
    printLine("close")
    finishSession(s0, end point)

main:
    end points: 2
    types: none
    sessions: s0
    data d0: <[]> (s0)
entry:
    initializeSession(s0, cut_lhs_0, d0)
    callProcess(foo, end point, s0 <- s0)
cut_lhs_0:
    printLine("wait")
    popTask(end point)
    \end{lstlisting}
    \caption{An example \ac{IR} program with two processes}
    \label{fig:IRProcessExample}
\end{figure}

\subsection{Environments}

Each process invocation creates an \textit{environment} which holds its dynamic state, similarly to a stack frame in a traditional function call. This state includes the number of remaining end points, the properties of any polymorphic types, the state of all sessions, the local data being used by the process and finally, a bitset indicating which data locations should be dropped when the process terminates.

All instructions in a process implicitly operate on its environment. When an instruction refers to a session or a data location, it is referring to the respective section in the current environment.

\subsection{Sessions}

\ac{IR} sessions are similar to both return addresses and coroutines. They are used to model the flow of control between two end points of a \ac{CLASS} channel.
A session is described by four properties: a reference to its opposite end point session (which might be itself), a data location to write to when sending data to it, and a continuation address and environment to switch to when passing control to it.

Sessions are stored in the environment of each process, and are referenced by their index in the environment's session section. For example, \texttt{s0} refers to the first session in the environment, \texttt{s1} to the second session, and so on. Additionally, references to sessions can be passed around as data through the \texttt{session} slot.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=IR]
entry:
    initializeSession(s0, rhs, d0) // 1
    continueSession(s0, cont)      // 2
rhs:
    finishSession(s0)              // 3
cont:
    ...                            // 4
    \end{lstlisting}
    \caption{Example flow control using sessions}
    \label{fig:IRSessionFlowControlSimple}
\end{figure}

Program flow through session is manipulated through three main instructions: \texttt{initializeSession}, \texttt{continueSession} and \texttt{finishSession}. An example flow of control through a session is shown in \Cref{fig:IRSessionFlowControlSimple}.

The \texttt{initializeSession(s0, rhs, d0)} instruction initializes the session \texttt{s0} in the current environment such that its remote counterpart (opposite end point) is itself, its writing data location is \texttt{d0} and its continuation is the block \texttt{rhs} on the current process.

Then, the \texttt{continueSession(s0)} instruction is executed, which jumps to the continuation of \texttt{s0} and replaces the continuation of \texttt{s0}'s remote session (itself in this case) with the block \texttt{cont} on the current process. This means that when \texttt{s0} is continued again, control will be passed to \texttt{cont}.

Finally, the \texttt{finishSession(s0)} instruction is executed, which passes control to the continuation of \texttt{s0}, which is \texttt{cont}. Additionally, it detaches \texttt{s0} from its remote session by setting its remote session reference to \texttt{NULL}. This instruction is similar to continue, but with the difference that flow of control won't ever return.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=IR]
entry:
    initializeSession(s0, lhs, d0) // 1
    initializeSession(s1, rhs, d1) // 2
    forwardSessions(s0, s1)        // 3
lhs:
    ...                            // 5
rhs:
    finishSession(s1)              // 4
    \end{lstlisting}
    \caption{Example flow control using session forwarding}
    \label{fig:IRSessionFlowControlForwarding}
\end{figure}

Additionally, the instruction \texttt{forwardSessions} is used to model forwarding of \ac{CLASS} channels. An example of its use is shown in \Cref{fig:IRSessionFlowControlForwarding}.

In this example two sessions \texttt{s0} and \texttt{s1} are initialized as before. Then, the \texttt{forwardSessions(s0, s1)} instruction is executed, which makes the remote session of \texttt{s0} be the remote session of \texttt{s1}, and vice-versa. After linking the sessions, the instruction jumps to the continuation of its second argument (\texttt{s1} in this case, and thus, the block \texttt{rhs}).

On the block \texttt{rhs}, the instruction \texttt{finishSession(s1)} is executed, which just like before passes control to the continuation of \texttt{s1}, which was set to \texttt{lhs} by the forwarding instruction.

\subsection{Data Storage}

All data in \ac{IR} programs (excluding meta data such as sessions and type information) is stored in one of two places: within a local data section on an environment, or within a cell. Local data sections are referenced by identifiers such as $d0$ and $d1$, similarly to sessions, while cells are referenced through cell slots (see \Cref{subsection:Cells}).

\subsubsection{Slots} \label{subsection:IRSlots}

\ac{IR} programs are completely platform agnostic, and thus, data types and addresses are described through their composition of \textit{slots}, instead of concrete byte sizes and offsets. A \textit{slot} is a unit of data in the \ac{IR}. There are many types of slots, from primitive types such as $\ints$ and $\strings$ to more domain-specific types such as $\sessions$ and $\exponentials$ (see \Cref{chapter:appendixIR} for a complete list).

In order to model branching data types (such as choices from \ac{CLASS}) and polymorphic data types, data layouts are described through trees of slots, instead of plain sequences. These trees branch on the choices taken or on the properties of polymorphic types (see \Cref{fig:IRSlotTreeExample} for some examples).

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=IR]
// Integer, followed by a boolean, followed by a string.
[int, bool, string]

// Integer, followed by a tag, followed by a boolean if the tag is 0,
// or by a string if the tag is 1.
[int, tag[[bool] | [string]]]

// If the polymorphic type t0 has the 'is value' flag set, then there
// are no slots. Otherwise, there's a session slot.
type<t0.isValue>[[] | [session]] 
    \end{lstlisting}
    \caption{Examples of slot trees}
    \label{fig:IRSlotTreeExample}
\end{figure}

Local data sections are described by their identifier and by a sum of slot trees describing the possible layouts of data that can be stored on them. For example, $data\ d0:\ \combst{\seqst{\ints; \bools} + \seqst{\strings}}$ describes a local data section $d0$ which can either store an integer followed by an $\ints$, or a $\strings$. Additionally, data sections may be associated to a session, indicating that a session passed to a process invocation should receive data from that data section (e.g., $data\ d0:\ \combst{\seqst{\ints}}\ (s0)$).

\subsubsection{Addressing Data} \label{subsection:DataAddressing}

A \textit{data location} is defined by a base address and an offset. The base address can be either a local data section (e.g., $d0$), remote data referenced by a session (e.g., $s0$), or a cell location (e.g., $c(d0)$). The offset is defined by two slot trees, written as $\offs{P}{F}$, $P$ describing the data being skipped (named \textit{past}), and $F$ describing the data that may come next (named \textit{future}). The future slot tree is necessary to determine the alignment of the data being accessed. For example, $\offs{\seqst{\ints; \bools}}{\seqst{\strings}}$ is an offset which skips an integer followed by a boolean, and expects a string to come next. When the past slot tree is empty, the future slot tree is unnecessary, and the offset is simply written as $0$. 

Locations are written as $\datal{B}{P}{F}$, where $B$ is the base address, and $\offs{P}{F}$ is the offset. For example, the location $\datal{d0}{\seqst{\ints}}{\seqst{\ints}}$ refers to the second integer stored in the local data section $d0$, while the location $\datal{s0}{\seqst{\bools}}{\seqst{\strings}}$ refers to a string stored in the remote data of the session $s0$, after a boolean. When the offset is zero, it is omitted for brevity. For example, $d0$ as a data location is equivalent to $\datal{d0}{\nilst}{\nilst}$ or just $d0.0$ - the future slot trees are unnecessary for empty past slot trees.

\subsection{Moving data}

Sometimes it is necessary to simply move data from one location to another. This is done through the \texttt{moveSlots} instruction, which takes as arguments a destination location, a source location and a slot tree describing the data to be moved. To exemplify, \texttt{moveSlots(s1, $\datal{d0}{\seqst{\bools}}{\seqst{\strings; \ints}}, \seqst{\strings, \ints}$)} moves a string followed by an integer from the local data section \texttt{d0} after a boolean to the start of the remote data section of session \texttt{s1}.

The \texttt{cloneSlots} instruction is used to clone data from one location to another, taking the same arguments. This instruction is only defined for cloneable slots, which are $\ints$, $\bools$, $\strings$, $\tags$ and $\exponentials$. In addition to copying the memory, it also increments reference counts for exponentials and allocates new strings as necessary. It used to model the exponential part of \ac{CLASS}.

\subsection{Dropping data} \label{subsection:IRDroppingData}

Although \ac{CLASS} is a linear language, it also supports both affine and exponential types. Thus, it is necessary to be able to drop some types of data if they are no longer needed. To this end, two instructions are provided: \texttt{dropSlots} and \texttt{deferDrop}.

The \texttt{dropSlots} instruction takes as arguments a data location and a slot tree, and immediately drops the passed data. This instruction is only defined for droppable slots, which are \texttt{string}, \texttt{session}, \texttt{cell} and \texttt{exponential}.

The \texttt{deferDrop} instruction takes as argument a drop bit identifier, and sets the respective bit. Drop bits are defined in the process header, and indicate a data location and a slot tree to be dropped when the process terminates, if their respective bit is set. Drop bit identifiers start with \texttt{e} followed by a number, such as \texttt{e0} and \texttt{e1}.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=IR]
main:
    data d0: <[string; string]>
    drop e0: [string] at d0.[string]~[string]
entry:
    ... // something that initializes both strings at d0
    deferDrop(e0) // the second string will be dropped later
    dropSlots(d0, [string]) // the first string is dropped now
    \end{lstlisting}
    \caption{Dropping data directly and through a drop bit}
\end{figure}

\subsection{Expressions}

Expressions are tree-like structure which compute basic values (\texttt{int}, \texttt{bool} or \texttt{string}) without side effects. Examples of expressions include arithmetic operations, comparisons, boolean operations, string concatenation and data access. A full specification of expressions can be found in \Cref{chapter:appendixIR}.

While expressions do not occur as instructions, they are used as arguments to some instructions, such as \texttt{writeExpression}, \texttt{branchExpression} and \texttt{print}.

An example of an expression is \texttt{(move(d0, int) + 3) + clone(d1, string)}. This expression reads an integer from \texttt{0}, adds \texttt{3} to it, then reads a cloned string from \texttt{d1} and finally concatenates the two. The \texttt{move} and \texttt{clone} expressions read data from the respective locations, with the difference that \texttt{move} consumes the data (cannot be read again) while \texttt{clone} leaves the data intact.

In the particular case of integers and booleans, both \texttt{move} and \texttt{clone} are equivalent, as these types are trivially copyable. For strings, however, the difference is important, as \texttt{clone} allocates a new string and copies the contents, while \texttt{move} simply uses the existing allocation.

\subsection{Input and output}

The \texttt{print} and \texttt{printLine} instructions are used to print values to the standard output. They take a single argument expression, which is evaluated and printed. The \texttt{printLine} instruction additionally appends a new line after printing the value.

The \texttt{writeScan} instruction is used to read values from the standard input. It takes as arguments a data location to store the read value to and a slot describing the type of data to be read.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=IR]
main:
    data d0: <[int; int]>
entry:
    writeScan(d0, int)
    writeScan(d0.[int]~[int], int)
    printLine(move(d0, int) + move(d0.[int]~[int], int))
    ...
    \end{lstlisting}
    \caption{Reading two integers from standard input and printing their sum}
\end{figure}

\subsection{Writing and binding sessions}

\begin{sloppypar}
References to sessions (\texttt{session} slots) can be written to and read from data locations using the \texttt{writeSession} and \texttt{bindSession} instructions, respectively. The first instruction takes a data location and a session identifier as arguments. The second takes a data location to read from, a session identifier to bind to, and a data location to set as the writing location of the session's remote end point.
\end{sloppypar}

An example of writing a session to local data and then binding it to another session is shown in \Cref{fig:IRSessionDataExample}. First, a session \texttt{s1} is initialized with its remote end point being itself, its writing location being \texttt{d1} and its continuation being the block \texttt{s1\_cont}. Then, a reference to the remote counterpart of session \texttt{s1} is written to the local data section \texttt{d0}. Next, the reference stored at \texttt{d0} is read and bound to the session \texttt{s2}, with its remote writing location being modified to \texttt{d2}. At this point, the remote session of \texttt{s2} is \texttt{s1}, and vice-versa. Finally, \texttt{s2} is continued, jumping to \texttt{s1\_cont}, and setting the continuation of \texttt{s1} to the current block. Thus, when executing \texttt{finishSession(s1)}, control will jump to \texttt{s2\_cont}.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=IR]
    initializeSession(s1, d1, s1_cont) // 1
    writeSession(d0, s1)               // 2
    bindSession(d0, s2, d2)            // 3
    continueSession(s2, s2_cont)       // 4
s1_cont:
    finishSession(s1)                  // 5
s2_cont:
    ...                                // 6
    \end{lstlisting}
    \caption{Writing a session to local data and binding it to another session}
    \label{fig:IRSessionDataExample}
\end{figure}

\subsection{Tags and branching} \label{subsection:Branching}

Branching is done through the \texttt{branchTag}, \texttt{branchExpression} and \texttt{branchTypeFlags} instructions. The first instruction branches on a tag stored a data location, similarly to a switch statement in C. The second instruction branches on the result a boolean expression, similarly to an if statement in C. Finally, the third instruction branches on whether a set of polymorphic types has a set of flag set.

Each possible branch is defined by a code location (block label) and an integer indicating how many end points are behind that branch. This is used to keep track of the number of remaining end points in the environment, and is explained in more detail in \Cref{subsection:EndPoints}.

Tags are written to data locations through the \texttt{writeTag} instruction, which takes as arguments a data location and a constant tag value.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=IR]
main:
    data d0: <tag[[int] | [string]]>
entry:
    writeTag(d0, 1)
    ...
    branchTag(d0, if_int:1, if_string:1)
if_int:
    ...
if_string:
    ...
    \end{lstlisting}
    \caption{Branching on a tag}
\end{figure}

\subsection{Tasks}

Tasks are a flow control mechanism completely separate from sessions, used to model the mix construct from \ac{CLASS}. For each thread of execution, there's a stack of tasks, where each task stores a continuation to be executed when the current task is finished.

Tasks can be pushed to the stack through the \texttt{pushTask} instruction, which takes a code location as argument. To finish the current task and jump to the continuation of the topmost task, the \texttt{popTask} instruction is used.

At the start of a thread, the task stack is initialized with a single task responsible for terminating the thread. Thus, the last instruction to be executed in a thread is always \texttt{popTask}.

\subsection{Jumps}

A simple jump to a constant code location is also possible through the \texttt{jump} instruction. This instruction is useful to merge control flow after branching, for example.

\subsection{Cells} \label{subsection:Cells}

Cells are used to model the shared state part of \ac{CLASS}. They're mutable memory locations which can be safely shared between multiple threads of execution. Cells are referenced through \texttt{cell} slots, and maintain a mutex to ensure safe concurrent access, as well as a reference count to guarantee proper deallocation.

A new cell can be created through the \texttt{writeCell} instruction, which takes as arguments a data location to write the \texttt{cell} slot to, and a slot tree describing the data that will be stored in the cell. The reference count of a cell can be incremented and decremented through the \texttt{acquireCell} and \texttt{releaseCell} instructions, respectively. Finally, the mutex of a cell can be locked and unlocked through the \texttt{lockCell} and \texttt{unlockCell} instructions, respectively.

The data stored in a cell can be accessed through any data location, by using a cell location as the base address, as explained in \Cref{subsection:DataAddressing}.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=IR]
main:
    data d0: <cell[int]>
entry:
    writeCell(d0, [int]) // create a cell with space for an integer
    lockCell(c(d0)) // lock the cell's mutex
    writeExpression(c(d0), 42) // write 42 to the cell
    unlockCell(c(d0)) // unlock the cell's mutex
    acquireCell(c(d0)) // increase reference count to 2
    releaseCell(c(d0)) // decrease reference count to 1
    releaseCell(c(d0)) // decrease reference count to 0, deallocating the cell
    \end{lstlisting}
    \caption{Creating and using a cell}
\end{figure}

\subsubsection{Cell Slot Arguments}

While other slots are represented solely by their type, \texttt{cell} slots come in two variants: one with a slot tree argument, and another without. The first variant is used to represent cells which store droppable data. The second variant is used to represent cells which store sessions.

The behavior differs only when a cell is deallocated, which happens when its reference count reaches zero. If the cell stores droppable data, the data is dropped according to the slot tree argument. If the cell stores sessions, the affine protocol is followed.

The affine protocol for sessions in cells is as follows. When a cell is to be deallocated, a tag with value $0$ is written to indicate the session will not be used, and control is passed to it with a continue instruction. Then, the session should finish, passing control back to the cell deallocator.

\subsection{Threads}

New threads of execution can be launched through the \texttt{launchThread} instruction, which takes as arguments a code location to start executing at and a list of data locations of locked cells to pass to the new thread. The new thread starts with a single task responsible for terminating it, and shares the same environment as the parent thread, but a separate task stack.

Accesses to the environment are not synchronized except for reference and end point counting, and it is the responsibility of the \ac{IR} generator to ensure different threads do not access the same data concurrently.

The list of locked cells is necessary to avoid undefined behavior on the generated C code, as explained further in \todo{reference the relevant C generation subsection here}. The list should contain all and only cells which are locked at the moment of launching the thread, and which will be owned and thus later unlocked by the new thread. 

\subsection{Polymorphism}

Processes in the \ac{IR} may be parametrized by polymorphic types. These types are identified by names which start with \texttt{t} followed by a number, such as \texttt{t0} and \texttt{t1}. Types may be used directly as slots in slot trees. Additionally, they may also be used in \texttt{branchTypeFlags} instructions, as mentioned in \Cref{subsection:Branching}.

Types can be written to data locations through the \texttt{writeType} instruction, producing a \texttt{type} slot. This slot can then be read by a process invocation instruction, such as \texttt{callProcess}. The \texttt{writeType} instructions takes as arguments a data location to write to, a slot tree describing the type's layout, and a set of types which must have the 'is value' flag set for the type to also have it set.

For example, \texttt{writeType(d0, [int; t1], value=if(t1))} writes a type to \texttt{d0} which stores first an integer, and then data of type \texttt{t1}, which is a polymorphic type in the current environment. Additionally, the written type will have the 'is value' flag set if and only if \texttt{t1} also has it set.

\subsection{Process calls}

Processes can be invoked through the \texttt{callProcess} instruction, which takes as arguments the name of the process to invoke (might be the same process), and a list of type, session and data arguments to initialize the new process environment.

A type argument is described by the target type identifier on the new process, and by either a data location containing a \texttt{type} slot, or by a slot tree and flags describing the type directly. For example, \texttt{t0 <- [int] (value=yes)} initializes the type parameter \texttt{t0} of the new process to be a type which stores an integer, and has the 'is value' flag set, while \texttt{t1 <- d3.[int]~[type]} initializes \texttt{t1} to the type stored at \texttt{d3} after an integer.

A session argument is described by the target session identifier on the new process, by either a source session identifier or a data location containing a \texttt{session} slot, and finally, by a data offset to apply to the writing location of the session. For example, \texttt{s0 <- s1+[int]~[int]} initializes the session parameter \texttt{s0} of the new process to be the same as session \texttt{s1} of the current process, but with its writing location pointing at $\datal{s1}{\seqst{\ints}}{\seqst{\ints}}$. If the offset is zero, it is omitted for brevity.

Finally, a data argument is described by the target data identifier on the new process, by a source data location, by a slot tree describing the data, and by a flag indicating whether to clone the data or not. For example, \texttt{d0 =[string] d1} writes to \texttt{d0} a clone of the string stored at \texttt{d1}, while \texttt{d1 <-[string] d2} moves to \texttt{d1} the string stored at \texttt{d2} without cloning it.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=IR]
foo:
    types: t0
    sessions: s0
    data d0: <[t0]>
entry:
    moveSlots(s0, d0, [t0]) // 4
    finishSession(s0)       // 5

main:
    sessions: s0
    data d0: <[int]>
entry:
    initializeSession(s0, d0, rhs)                                     // 1
    writeExpression(s0, 42)                                            // 2
    callProcess(foo, t0 <- [int] (value=yes), s0 <- s0, d0 <-[int] d0) // 3
rhs:
    printLine(move(d0, int)) // 6
    ...
    \end{lstlisting}
    \caption{Calling a process with type, session and data arguments}
    \label{fig:IRProcessCallExample}
\end{figure}

An example of calling a process with type, session and data arguments is shown in \Cref{fig:IRProcessCallExample}. First, the session \texttt{s0} is initialized to have its remote end point be itself, its writing location be \texttt{d0} and its continuation be the block \texttt{rhs}. Then, the integer \texttt{42} is written to the remote data of \texttt{s0} (which is \texttt{d0}) Next, the process \texttt{foo} is called, with its type parameter \texttt{t0} being set to an integer with the 'is value' flag set, its session \texttt{s0} being set to the current session \texttt{s0}, and its data section \texttt{d0} being initialized by a move of the local data section \texttt{d0}. Inside \texttt{foo}, the integer stored at its local data section \texttt{d0} (received from \texttt{main}) is moved to the remote data of its session \texttt{s0} (which is still \texttt{d0} from the \texttt{main} process), and then, the session is finished, passing control back to the block \texttt{rhs} of the calling process. Finally, the integer stored at \texttt{d0} is printed.

\subsection{Exponentials}

Exponentials in \ac{CLASS} can be modeled through the \texttt{exponential} slot, which stores the necessary data to dynamically call a process closure, taking care of any captured data. Exponentials are created through the \texttt{writeExponential} instruction, which takes the same arguments as \texttt{callProcess}, with the exception that session arguments are not allowed, and that passed data must be cloneable. Additionally, the referenced process is expected to follow the exponential process convention.

The convention for exponential processes is simply that they must take a single session argument, \texttt{s0}, which will be used to communicate with the caller. This session is initialized by the caller when the \texttt{callExponential} instruction is called. This instruction takes as arguments a data location containing an \texttt{exponential} slot, a session identifier to bind the exponential process session to, and a data location to set as the writing location on the exponential process. See \Cref{fig:IRExponentialCallExample} for an example of creating and calling an exponential.

One important detail is that exponentials are reference counted data, and the \texttt{exponential} slot must be dropped when no longer needed, or at the end of the process, if it was not moved. This is done through the \texttt{dropSlots} or \texttt{deferDrop} instructions, as explained in the \Cref{subsection:IRDroppingData} section. Drops of exponentials decrement this reference count, and clones increment it.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=IR]
foo:
    types: t0
    sessions: s0
    data d0: <[t0]>
entry:
    moveSlots(s0, d0, [t0]) // 6, 10
    finishSession(s0)       // 7, 11

main:
    sessions: s0 s1
    data d0: <[string]>
    data d1: <[exponential]>
    data d2: <[string]>
    data d3: <[string]>
    drop e0: [exponential] at d1
entry:
    writeExpression(d0, "Hello, World!")                                    // 1
    writeExponential(d1, foo, t0 <- [string] (value=yes), d0 <-[string] d0) // 2
    deferDrop(e0)               // 3
    callExponential(d1, s0, d2) // 4
    callExponential(d1, s1, d3) // 4
    continueSession(s0, rhs0)   // 5
rhs0:
    printLine(move(d2, string)) // 8
    continueSession(s1, rhs1)   // 9
rhs1:
    printLine(move(d3, string)) // 12
    ...
    \end{lstlisting}
    \caption{Calling an exponential with type and data arguments}
    \label{fig:IRExponentialCallExample}
\end{figure}

In \Cref{fig:IRExponentialCallExample}, the process \texttt{foo} is a simple polymorphic process which takes a type parameter \texttt{t0}, a session \texttt{s0} and a data section \texttt{d0}. It moves data of type \texttt{t0} from its local data section \texttt{d0} to the remote data of its session \texttt{s0}, and then finishes the session, passing control back to the caller. When called as an exponential, \texttt{s0} will be initialized by the caller.

The \texttt{main} process first stores a new string at \texttt{d0}, and then creates a new exponential at \texttt{d1} for the process \texttt{foo}, moving the created string to it. This string will be cloned every time the exponential is called, and dropped when the exponential is freed. The exponential will be dropped at the end of the process through the drop bit \texttt{e0}, which is set by the \texttt{deferDrop(e0)} instruction.

The exponential is then called twice, first binding its session to \texttt{s0} and its writing location to \texttt{d2}, and then binding its session to \texttt{s1} and its writing location to \texttt{d3}. Each call will clone the string stored at \texttt{d0} and pass it to the exponential process. Control is not immediately passed to the exponential process. Instead, the caller only passes control to the exponential process when it continues either \texttt{s0} or \texttt{s1}. This is done through the \texttt{continueSession} instructions, which jump to the continuation of the respective session, which was set to the entry block of the exponential process by the \texttt{callExponential} instructions.

Finally, within the exponential process, the string is moved from the local data section \texttt{d0} to the remote data of the session \texttt{s0} (which is either \texttt{d2} or \texttt{d3} of the caller, depending on which call was continued), and then, the session is finished, passing control back to the caller. The caller then prints the received string.

\subsection{End points} \label{subsection:EndPoints}

One important aspect of the \ac{IR} which hasn't been explained yet is the concept of end points. These are used to ensure proper deallocation of the process environment when there's no more code left to execute within it. Each environment maintains a count of the number of remaining end points, which is specified in the process header (omitted in previous examples for brevity).

Each instruction which passes control to another block without a continuation might be marked as an end point. These instructions are \texttt{finishSession}, \texttt{forwardSessions}, \texttt{popTask} and \texttt{callProcess}. When such an instruction is executed, the environment's end point count is decremented. When it reaches zero, the environment is deallocated, and any remaining data is dropped according to the drop bits defined in the process header. A simple example of this mechanism is shown in \Cref{fig:IREndPointsExample1}.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=IR]
main:
    end points: 2
    sessions: s0
    data d0: <[]>
entry:
    initializeSession(s0, d0, rhs)
    finishSession(s0, end point) // end points decremented to 1
rhs:
    popTask(end point) // end points decremented to 0, environment is freed
    \end{lstlisting}
    \caption{Decrementing the end point count and deallocating the environment}
    \label{fig:IREndPointsExample1}
\end{figure}

The only other instructions which interact with the end point mechanism are the branching instructions, as mentioned in \Cref{subsection:Branching}. Each possible branch of a branching instruction is marked with the number of end points that will be behind that branch. When a given branch is taken, the environment's end point count is decremented by the difference between the maximum end point count across all branches and by end point count of the chosen branch. An example of this mechanism is shown in \Cref{fig:IREndPointsExample2}.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=IR]
foo:
    end points: 2
    data d0: <[int]>
entry:
    branchExpression(move(d0, int) > 0, if_true:2, if_false:1) // max = 2
if_true:
    ... // end points remains 2 (max - curr = 2 - 2 = 0)
if_false:
    ... // end points decremented by 1 (max - curr = 2 - 1 = 1)
    \end{lstlisting}
    \caption{Modifying the end point count through branching}
    \label{fig:IREndPointsExample2}
\end{figure}

\section{Generating IR programs from CLASS}

In this section formally define the base translation from \ac{CLASS} to the \ac{IR} we defined in the previous section. It starts by defining the concept of \textit{value}, \textit{droppable} and \textit{cloneable} session types. Then, it describes how session types are mapped to the slot trees introduced in \Cref{subsection:IRSlots}. Finally, the translation from \ac{CLASS} processes to \ac{IR} programs is incrementally defined, starting from simple processes and adding more constructs until we cover the whole language. Transformations applied to this scheme for optimization purposes are left to the next session.

\subsection{Value, droppable and cloneable types}

To manage the data of sessions in an efficient manner, we define three subsets of session types: value types $\valueset$, droppable types $\droppableset$ and cloneable types $\cloneableset$, such that $\cloneableset \subset \droppableset \subset \valueset$
. Thus all cloneable types are droppable, and all droppable types are value types.

A session type $A$ is a value type, $A \in \valueset$, if and only if it is strictly positive or strictly negative. This means that a session of a negative value type is finished (has no continuation), and is only used to received already written data, while a session of a positive value type will be finished after writing data to it, i.e., flow of control will never return to the process which wrote to it. This includes types such as $\recvt{A}{\waitt}$ and $\sendt{A}{\closet}$, but not $\recvt{A}{\closet}$ or $\sendt{A}{\waitt}$.

A session type $A$ is considered a \textit{droppable type}, $A \in \droppableset$, if and only if it is a value type, and if the data sent over it can be dropped, effectively making the type affine. This includes types such as $\closet$, $\lintt$, $\lstringt$, $\bangt{A}$, $\affinet{A}$ and, as long as $A, B \in \droppableset$, $\sendt{A}{B}$.

Finally, a session type $A$ is considered a \textit{cloneable type}, $A \in \cloneableset$, if and only if it is a droppable type, and if the data sent over it can be cloned. This includes types such as $\closet$, $\lintt$, $\lstringt$ and $\bangt{A}$, but not, for example, $\affinet{A}$.

We denote $\isvalue{P}{A}$ as whether $A \in \valueset$ and having polarity $P$ (positive $+$ or negative $-$) is $\impossible$, $\guaranteed$ or $\dependent{p_1,\,\dots,\,p_n}$ on whether all type flag requisites $p_i,\,\dots,\,p_n$ are met. A type flag requisite $p_i$ is defined as a test of whether a given polymorphic type variable $t_i$ belongs to either $\valueset$, $\droppableset$ or $\cloneableset$ (e.g, $t_2 \in \droppableset$ is a type flag requisite).


This function is defined below through pattern matching on session types. For brevity, we omit the definition of $\isvalue{-}{A}$, as it can be defined through duality: $\isvalue{-}{A} = \isvalue{+}{\dual A}$. Additionally, we omit the cases of $\isvalue{+}{A}$ where $A$ is a negative type, as they are all $\impossible$.

\begin{align*}
    &\isvalue{+}{\lintt A} &&= \guaranteed \\
    &\isvalue{+}{\lboolt A} &&= \guaranteed \\
    &\isvalue{+}{\lstringt A} &&= \guaranteed \\
    &\isvalue{+}{\closet{}} &&= \guaranteed \\
    &\isvalue{+}{\sendt{A}{B}} &&= \isvalue{+}{B} \\
    &\isvalue{+}{\sendtyt{X}{B}} &&= \guaranteed \\
    &\isvalue{+}{\bangt A} &&= \guaranteed \\
    &\isvalue{+}{\affinet A} &&= \isdroppable{+}{A} \\
    &\isvalue{+}{\statet A} &&= \guaranteed \\
    &\isvalue{+}{\statelt A} &&= \guaranteed \\
    &\isvalue{+}{\choicet{\labelt a A\ (\dots)\ \labelt z Z}} &&= \bigcup\,(\isvalue{+}{A},\,\dots,\,\isvalue{+}{Z}) \\
    &\isvalue{+}{X} &&= \dependent{t_x \in \valueset} \text{ where } X \text{ is identified by } t_x \\
\end{align*}

We start by defining this mapping for session types $A$ which are strictly positive or negative (i.e., value types, $A \in \valueset$). Let $\slots{A}$ be the slot tree corresponding to the data exchanged over a value type $A$. This function is defined through pattern matching on session types in \Cref{fig:SessionTypeToSlotTree}.

To exemplify, consider the session type $\sendt{\lintt}{\sendt{\closet}{\choicet{\labelt a \lstringt\ \labelt b \lboolt}}}$. Its slot tree is \texttt{[session; session; tag[[string] | [bool]]]}, as first a session is sent, then another session is sent, and finally, a tag is sent followed by either a string or a boolean, depending on the sent tag.

To extend this concept to non-value types, we must consider that session types may have multiple segments of data exchange, separated by changes in polarity. We can separate a session type into its segments by replacing every continuation of a different polarity with the unit type of that polarity ($\closet$ or $\waitt$) on the current segment and starting a new segment with the continuation.

For example, we can split $\sendt{\lintt}{\recvt{\lstringt}{\closet}}$ into three segments: first $\sendt{\lintt}{\closet}$, then $\recvt{\lstringt}{\waitt}$ and finally  $\closet$. Each segment is either strictly positive or strictly negative (a value), and thus, we can map each segment to a slot tree through the $\slots{A}$ function defined above.

The slot tree corresponding to the first segment of a session type $A$ is designated as its \textit{active slot tree}  (denoted simply by $\slots{A}$), and the slot trees corresponding to the remaining segments as its \textit{remainder slot trees}. Additionally, we denote positive segments as \textit{remote slot trees} and negative segments as \textit{local slot trees}, as positive segments correspond to data which is sent (and thus stored remotely), while negative segments correspond to data which is received (and thus stored locally). The local set of slot trees of a session type $A$ is denoted by $\alllocalslots{A}$, the remote set of slot trees by $\allremoteslots{A}$, and the total set of slot trees by $\allslots{A}$. 

\subsection{Environment}

This section introduces notation to represent the compilation state, which is referred to as the environment. An environment $\varepsilon$ is a tuple $(N, T)$ where $N$ is a mapping from channel names to channel states, and $T$ is a mapping from type variables to a tuple $(p, t)$ where $p$ is its polarity and $t$ its identifier within the process.

A channel state is a tuple $(s, d, o)$ where $s$ is the session identifier corresponding to the channel, $d$ is the local data section identifier corresponding to the channel, and $o$ is the data offset (as described in \Cref{subsection:DataAddressing}) to apply to the location of the next write or read operation on the channel.

$\varepsilon[x \mapsto (s, d, o)]$ is defined as the environment $\varepsilon$ where channel $x$ is mapped to the channel state $(s, d, o)$. Additionally $s(\varepsilon, x)$ denotes the session identifier of channel $x$ in the environment $\varepsilon$, $d(\varepsilon, x)$ the data section identifier of channel $x$ in the environment $\varepsilon$, and $o(\varepsilon, x)$ the data offset of channel $x$ in the environment $\varepsilon$.

To simplify data access, we additionally define $l(\varepsilon, x) = d(\varepsilon, x).o(\varepsilon, x)$, i.e., the local data location corresponding to channel $x$ in the environment $\varepsilon$, and $r(\varepsilon, x) = s(\varepsilon, x).o(\varepsilon, x)$, i.e., the remote data location corresponding to channel $x$ in the environment $\varepsilon$.

\subsection{Instruction generation}

The \ac{IR} instructions generated from a \ac{CLASS} process $P$ on a given environment $\varepsilon$ are denoted by $\getinstructions{P}{\varepsilon}$. This function produces a sequence of \ac{IR} instructions, optionally followed by blocks with more instructions, and will be defined incrementally in the following sections.

As instructions are generated, the process header is modified incrementally to include any new sessions, local data sections or drop bits which are necessary for the generated code to work.

In the subsections below, some important concepts used throughout the instruction generation rules are defined.

\subsubsection{Remainder type}

The remainder $r(\tau)$ of a type $\tau$ is defined as the type which is left after executing the next possible action on a session of type $\tau$. For example, $r(\sendt{A}{B}) = B$. The remainder is not defined for types without continuation, such as $\closet{}$ and $\waitt{}$

\subsubsection{Continue if negative}

To simplify the definition of the generation rules, a pseudo-instruction \texttt{continueIfNegative(x)} is defined, where $x$ is the channel name. This instruction is replaced by a \texttt{continueSession} instruction and a new block for its proceeding instructions if $r(\tau)$ is a negative type, where $\tau$ is the type of channel $x$.

This is used to achieve the same effect as the write-to-read adjustment of the \ac{SAM}, ensuring that whenever a read operation is performed, its writing counterpart must have already executed, and thus, written the data to the local data section we'll be reading from.

\subsubsection{Advancing a channel} \label{subsubsection:AdvancingChannel}

One other necessary operation is advancing the offset of the channel's state in the environment after a write or read operation. To perform this update, the function $\advancech{p}{\varepsilon}{x}{t}{A}$ is used, where $p$ is the current polarity of the type of $x$, $\varepsilon$ is the current environment, $x$ is the channel name, $t$ is the slot tree corresponding to the data to skip over in the offset and $A$ is the type of channel $x$ in the remaining process.

Additionally, whenever the polarity of $A$ is different from the polarity $p$, of the previous type of channel $x$, the offset must be reset to zero. This is done because whenever the polarity changes, a new segment of the session type starts. If the polarity was positive and became negative, then the process will start receiving data at the start of the local data section. If the polarity was negative and became positive, then the process will start writing data at the start of the remote data section.

This function produces a new environment $\varepsilon[x \mapsto (s, d, o)]$ where $s = s(\varepsilon, x)$, $d = d(\varepsilon, x)$ and, if $A$ has polarity $p$, $o = \slotoffset{$\concatst{\offsetpast{o(\varepsilon, x)}}{t}$}{$\slots{r(\tau)}$}$, otherwise, $o = 0$.

For example, $\advancech{+}{\varepsilon}{x}{\seqst{\sessions}}{\sendt{\lintt}{\lintt}}$ where $x$ previously had offset $\slotoffset{\seqst{\sessions}}{\seqst{\sessions; \ints}}$ will produce an environment where the offset of $x$ is $\slotoffset{\seqst{\sessions; \sessions}}{\ints}$.

Alternatively, $\advancech{+}{\varepsilon}{x}{\seqst{\ints}}{\colintt}$ where $x$ previously had offset $\slotoffset{\seqst{\ints}}{\nilst}$ will produce an environment where the offset of $x$ is $0$, as the polarity of $\colintt$ is negative, which is different from the previous polarity of $x$, which was positive.

\subsection{Expression generation}

Apart from generating instructions for processes, \ac{IR} expressions must be generated from \ac{CLASS} expressions when generating instructions for processes such as $\printp$, $\letp$ and $\ifp$. To achieve this, the function $\getexpression{E}{\varepsilon}$ is defined, which takes a \ac{CLASS} expression $E$ and an environment $\varepsilon$, and produces equivalent an \ac{IR} expression.

This function is defined through pattern matching on \ac{CLASS} expression, as shown below.

\begin{align*}
    &\getexpression{E_1 + E_2}{\varepsilon} = \getexpression{E_1}{\varepsilon} + \getexpression{E_2}{\varepsilon} & & |\ & & \getexpression{E_1 - E_2}{\varepsilon} = \getexpression{E_1}{\varepsilon} - \getexpression{E_2}{\varepsilon} \\
    &\getexpression{E_1 * E_2}{\varepsilon} = \getexpression{E_1}{\varepsilon} * \getexpression{E_2}{\varepsilon} & & |\ & & \getexpression{E_1 / E_2}{\varepsilon} = \getexpression{E_1}{\varepsilon} / \getexpression{E_2}{\varepsilon} \\
    &\getexpression{E_1 \% E_2}{\varepsilon} = \getexpression{E_1}{\varepsilon}\,\%\,\getexpression{E_2}{\varepsilon} & & |\ & & \getexpression{-E}{\varepsilon} = -\getexpression{E}{\varepsilon} \\
    &\getexpression{E_1\,\texttt{and}\,E_2}{\varepsilon} = \getexpression{E_1}{\varepsilon}\ \texttt{and}\ \getexpression{E_2}{\varepsilon} & & |\ & & \getexpression{E_1\,\texttt{or}\,E_2}{\varepsilon} = \getexpression{E_1}{\varepsilon}\ \texttt{or}\ \getexpression{E_2}{\varepsilon} \\
    &\getexpression{\texttt{not}\,E}{\varepsilon} = \texttt{not}\ \getexpression{E}{\varepsilon} & & |\ & & \getexpression{E_1 < E_2}{\varepsilon} = \getexpression{E_1}{\varepsilon} < \getexpression{E_2}{\varepsilon} \\
    &\getexpression{E_1 \leq E_2}{\varepsilon} = \getexpression{E_1}{\varepsilon} \leq \getexpression{E_2}{\varepsilon} & & |\ & & \getexpression{E_1 > E_2}{\varepsilon} = \getexpression{E_1}{\varepsilon} > \getexpression{E_2}{\varepsilon} \\
    &\getexpression{E_1 \geq E_2}{\varepsilon} = \getexpression{E_1}{\varepsilon} \geq \getexpression{E_2}{\varepsilon} & & |\ & & \getexpression{E_1 == E_2}{\varepsilon} = \getexpression{E_1}{\varepsilon} == \getexpression{E_2}{\varepsilon} \\
    &\getexpression{n}{\varepsilon} = n \text{ where } n \text{ is an integer literal} & & |\ & & \getexpression{b}{\varepsilon} = b \text{ where } b \text{ is a boolean literal} \\
    &\getexpression{s}{\varepsilon} = s \text{ where } s \text{ is a string literal} & & |\ & & \getexpression{x}{\varepsilon} = \texttt{move}(l(\varepsilon, x)) \text{ where } x \text{ is linear}\\
    &\getexpression{x}{\varepsilon} = \texttt{clone}(l(\varepsilon, x)) \text{ where } x \text{ is exponential}
\end{align*}

\subsection{End point counting}

One other important aspect of the compilation is counting the number of end points of the generated \ac{IR} code for a given \ac{CLASS} process. This is necessary to ensure that the generated code properly deallocates the process environment when there's no more code left to execute within it, as explained in \Cref{subsection:EndPoints}.

The number of end points in a process $P$ is denoted by $\getendpoints{P}{\varepsilon}$, which is defined by pattern matching on processes. It will be incrementally defined along with the instruction generation rules in the following sections.

\subsection{Process Definitions} \label{subsection:ProcessDefinitions}

A \ac{CLASS} program is a set of process definitions, each with a unique name. For each process definition, a set of resulting \ac{IR} processes is generated, one for each possible combination of polarities of its type parameters. This is necessary to ensure that the polarities of type parameters are always known at compile time, as they greatly affect the flow of control of the generated code.

For each resulting \ac{IR} process, an environment $\varepsilon = (N, T)$ is created. The mapping $N$ initially maps each argument channel name to a channel state $(s, d, 0)$, where $s$ and $d$ are respectively a unique session identifier and a unique data section identifier for the channel. Both $s$ and $d$ are added to the process header, $d$ being defined to have the layout $\alllocalslots{\tau}$, where $\tau$ is the type of the argument channel. This effectively reserves space for the data which will be received over the channel.

The mapping $T$ of the environment maps each type parameter name to a tuple $(p, t)$ such that $p$ is the polarity of the type parameter in the current combination, and $t$ is a unique identifier for the type parameter, which is also added to the process header.

Finally, we generate the instructions for the process body $P$ (starting by the entry block) through $\getinstructions{P}{\varepsilon}$, and set the number of end points of the process to $\getendpoints{P}{\varepsilon}$.

\subsection{Cut, Parallel and Empty}

We start by defining the compilation of a $\cutp$ process, which can be seen below. We assume, without loss of generality, that $A$ is a positive type, and thus, that $P$ will be writing to $x$ before $Q$ executes - if $A$ were negative, we could simply swap $P$ and $Q$. The number of end points of the generated code is the sum of the number of end points of both $P$ and $Q$.

First, a fresh session identifier $s$ is generated and added to the process header. Additionally, a data section with unique identifier $d$ is added to the header, with a layout given by $\allslots{A}$. In other words, $d$ reserves space for all data which will be both sent and received over the session of type $A$. This is necessary as both sides of the cut share the same data section.

The process initializes the session $s$ with a new block \texttt{rhs} as continuation, and $d$ as a writing location. Then, it recursively compiles both $P$ and $Q$ with a new environment where the name $x$ is bound to $(s, d, 0)$. $P$ is placed on the original block, and $Q$ placed on the new block \texttt{rhs}.

\begin{compilation}{\cutc{P}{x: A}{Q}}{\varepsilon}
{\getendpoints{P}{\varepsilon} + \getendpoints{Q}{\varepsilon}}
    \initsession{s}{\texttt{rhs}}{d}
    \recurse{P}{\varepsilon[x \mapsto (s, d, 0)]}
    \labelir{rhs}
    \recurse{Q}{\varepsilon[x \mapsto (s, d, 0)]}
\end{compilation}

The compilation of a $\parp$ process is shown below. The process starts by generating code to insert a new task for executing $Q$ into the task linked list. Then, it compiles $P$, which will be executed immediately. AS with the $\cutp$ process, the number of end points of the generated code is the sum of the number of end points of both $P$ and $Q$.

\begin{compilation}{\parc{P}{Q}}{\varepsilon}
{\getendpoints{P}{\varepsilon} + \getendpoints{Q}{\varepsilon}}
    \pushtask{rhs}
    \recurse{P}{\varepsilon}
    \labelir{rhs}
    \recurse{Q}{\varepsilon}
\end{compilation}

The $\emptyp$ process is compiled as shown below. The process marks the end of the current task, as it has no continuation. The flow of control is thus simply passed to the next task in the linked list. Additionally, we mark this instruction as an end point. 

\begin{compilation}{\emptyc}{\varepsilon}{1}
    \poptask{\hasendpoint}
\end{compilation}

\subsection{Close and Wait}

The compilation of a $\closep$ process can be seen below. The session identifier is fetched from the current environment $\varepsilon$. This action doesn't have a continuation, as the session is closed and no more operations can be performed on it. The flow of control is simply passed to the continuation of the session, and won't return. Additionally, since there's no continuation, the instruction is marked as an end point.

\begin{compilation}{\closec{x}}{\varepsilon}{1}
    \finishsession{s(\varepsilon, x)}{\hasendpoint}
\end{compilation}

The $\waitp$ process is skipped during compilation: $\getendpoints{\waitc{x}{P}}{\varepsilon} \equiv \getendpoints{P}{\varepsilon}$, $\getinstructions{\waitc{x}{P}}{\varepsilon} \equiv \getinstructions{P}{\varepsilon}$. There's no actual code generated for the wait action, as the action of waiting for the other side of the channel is already performed implicitly by the \ac{SAM} execution scheme, closely mirrored by the continue mechanism we defined earlier.

\subsection{Linear let, scan and print}

The compilation of a $\letp$ process is shown below. The compiler generates the \ac{IR} expression corresponding to the \ac{CLASS} expression $E$, and writes the result to the remote data of the channel $x$. Then, since this process has no continuation, the session is finished, similarly to the $\closep$ process.

\begin{compilation}{\letc{x}{E}}{\varepsilon}
{1}
    \writeexpr{r(\varepsilon, x)}{\getexpression{E}{\varepsilon}}
    \finishsession{s(\varepsilon, x)}{\hasendpoint}
\end{compilation}

The compilation of a $\scanp$ process is near identical except that instead of computing an expression, we use the \texttt{writeScan} instruction to read from the standard input.

\begin{compilation}{\scanc{x}}{\varepsilon}
{1}
    \writescan{r(\varepsilon, x)}{\slots{\tau}} \comment \text{where } x:\tau
    \finishsession{s(\varepsilon, x)}{\hasendpoint}
\end{compilation}

To compile the $\printp$ and $\printlnp$ processes, a single instruction is generated to print the result of the expression $E$ to the standard output. Then, the process continues by recursing on its continuation $P$.

\begin{figure}[H]
    \begin{minipage}{0.45\textwidth}
    \begin{compilationembed}{\printc{E}{P}}{\varepsilon}
    {\getendpoints{P}{\varepsilon}}
        \print{\getexpression{E}{\varepsilon}}
        \recurse{P}{\varepsilon}
    \end{compilationembed}
    \end{minipage}
    \hfill
    \begin{minipage}{0.45\textwidth}
    \begin{compilationembed}{\printlnc{E}{P}}{\varepsilon}
    {\getendpoints{P}{\varepsilon}}
        \printline{\getexpression{E}{\varepsilon}}
        \recurse{P}{\varepsilon}
    \end{compilationembed}
    \end{minipage}
\end{figure}

\subsection{Choice and branching}

The compilation of choice processes is shown below. Code is generated which writes a tag to the remote data of the channel $x$. We define $i(\#a)$ as the index of the tag \texttt{a} in the alphabetically sorted list of tags in the offer process. Then, the pseudo-instruction \texttt{continueIfNegative} is inserted, which adds a \texttt{continueSession} instruction if the remainder type of $x$ is negative. Finally, the process recurses on its continuation $P$, advancing the offset of channel $x$ to skip over the written tag, taking into account the remainder type of the channel, as explained in \Cref{subsubsection:AdvancingChannel}.

\begin{compilation}{\choosec{a}{x}{P}}{\varepsilon}{\getendpoints{\varepsilon}{P}}
    \writetag{r(\varepsilon, x)}{i(\#a)}
    \continueifneg{x}{A} \comment \text{where } x:A \text{ in }P
    \recurse{P}{\advancech{+}{\varepsilon}{x}{\seqst{\tags}}{A}}
\end{compilation}

The compilation of a $\casep$ process is shown below. The compiler generates code which reads a tag from the local data of channel $x$, jumps to the corresponding label and then recurses, generating code for each possible branch, preceded by the respective label. The labels are generated by their alphabetical order, so that their index matches the one written by the \texttt{writeTag} instruction. As before, the offset of channel $x$ is advanced to skip over the read tag. Here, the remainder type of $x$ depends on the chosen branch.

\begin{compilation}{\casec{x}{\labelc{a}{A},\,\dots,\,\labelc{z}{Z}}}{\varepsilon}{\max(\getendpoints{A}{\varepsilon},\,\dots,\,\getendpoints{Z}{\varepsilon})}
    \branchtag{l(\varepsilon, x)}{\texttt{a}:\getendpoints{A}{\varepsilon},\,\dots,\,\texttt{z}:\getendpoints{Z}{\varepsilon}}
    \labelir{a}
    \recurse{A}{\advancech{-}{\varepsilon}{x}{\seqst{\tags}}{\tau_A}} \comment \text{where } x:\tau_A \text{ in }A
    \beginir\dots
    \labelir{z}
    \recurse{Z}{\advancech{-}{\varepsilon}{x}{\seqst{\tags}}{\tau_Z}} \comment \text{where } x:\tau_Z \text{ in }Z
\end{compilation}


\subsection{Send and Receive}

The compilation of a $\sendp$ process is shown below. The process initializes a session $s$ with a new block \texttt{lhs} as continuation and the local data section $d$ as a writing location. $s$ and $d$ are added to the process header, similarly to the $\cutp$ process. In this case, however, $d$ has a layout given by $\alllocalslots{A}$, i.e., it only reserves space for received data. This is because, unlike the $\cutp$ process, only this end point of the session will be using this data section to read data.

The initialized session $s$ is then written the remote data of $x$, after which a \texttt{continueIfNegative} instruction is placed. This is necessary, as before, to implement the write-to-read adjustment of the \ac{SAM}. After this, the process recurses immediately on $Q$, advancing the offset of channel $x$ to skip over the sent data, as explained in \Cref{subsubsection:AdvancingChannel}.

Finally, on the new block \texttt{lhs}, the process recurses on $P$, with a new environment where $y$ is bound to the channel state $(s, d, 0)$. This block will only be executed when the reader of the session we just wrote passes control to it.

\begin{compilation}{\sendc{x}{y}{P}{Q}}{\varepsilon}
{\getendpoints{\varepsilon}{P} + \getendpoints{\varepsilon}{Q}}
    \initsession{s}{\texttt{lhs}}{d}
    \writesession{r(\varepsilon, x)}{s}
    \continueifneg{s(\varepsilon, x)}{A} \comment \text{where } x:A \text{ in }Q
    \recurse{Q}{\advancech{+}{\varepsilon}{x}{\seqst{\sessions}}{A}}
    \labelir{lhs}
    \recurse{P}{\varepsilon[y \mapsto (s, d, 0)]}
\end{compilation}

The $\recvp$ process is compiled as shown below. When executing this process, a session has already been written to the local data section associated to channel $x$. A session binding instruction is generated to bind this stored session into a fresh session identifier $s$, which is added to the process header, and a to a fresh local data section $d$, which is also added to the header, with layout $\alllocalslots{A}$, similarly to the $\sendp$ process.

The newly bound session must be continued if its type is negative, ensuring that the writing side of the session executes first. After this, the compilation recurses on $P$, with a new environment where $x$ has been advanced to skip over the received session, and $y$ is bound to the channel state $(s, d, 0)$.

\begin{compilation}{\recvc{x}{y: A}{P}}{\varepsilon}
{\getendpoints{\varepsilon}{P}}
    \bindsession{s}{l(\varepsilon, x)}{d}
    \continueifneg{s}{A} \comment \text{where } x:A \text{ in }P
    \recurse{P}{\advancech{-}{\varepsilon}{x}{\seqst{\sessions}}{A}[y \mapsto (s, d, 0)]}
\end{compilation}

\subsection{Forwarding}

Given a process $\fwdc{x}{y}$, it can be assumed without loss of generality that $x$ is of negative type and $y$ of positive type - if this is not the case, $x$ and $y$ can be swapped.

Forwarding requires us to move any data which has been received (but not consumed) through $x$ on its local data section to the remote data of $y$, which is positive. This data is known be composed of the slots given by $\slots{A}$, where $A$ is the type being forwarded. For example, if $A = \lintt$, then $\seqst{\ints}$ must be moved from the local data of $x$ to the remote data of $y$. This is the first operation performed by the forwarding process, as shown below.

\begin{compilation}{\fwdc{x}{y}}{\varepsilon}
{1}
    \moveslots{r(\varepsilon, y)}{l(\varepsilon, x)}{\slots{A}}
    \forwardsessions{s(\varepsilon, x)}{s(\varepsilon, y)}{\hasendpoint}
\end{compilation}

\subsection{Process Calls}

\subsection{Creating and calling exponentials}

The right-hand-side $P$ of a $\bangc{x}{y}{P}$ process is compiled as a separate \ac{IR} process, with a unique identifier generated from the identifier of the process definition being compiled. This new process inherits the same type variables as the current process. The argument session $y$ is bound to a new session identifier $s$ in the new process header, along with a new local data section $d$ with layout $\alllocalslots{A}$, where $A$ is the type of channel $y$. The number of end points of the new process' header is set to $\getendpoints{P}{\varepsilon}$.

All free names in $P$ which are not $y$ are exponentials (guaranteed by the typing rules of \ac{CLASS}), and should be passed to the new process as arguments. For each of them, a data section is created in the new process header, with layout $\alllocalslots{\whynott{\tau}}$, where $\tau$ is the type of the free name. The environment used to compile $P$ is also updated to bind these names to their respective data sections, with offset $0$.

On the original process, an exponential write instruction is generated referencing the new process identifier, along with all necessary type arguments (derived from the type parameters of the current process), and all data arguments for each of the free names in $P$. Finally, since the $\bangp$ process has no continuation, the session is finished, similarly to the $\closep$ process.

\begin{compilation}{\bangc{x}{y}{P}}{\varepsilon}
{1}
    \writeexp{r(\varepsilon, x)}{id}{T, D}
    \finishsession{s(\varepsilon, x)}{\hasendpoint}
\end{compilation}

The list of type arguments $T_1,\,\dots,\,T_n$ is generated similarly to the type arguments of a process call, but inheriting the same exact type parameters as the current process.

The list of data arguments $D_1,\,\dots,\,D_m$ is generated from the free names in $P$, excluding $y$. Each $D_i$ is a tuple $(d_t, d_s, t, c)$, where $d_t$ is the target data section identifier of the argument in the environment of the process being called, $d_s = l(\varepsilon, x_i)$ is the local data location of channel $x_i$ in $\varepsilon$, $t = \slots{\whynott{\tau}}$ is the slot tree corresponding to the type $\whynott{\tau}$, where $x_i: \tau$ and $c$ is the flag indicating whether the argument data should be cloned or moved, which in this case is always \texttt{clone}, as all free names in $P$ are exponentials.

\subsection{Unfolds}

Unfolded processes are compiled such that positive unfolds ($\unfoldmup$) always pass control to their continuation. If the remainder type is negative, i.e., the next action will read data from the channel, then we must pass control to the other side so that it can write the data before we read it. If the remainder type is positive, we cannot immediately continue as we must first give an opportunity for the other side to read any data we may have already written relative to the previous iteration of the unfold.

Negative unfolds ($\unfoldnup$) only pass control to their continuation if the remainder type is negative, as in this case, the positive side must have already executed a positive unfold, and thus, given control to the negative side. If the remainder type is negative, the positive side must execute first, and thus we surrender control back to it. If the remainder type is positive, we can continue executing immediately.

In both cases, the process finishes by recursing on the right-hand-side $P$ of the unfold, with a new environment where $x$ is bound to a new channel state equal to its previous state, but with offset $0$, as a new segment of the session type starts.

\section{Generating C code from IR programs}

In this section we describe the C programs the compiler generates from the \acf{IR}, which is produced by the code generation phase.

The intermediate representation used by the compiler is an imperative stateful language which closely resembles an assembly language for an abstract machine. An \ac{IR} program is a list of blocks of instructions, which may be labeled. Each block corresponds to a process definition in the source \ac{CLASS} program.

We start by showing the C type definitions for the data structures generated by the compiler. Then, we give an overview of our intermediate representation, and show how these \ac{IR} constructs are translated to C code.

\subsection{Data Types}

Below, we show the C type which describes an execution environment, which is responsible for binding session records to session indices. At any time during the execution of a program, there exists an active environment, where the records accessible to the current process are stored. The environment is a struct which contains an array of pointers to session records, with at most $255$ elements.
% and a pointer to the first exponential closure in the environment

% missing struct exponential* exponential;
\begin{lstlisting}[language=C]
struct environment {
    struct record* records[];
};
\end{lstlisting}

The session records, whose type is shown below, describe the current state of a session. The fields \texttt{cont}, \texttt{cont\_env} and \texttt{cont\_record} are used to implement the coroutining aspect of the execution. The \texttt{cont} field is a pointer which stores the program address to jump to when resuming the opposite end point of the session (when executing a flip). This address is obtained from a label, through the GCC extension for computed gotos. The \texttt{cont\_env} field stores a pointer to the environment to switch to when executing a flip, and the \texttt{cont\_record} field stores the index of the session record itself in the environment referenced by \texttt{cont\_env}. The purpose of these fields will be explained more clearly in the next subsections.

To store the data exchanged asynchronously between the two end points of the session, we keep a session buffer in the field \texttt{buffer}, which is a simple byte array. Its size is determined at allocation time, and is at most $255$ bytes. To track how many data has already been written and pending to read, we use the fields \texttt{written} and \texttt{read}, respectively. The \texttt{written} field keeps the count on how many bytes have been written to the buffer, and the \texttt{read} field keeps the count on how many bytes have been read from the buffer.

\begin{lstlisting}[language=C]
struct record {
    void* cont;
    struct environment* cont_env;
    unsigned char cont_record;
    unsigned char written, read;
    unsigned char buffer[];
};
\end{lstlisting}

Finally, we define a C type for tasks. Tasks store a continuation, i.e., a program address and an environment to switch to. These exist solely to implement the parallel construct of \ac{CLASS}, which corresponds to the mix rule of linear logic. Tasks form a linked list, where each task points to the next task to be executed.

struct task {

\end{lstlisting}

\subsection{Registers}

Translated \ac{IR} instructions operate on the registers shown below. The \texttt{env} register points to the current environment, on which operations are performed. The \texttt{task} registers point to the next task to be executed. The rest of the registers are used to store temporary values.

\begin{lstlisting}[language=C]
struct environment *env, *tmp_env;
struct task *task, *tmp_task;
struct record *tmp_record;
void *tmp_cont;
\end{lstlisting}

\subsection{Main function and labels}

The main function of the generated C program is shown below. It initializes the environment, allocates space for the session records, and then jumps to the entry process. For each process definition, a label of the form \texttt{proc\_X} is generated, where \texttt{X} is the name of the process. The code each for process definition is generated from its \ac{IR} instructions, immediately after the label.

\begin{lstlisting}[language=C]
int main() {
    /* The last task in the list of tasks finishes the program */
    task = malloc(sizeof(struct task));
    task->cont = &&end;

    /* Initializes the environment, where n is the number of session records
       necessary for the entry process */
    env = malloc(sizeof(struct environment) + /*n*/ * sizeof(struct record*));
    goto proc_entry;

    /* ... process definitions ... */

end:
    return 0;
}
\end{lstlisting}

Additionally, any labels in the \ac{IR} are directly translated to C labels, with extra care taken to ensure that each label is unique.


\subsection{Tasks}

There are two \ac{IR} instructions which manipulate the linked list of tasks. The \texttt{newTask} instruction, from which code is generated as shown below, allocates a new task, sets its continuation to a chosen label \texttt{cont}, and inserts it at the end of the linked list.

\begin{lstlisting}[language=C]
    /* newTask(cont) */
    tmp_task = malloc(sizeof(struct task));
    tmp_task->next = task;
    tmp_task->cont = &&cont;
    tmp_task->cont_env = env;
    task = tmp_task;
\end{lstlisting}

The \texttt{nextTask} instruction, whose generation is shown below, removes the first task from the linked list, changes the current environment and jumps to its continuation.

\begin{lstlisting}[language=C]
    /* nextTask() */
    tmp_task = task;
    task = task->next;
    env = tmp_task->cont_env;
    tmp_cont = tmp_task->cont;
    free(tmp_task);
    goto *tmp_cont;
\end{lstlisting}

\subsection{Session initialization and freeing}

Sessions are initialized with the \texttt{initSession} instruction. This instruction receives the index \texttt{record} of the session record in the current environment, the \texttt{size} of the session record buffer in bytes, and the initial continuation of the session, referenced by a label \texttt{cont}. The generated C code for this instruction is shown below.

\begin{lstlisting}[language=C]
    /* initSession(record, size, cont) */
    env->records[record] = malloc(sizeof(struct record) + size);
    env->records[record]->cont = &&cont;
    env->records[record]->cont_env = env;
    env->records[record]->cont_record = record;
    env->records[record]->written = 0;
    env->records[record]->read = 0;
\end{lstlisting}

Sessions are freed with the \texttt{freeSession} instruction. This instruction receives the index \texttt{record} of the session record in the current environment.

\begin{lstlisting}[language=C]
    /* freeSession(record) */
    free(env->records[record]);
\end{lstlisting}

\subsection{Session buffer manipulation}

To simplify write and read operations on session buffers, we define the \texttt{PUSH} and \texttt{POP} macros, shown below. These macros write and read to the buffer, respectively, and change the \texttt{written} and \texttt{read} fields of the session record accordingly.

\begin{lstlisting}[language=C]
#define READ(record) env->records[record]->read
#define WRITTEN(record) env->records[record]->written
#define BUFFER(record) env->records[record]->buffer

#define PUSH(record, type, value) \
    *((type*)&BUFFER(record)[WRITTEN(record) += sizeof(type)]) = value
#define POP(record, type) \
    *((type*)&BUFFER(record)[READ(record) += sizeof(type)])
\end{lstlisting}

The \texttt{pushClose} and \texttt{popClose} instructions both receive the index \texttt{record} of the session record in the current environment. Both instructions compile to nothing, as close tokens are zero-sized, and thus, nothing needs to be written or read from the session buffer. They're included only for debugging purposes.

The \texttt{pushTag} instruction receives the index \texttt{record} of the session record in the current environment, and a tag \texttt{tag} to be pushed to the session buffer. The generated C code for this instruction is shown below.

\begin{lstlisting}[language=C]
    /* pushTag(record, tag) */
    PUSH(record, unsigned char, tag);
\end{lstlisting}

Since tags are represented as \texttt{unsigned char}, we limit the maximum number of branches in choice and offer processes to $256$.

The \texttt{popTag} instruction receives the index \texttt{record} of the session record in the current environment, and a mapping \texttt{cases} from tags to labels.

\begin{lstlisting}[language=C]
    /* popTag(record, cases) */
    switch (POP(record, unsigned char)) {
        case /*tag*/: goto /*label*/; /* for each (tag, label) in cases */
    }
\end{lstlisting}

The \texttt{pushSession} instruction receives the indices \texttt{record} and \texttt{argRecord} of the session records in the current environment, and pushes a pointer to the session record \texttt{argRecord} to the buffer of the session record \texttt{record}. The generated C code for this instruction is shown below.

\begin{lstlisting}[language=C]
    /* pushSession(record, argRecord) */
    PUSH(record, struct record*, env->records[argRecord]);
\end{lstlisting}

The \texttt{popSession} instruction receives the indices \texttt{record} and \texttt{argRecord} of the session records in the current environment, pops a session record pointer from the buffer of the session record \texttt{record} and binds it to \texttt{argRecord} in the current environment.

\begin{lstlisting}[language=C]
    /* popSession(record, argRecord) */
    env->records[argRecord] = POP(record, struct record*);
\end{lstlisting}

\subsection{Flips}

We call the operation of switching the flow of control between two end points of a session a flip. Flips are generated by the \texttt{flip} instruction. This instruction receives the index \texttt{record} of the session record in the current environment, and swaps the current environment and program address with the session record's continuation environment and program address. Additionally, we update the \texttt{cont\_record} field of the record to store the index of the session record in the old environment, which is required by the \texttt{fwd} instruction, as we will see later. In the implementation, care is taken to ensure the continuation label \texttt{cont} is given a unique name for each flip.

Notice that we use the computed goto extension provided by GCC, which allows us to jump to a label stored in a variable. This is necessary to implement the flip operation, as the continuation label is kept in the session record.

\begin{lstlisting}[language=C]
    /* flip(record) */
    tmp_cont = env->records[record]->cont;
    tmp_env = env->records[record]->cont_env;
    env->records[record]->cont = &&cont;
    env->records[record]->cont_env = env;
    env->records[record]->cont_record = record;
    env = tmp_env;
    goto *tmp_cont;
cont:
\end{lstlisting}

\subsection{Forwarding}

The \texttt{fwd} instructions ties two session records in the current environment, \texttt{record1} and \texttt{record2}, together into a single session record, where the inactive end points of the two sessions become the two end points of the new session. Without loss of generality, we assume that \texttt{record1} corresponds to a session with a reading (negative) type, and \texttt{record2} corresponds to a session with a writing (positive) type - if the opposite is true, the caller can simply swap the arguments.

\texttt{fwd} generates code as shown below. Since \texttt{record1} has a negative type, the currently inactive end point of the session must have already written data to the buffer, which is pending to be read. Similarly, since \texttt{record2} has a positive type, the currently inactive end point of the session may have data which it still hasn't read from its buffer. Thus, the first block of code appends any pending data in the  buffer of \texttt{record1} to the buffer of \texttt{record2}. Then, the continuation of \texttt{record2} is set to point to the continuation of \texttt{record1}. At this point, the only thing that remains to be done is to change the binding which originally belonged to \texttt{record1} to point to the record \texttt{record1}, and then \texttt{record1} session is freed, as the \texttt{record2} session now holds all the data. Finally, the flow of control is passed to the old continuation of \texttt{record2}.

Note that this is the only instruction which makes use of the \texttt{cont\_record} field of the session record. Its only purpose is to allow the rebinding of a session record on a non-active end point's environment.

\begin{lstlisting}[language=C]
    /* fwd(record1, record2) */
    memcpy(/*dst=*/  BUFFER(record2) + WRITTEN(record2),
           /*src=*/  BUFFER(record1) + READ(record1),
           /*size=*/ WRITTEN(record1) - READ(record1));
    WRITTEN(record2) += WRITTEN(record1) - READ(record1);

    tmp_cont = env->records[record2]->cont;
    tmp_env = env->records[record2]->cont_env;
    env->records[record1]->cont = env->records[record1]->cont;
    env->records[record1]->cont_env = env->records[record1]->cont_env;
    env->records[record1]->cont_record = env->records[record1]->cont_record;

    tmp_record = env->records[record1];
    tmp_record->cont_env[tmp_record->cont_record] = record2;
    free(tmp_record);

    env = tmp_env;
    goto *tmp_cont;
\end{lstlisting}

\subsection{Process calls}

Process calls are performed through the \texttt{call} instruction. This instruction receives the label of the process to be called, the size of the environment to be created, and a mapping containing the indices of the session records to be passed as arguments. The generated C code for this instruction is shown below.

\begin{lstlisting}[language=C]
    /* call(proc, size, args) */
    tmp_env = malloc(sizeof(struct environment) + size * sizeof(struct record*));
    /* for each i in 0..#args */
    tmp_env->records[/*i*/] = env->records[args[/*i*/]];
    env = tmp_env;
    goto proc;
\end{lstlisting}

\section{Next Steps and Future Work}

\todo{Rewrite this section}

An implementation of the proposed solution, including some polymorphism functionality, recursion and exponentials, has already been developed, but still has to be profiled and optimized. In terms of language features, it still doesn't cover any of the shared state and reference cell constructs of \ac{CLASS}.

One challenge brought up by polymorphism is that we no longer know at compile time whether on a given code section a type variable is positive or negative, and thus, whether we should generate a flip or not when encountering it as a remainder type. We expect to solve this problem by keeping track of the polarity of type variables in the environment, and branching on it when necessary.

Memory management is currently very inefficient, as we allocate a new session record as sessions are created as needed and freed as they are closed, using the \texttt{malloc} and \texttt{free} functions provided by the C standard library. These functions are very slow, and we could improve performance by using a custom memory allocator, specially given that due to the linear nature of \ac{CLASS}, we have plenty of guarantees about the lifetime of session records. It would also be interesting to explore the possibility of reusing data by doing in-place updates on session buffers, instead of copying data around.

One other issue also related to memory management is the deallocation of environments. Currently, environments are never deallocated, which means that we have at least one memory leak for each process call. Once again, due to the linearity of \ac{CLASS}, it's possible that we may be able to determine statically when an environment is no longer needed, and deallocate it. The challenge lies in determining when an environment is no longer needed, as it may be shared between multiple sessions, and sessions may be passed around dynamically. This is a problem that will be tackled in the full implementation. We're expecting to solve the problem through type driven compilation, and thus avoid the need for garbage collection. This can be achieved by using a reference counting mechanism, where an environment's reference count is decremented each time one of its sessions is closed, and deallocated when the count reaches zero.

Adding support for native types such as integers and booleans is also something that will be addressed in the final implementation, as it will greatly increase the performance capabilities of the compiler.

Although this work focuses on generating sequential code, it should still be useful to make use of the natural parallelism of the \ac{CLASS} language. One possibly solution would be to distribute the tasks in the task list to multiple threads, through a thread pool, for example.

Finally, there are several other improvements and optimizations that could be made to the compiler that are not and won't be addressed in this work, but would be interesting to explore in the future. One such improvement would be to change the target language from C to LLVM IR, which is a low-level intermediate representation used by the LLVM compiler infrastructure. This would allow us to take advantage of the more advanced optimizations provided by the LLVM compiler.
