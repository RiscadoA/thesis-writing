\label{chap:optimizations}

This chapter describes the various optimizations implemented during this project. The first section goes over the transformations made to the compiler to produce more efficient code when handling \textit{value} types. The second section describes optimizations specific to the C code generation phase. Finally, the last section introduces a new compilation phase which applies a series of transformations to the generated \ac{IR} code before passing it to the C code generation phase.

\section{Handling value types more efficiently}

The compiler presented in \Cref{chap:architecture} does not take any advantage of the fact that many types in the language can be handled more efficiently than the general case. For example, the type $\sendt{\lintt}{\lintt}$ is stored as a pointer to a session (essentially a closure) followed by an integer, while it could be stored as just a pair of integers. This change would save both memory and time, as the pointer indirection would be removed, along with some unnecessary jumps.

This section describes the implemented optimizations which take advantage of properties such as these to generate more efficient code. In the first subsection, three type properties are defined, which determine which optimizations can be applied to them. Then, the second subsection describes the necessary compiler adaptations to obtain these properties. The last three subsections describe the optimizations applied to the multiplicative, exponential and affine types, respectively.

\subsection{Value, droppable and cloneable types}

In the optimizations described in this section, types are optimized based on whether they're \textit{value}, \textit{droppable} or \textit{cloneable} types. These properties are referred to as \textit{type flags}. Each type flag may either be $\guaranteed$ to hold, $\impossible$ to hold, or be dependent on whether some type variables have some type flags set, which is denoted as $\dependent{F_1,\,\dots,\,F_n}$, where each $F_i$ is either $\depisvalue{t_j}$, $\depisdroppable{t_j}$ or $\depiscloneable{t_j}$ (value, droppable and cloneable flags, respectively), and $t_j$ is a type variable. These requirements are referred to as \text{type flag requirements}. The union of two type flag requirements $R_1$ and $R_2$, denoted as $R_1 \land R_2$, is defined as follows:
$$
\begin{tabularx}{\linewidth}{*{3}{>{\centering\arraybackslash}X}}
    $R_1 \land R_2 = R_2 \land R_1$ & $R \land \impossible = \impossible$ & $\quad R \land \guaranteed = R$ \\
\end{tabularx}
$$
$$
\dependent{F_1,\,\dots,\,F_n} \land \dependent{G_1,\,\dots,\,G_m} = \dependent{F_1,\,\dots,\,F_n,\,G_1,\,\dots,\,G_m}
$$

Value types are types which have a strict polarity, being either strictly positive or strictly negative. A session of a negative value type is finished, i.e., flow control won't leave the process through the session (having no continuation), which means it is only used to read data. A session of a positive value type will be finished after writing the current segment, i.e., flow of control will never return to the current process, being only used to write data. The value type flag requisites of type $A$ are denoted as $\isvalue{A}$, where $\typeenv$ is the type environment introduced in \Cref{subsubsection:TypeEnvironments}, and their definition for positive types is shown in \Cref{fig:IsValueDefinition}. For negative types, $\isvalue{A} = \isvalue{\dualt A}$.


\begin{figure}[H]
    \centering
    \begin{align*}
        &\isvalue{\lintt} = \guaranteed && \isvalue{\lboolt} = \guaranteed \\
        &\isvalue{\lstringt} = \guaranteed && \isvalue{\closet{}} = \guaranteed \\
        &\isvalue{\sendt{A}{B}} = \isvalue{B} && \isvalue{\sendtyt{X}{B}} = \guaranteed \\
        &\isvalue{\bangt A} = \guaranteed && \isvalue{\affinet A} = \impossible \\
        &\isvalue{\statet A} = \guaranteed && \isvalue{\statelt A} = \guaranteed \\
        &\isvalue{\choicet{\labelt a A\ (\dots)\ \labelt z Z}} = \bigwedge\,(\isvalue{A},\,\dots,\,\isvalue{Z}) && \isvalue{X} = \dependent{\depisvalue{\typeidof{\typeenv}{X}}} \\
        &\isvalue{A} = \impossible \text{ if } \polarityof{\typeenv}{A} = - &&
    \end{align*}
    \caption{Definition of $\isvalue{A}$ for positive types}
    \label{fig:IsValueDefinition}
\end{figure}

Droppable types are types for which a drop function can be implemented, effectively making them affine. The droppable type flag requisites of type $A$ are denoted as $\isdroppable{A}$, and their definition for positive types is shown in \Cref{fig:IsDroppableDefinition}. For negative types, $\isdroppable{A} = \isdroppable{\dualt A}$.

\subsection{Adding type flags to the compiler}

For a type flag to be known even when polymorphism is activated, the value of flag (set or unset) must be stored on the type information on process environments. This is done by adding a new integer field to the \texttt{type} struct, which stores one bit for each of the type flags.

Additionally, all instructions which pass around type information must be extended to support these type flags. For example, \texttt{writeType} originally received only the type's slot tree as an argument. Now, it must also receive the flag requirements for each of the flags. To enable different memory representations for session types based on these flags, slot trees also need to be extended with a new node kind $\flagsst{R}{T_1}{T_2}$. This new node is similar to the $\tagst{\dots}$ node, but instead of branching on a written tag, it branches on whether some flag requirements $R$ are met - if $R$ is met, $T_1$ is chosen, otherwise, $T_2$ is chosen.

Finally, to allow generating code which depends on type flags, it is also necessary to add a new branching instruction \texttt{branchFlags}, with the exact same syntax as \texttt{branchExpression}, but instead of branching on a boolean expression, it branches on whether some flag requirements are met.

All of these newly introduced branches depend on flag requirements which are usually possible to determine as either $\guaranteed$ or $\impossible$ during compile time. Only when compiling polymorphic code must the final program performs these checks at runtime.

\subsection{Sending and receiving values} \label{subsection:SendValueOptimizations}

The first implemented optimization takes advantage of the fact that a session of a positive value type $A$ being sent (e.g., $\sendt{A}{B}$) is a session which will have control returned to it only once, and immediately when it is received. The total number of operations can be reduced by simply immediately writing the data of the value instead of writing a session which would write that data. For example, instead of $\sendt{\lintt}{\sendt{\lintt}{\lintt}}$ being represented as $\seqst{\sessions;\sessions;\ints}$, it can be represented as $\seqst{\ints;\ints;\ints}$.

First, the mapping from sessions types $A$ to their respective slot trees introduced in \Cref{fig:SessionTypeToSlotTree} is updated such that, if the left-hand-side $A$ type is a positive value type, the slots of the $A$ are computed, and concatenated with the slots of the right-hand-side $B$. Otherwise, as before, a $\sessions$ slot is simply added before the slots of $B$. Formally:
$$
    \slots{\theta}{\sendt{A}{B}} = \concatst{\flagsst{\isvalue{A}}{\slots{\theta}{A}}{\seqst{\sessions}}}{\slots{\theta}{B}}
$$

Then, the compilation of both $\sendp$ and $\recvp$ processes must be modified to reflect this new structure. A \texttt{branchFlags} instruction is generated which branches on whether the type of the argument session being sent or received is a positive or negative value, respectively. If it is not a value, the implementation is the same as before.

On the sending side, if the argument is a positive value type, the argument's session is initialized with a writing location set to the main session's writing location. Then, the send's argument code is immediately executed, writing the data to the main session, through the argument session. When it finishes, the right-hand-side of the send continues executing, writing data after the data that has just been written.

On the receiver side, instead of receiving a new session, the data is simply moved from the main session using \texttt{moveSlots} into the local data associated with the argument's name. The right-hand-side continues executing, reading data after the data that was just moved.

\subsection{Exponential values} \label{subsection:ExponentialValueOptimizations}

The second implemented optimization greatly simplifies the representation of exponential types when their inner type is a cloneable value type. Instead of representing $\bangt{A}$ as an $\exponentials$ slot, the value can simply be computed immediately and stored directly. Without this optimization, for example, storing the result of a complex computation as an exponential would require re-executing the entire computation every time the exponential is called. With this optimization, the computation is executed only once, and then the result is cloned whenever a call is made. When the exponential is dropped, the resulting value is simply dropped.

Once again, the mapping from session types to slot trees is modified. If the inner type $A$ of a $\bangt{A}$ type is a cloneable and droppable type, the slots of $A$ are computed and used directly. Otherwise, a single $\exponentials$ slot is used, as before. Formally:
$$
    \slots{\theta}{\bangt{A}} = \flagsst{\iscloneable{A} \land \isdroppable{A}}{\slots{\theta}{A}}{\seqst{\exponentials}}
$$

This change turns, for example, the representation of $\bangt{\bangt{\lintt}}$ into just $\ints$, instead of an $\exponentials$ which would produce another $\exponentials$ which would finally produce an $\ints$.

The $\bangc{x}{y}{P}$ process, just like the $\sendp$ and $\recvp$ processes, is modified to generate a \texttt{branchFlags} instruction which branches on whether the inner type $A$ is a cloneable and droppable type. If it is not, the implementation is the same as before. Otherwise, the inner process $P$ is executed immediately, with the name $y$ bound as an alias of $x$, leading to the data being written directly where the exponential would be stored.

On the $\whynotc{x}{P}$ process, nothing changes. The drop of the slots corresponding to the exponential are deferred, as before. Previously these slots would always be a single $\exponentials$ slot, but now they might be the slots of the inner type $A$, if $A$ is a cloneable and droppable type.

Finally, the $\callc{x}{y}$ process is modified to simply generate a \texttt{cloneSlots} instruction whenever the inner type $A$ is a cloneable and droppable type, instead of generating a \texttt{callExponential} instruction.
