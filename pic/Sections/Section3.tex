\subsection{IR to C}

In this section we describe the C programs generated by the compiler, from the intermediate representation (IR) produced by the code generation phase.

The intermediate representation (IR) used by the compiler is an imperative stateful language which closely resembles an assembly language. An IR program is a list of blocks of instructions, which may be labeled. Each block corresponds to a process definition in the source CLASS program.

We start by showing the C type definitions for the data structures generated by the compiler. Then, we give an overview of our intermediate representation (IR), and show how these IR constructs are translated to C code.

\subsubsection{Data Types}

In Figure \ref{fig:RecordType} we show the C type which describes a session record. The fields \texttt{cont}, \texttt{cont\_env} and \texttt{cont\_record} are used on \textit{flips}, i.e., when resuming the opposite end point of a session. Respectively, they store the program address to jump to, the environment to switch to, and the index of the session record on the opposite end point.

The fields \texttt{written} and \texttt{read} are used to keep track of how many bytes have been written and read from the buffer.

Finally, the \texttt{buffer} field is an array of bytes which stores the data exchanged between the two end points of the session. Its size is determined at allocation time, and is at most $255$ bytes.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]
struct record {
    void* cont;
    struct environment* cont_env;
    unsigned char cont_record;
    unsigned char written, read;
    unsigned char buffer[];
};
    \end{lstlisting}
    \caption{C type describing a session record}
    \label{fig:RecordType}
\end{figure}

Figure \ref{fig:EnvironmentType} shows the C type which describes an environment. It contains a pointer to the first exponential closure in the environment, and an array of pointers to session records, of at most $255$ elements.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]
struct environment {
    struct exponential* exponential;
    struct record* records[];
};
    \end{lstlisting}
    \caption{C type describing an environment}
    \label{fig:EnvironmentType}
\end{figure}

The exponential closures form a linked list, where each closure points to its parent closure, as shown in Figure \ref{fig:ExponentialType}. The \texttt{cont} field stores the program address to jump to, and the \texttt{size} field stores the size of the environment that should be created when the closure is instantiated.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]
struct exponential {
    struct exponential* parent;
    void* cont;
    int size;
};
    \end{lstlisting}
    \caption{C type describing an exponential closure}
    \label{fig:ExponentialType}
\end{figure}

Finally, we define a C type for tasks in Figure \ref{fig:TaskType}. Tasks store a program address and an environment to switch to. Additionally, they store a pointer to the next task in the linked list of tasks. These are used to implement the CLASS parallel construct sequentially.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]
struct task {
    struct task* next;
    void* cont;
    struct environment* cont_env;
};
    \end{lstlisting}
    \caption{C type describing a task}
    \label{fig:TaskType}
\end{figure}

\subsubsection{Registers}

Translated IR instructions operate on the registers shown in Figure \ref{fig:Registers}. The \texttt{env} register points to the current environment, on which operations are performed. The \texttt{task} registers point to the next task to be executed. The rest of the registers are used to store temporary values.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]
struct environment *env, *tmp_env;
struct task *task, *tmp_task;
struct record *tmp_record;
void *tmp_cont;
    \end{lstlisting}
    \caption{Registers used by the IR}
    \label{fig:Registers}
\end{figure}

\subsubsection{Main function}

The main function of the generated C program is shown in Figure \ref{fig:MainFunction}. It initializes the environment, allocates space for the session records, and then jumps to the entry process.

For each process definition, a label of the form \texttt{proc\_X} is generated, where \texttt{X} is the name of the process. The code each for process definition is generated from its IR instructions, immediately after the label.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]
int main() {
    /* The last task in the list of tasks finishes the program */
    task = malloc(sizeof(struct task));
    task->cont = &&end;

    /* Initializes the environment, where n is the number of session records
       necessary for the entry process */
    env = malloc(sizeof(struct environment) + /*n*/ * sizeof(struct record*));
    goto proc_entry;

    /* ... process definitions ... */

end:
    return 0;
}
    \end{lstlisting}
    \caption{Main function of the generated C program}
    \label{fig:MainFunction}
\end{figure}

\subsubsection{Labels}

All labels in the IR are translated directly to C labels, with extra care taken to ensure that each label is unique.

\subsubsection{Session buffer manipulation}

To simplify write and read operations on session buffers, we define the \texttt{PUSH} and \texttt{POP} macros, shown in Figure \ref{fig:PushPopMacros}. These macros write and read to the buffer, respectively, and change the \texttt{written} and \texttt{read} fields of the session record accordingly.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]
#define READ(record) env->records[record]->read
#define WRITTEN(record) env->records[record]->written
#define BUFFER(record) env->records[record]->buffer

#define PUSH(record, type, value) \
    *((type*)&BUFFER(record)[WRITTEN(record) += sizeof(type)]) = value
#define POP(record, type) \
    *((type*)&BUFFER(record)[READ(record) += sizeof(type)])
    \end{lstlisting}
    \caption{Macros for session buffer manipulation}
    \label{fig:PushPopMacros}
\end{figure}

\subsubsection{Tasks}

There are two IR instructions which manipulate the linked list of tasks. The \texttt{newTask} instruction, from which code is generated as shown in Figure \ref{fig:NewTaskIR}, allocates a new task, sets its continuation to a label \texttt{cont}, and inserts it at the end of the linked list.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]
    /* newTask(cont) */
    tmp_task = malloc(sizeof(struct task));
    tmp_task->next = task;
    tmp_task->cont = &&cont;
    tmp_task->cont_env = env;
    task = tmp_task;
    \end{lstlisting}
    \caption{IR construct for creating a new task}
    \label{fig:NewTaskIR}
\end{figure}

The \texttt{nextTask} instruction, whose generation is shown in Figure \ref{fig:NextTaskIR}, removes the first task from the linked list, changes the current environment and jumps to its continuation.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]
    /* nextTask() */
    tmp_task = task;
    task = task->next;
    env = tmp_task->cont_env;
    tmp_cont = tmp_task->cont;
    free(tmp_task);
    goto *tmp_cont;
    \end{lstlisting}
    \caption{IR construct for advancing to the next task}
    \label{fig:NextTaskIR}
\end{figure}

\subsubsection{Session initialization and freeing}

Sessions are initialized with the \texttt{initSession} instruction. This instruction receives the index \texttt{record} of the session record in the current environment, the \texttt{size} of the session record buffer in bytes, and the initial continuation of the session, referenced by a label \texttt{cont}. The generated C code for this instruction is shown in Figure \ref{fig:InitSessionIR}.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]
    /* initSession(record, size, cont) */
    env->records[record] = malloc(sizeof(struct record) + size);
    env->records[record]->cont = &&cont;
    env->records[record]->cont_env = env;
    env->records[record]->cont_record = record;
    env->records[record]->written = 0;
    env->records[record]->read = 0;
    \end{lstlisting}
    \caption{IR construct for initializing a session}
    \label{fig:InitSessionIR}
\end{figure}

Sessions are freed with the \texttt{freeSession} instruction. This instruction receives the index \texttt{record} of the session record in the current environment. The generated C code for this instruction is shown in Figure \ref{fig:FreeSessionIR}.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]
    /* freeSession(record) */
    free(env->records[record]);
    \end{lstlisting}
    \caption{IR construct for freeing a session}
    \label{fig:FreeSessionIR}
\end{figure}

\subsubsection{Flips}

Flips are generated by the \texttt{flip} instruction. This instruction receives the index \texttt{record} of the session record in the current environment. The generated C code for this instruction is shown in Figure \ref{fig:FlipIR}. This instruction swaps the current environment and program address with the session record's environment and continuation.

In the implementation, care is taken to ensure the continuation label \texttt{cont} is given a unique name for each flip.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]
    /* flip(record) */
    tmp_cont = env->records[record]->cont;
    tmp_env = env->records[record]->cont_env;
    env->records[record]->cont = &&cont;
    env->records[record]->cont_env = env;
    env->records[record]->cont_record = record;
    env = tmp_env;
    goto *tmp_cont;
cont:
    \end{lstlisting}
    \caption{IR construct for flipping a session}
    \label{fig:FlipIR}
\end{figure}

\subsubsection{Pushing and popping close tokens}

The \texttt{pushClose} and \texttt{popClose} instructions both receive the index \texttt{record} of the session record in the current environment.

Both instructions compile to nothing, as close tokens are zero-sized, and thus, nothing needs to be written or read from the session buffer. They're present only for debugging purposes.

\subsubsection{Pushing and popping tags}

The \texttt{pushTag} instruction receives the index \texttt{record} of the session record in the current environment, and a tag \texttt{tag} to be pushed to the session buffer. The generated C code for this instruction is shown in Figure \ref{fig:PushTagIR}.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]
    /* pushTag(record, tag) */
    PUSH(record, unsigned char, tag);
    \end{lstlisting}
    \caption{IR construct for pushing a tag}
    \label{fig:PushTagIR}
\end{figure}

Since tags are represented as \texttt{unsigned char}, we limit the maximum number of branches in choice and offer processes to $256$.

The \texttt{popTag} instruction receives the index \texttt{record} of the session record in the current environment, and a mapping \texttt{cases} from tags to labels. The generated C code for this instruction is shown in Figure \ref{fig:PopTagIR}.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]
    /* popTag(record, cases) */
    switch (POP(record, unsigned char)) {
        case /*tag*/: goto /*label*/; /* for each (tag, label) in cases */
    }
    \end{lstlisting}
    \caption{IR construct for popping a tag}
    \label{fig:PopTagIR}
\end{figure}

\subsubsection{Pushing and popping sessions}

The \texttt{pushSession} instruction receives the indices \texttt{record} and \texttt{argRecord} of the session records in the current environment, and pushes a pointer to the session record \texttt{argRecord} to the buffer of the session record \texttt{record}. The generated C code for this instruction is shown in Figure \ref{fig:PushSessionIR}.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]

The generated C code for this instruction is shown in Figure \ref{fig:PopSessionIR}.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]
    /* popSession(record, argRecord) */

\end{figure}

\subsubsection{Forwarding}

The \texttt{fwd*} instructions tie two session records in the current environment, \texttt{record1} and \texttt{record2}, together into a single session record, where the end points of the two sessions become the two end points of the new session. All of the variants assume \texttt{record1} corresponds to a session with a writing type, and \texttt{record2} corresponds to a session with a reading type.

There are four different instructions for forwarding, for different states of the session records. We consider a session to be in $\writemode$ mode if its buffer holds data which the continuation hasn't read yet, and in $\readmode$ mode if it holds data which the active end point hasn't read yet.

\begin{enumerate}
    \item \texttt{fwdWW}, for when both \texttt{record1} and \texttt{record2} are in $\writemode$ mode.
    \item \texttt{fwdRR}, for when both \texttt{record1} and \texttt{record2} are in $\readmode$ mode.
    \item \texttt{fwdWR} for when \texttt{record1} is in $\writemode$ mode and \texttt{record2} is in $\readmode$ mode.
    \item \texttt{fwdRW} for when \texttt{record1} is in $\readmode$ mode and \texttt{record2} is in $\writemode$ mode.
\end{enumerate}

\texttt{fwdWW} generates C code as seen in Figure \ref{fig:FwdWWIR}. The first block of code copies any unread data from the buffer of \texttt{record1} to the buffer of \texttt{record2}. Then, the continuation of \texttt{record2} is set to point to the continuation of \texttt{record1}. At this point, the \texttt{record1} session is freed, as the \texttt{record2} session now holds all the data. Finally, the flow of control is passed to the old continuation of \texttt{record2}.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]
    /* fwdWW(record1, record2) */
    memcpy(/*dst=*/  BUFFER(record2) + WRITTEN(record2),
           /*src=*/  BUFFER(record1) + READ(record1),
           /*size=*/ WRITTEN(record1) - READ(record1));
    WRITTEN(record2) += WRITTEN(record1) - READ(record1);

    tmp_cont = env->records[record2]->cont;
    tmp_env = env->records[record2]->cont_env;
    env->records[record2]->cont = env->records[record1]->cont;
    env->records[record2]->cont_env = env->records[record1]->cont_env;
    env->records[record2]->cont_record = env->records[record1]->cont_record;

    tmp_record = env->records[record1];
    tmp_record->cont_env[tmp_record->cont_record] = record2;
    free(tmp_record);

    env = tmp_env;
    goto *tmp_cont;
    \end{lstlisting}
    \caption{IR construct for forwarding from $\writemode$ to $\writemode$}
    \label{fig:FwdWWIR}
\end{figure}

\texttt{fwdWR} generates code in a similar way to \texttt{fwdWW}, as shown in Figure \ref{fig:FwdWRIR}. The difference is that no data needs to be copied from the buffer of \texttt{record1} to the buffer of \texttt{record2}. If \texttt{record1} is in $\readmode$ mode, and it is of positive type, then all of the data in its buffer has already been read.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]
    /* fwdWR(record1, record2) */
    tmp_cont = env->records[record2]->cont;
    tmp_env = env->records[record2]->cont_env;
    env->records[record2]->cont = env->records[record1]->cont;
    env->records[record2]->cont_env = env->records[record1]->cont_env;
    env->records[record2]->cont_record = env->records[record1]->cont_record;

    tmp_record = env->records[record1];
    tmp_record->cont_env[tmp_record->cont_record] = record2;
    free(tmp_record);

    env = tmp_env;
    goto *tmp_cont;
    \end{lstlisting}
    \caption{IR construct for forwarding from $\writemode$ to $\readmode$}
    \label{fig:FwdWRIR}
\end{figure}

\texttt{fwdRW} generates code as shown in Figure \ref{fig:FwdRWIR}. The first block, this time copies the data that hasn't been read from the buffer of \texttt{record2} to the buffer of \texttt{record1}. Then, the continuation of \texttt{record1} is set to point to the continuation of \texttt{record2}. At this point, the \texttt{record2} session is freed, as the \texttt{record1} session now holds all the data. Finally, the flow of control is passed to the old continuation of \texttt{record1}.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]
    /* fwdRW(record1, record2) */
    memcpy(/*dst=*/  BUFFER(record1) + WRITTEN(record1),
           /*src=*/  BUFFER(record2) + READ(record2),
           /*size=*/ WRITTEN(record2) - READ(record2));
    WRITTEN(record1) += WRITTEN(record2) - READ(record2);

    tmp_cont = env->records[record1]->cont;
    tmp_env = env->records[record1]->cont_env;
    env->records[record1]->cont = env->records[record2]->cont;
    env->records[record1]->cont_env = env->records[record2]->cont_env;
    env->records[record1]->cont_record = env->records[record2]->cont_record;

    tmp_record = env->records[record2];
    tmp_record->cont_env[tmp_record->cont_record] = record1;
    free(tmp_record);

    env = tmp_env;
    goto *tmp_cont;
    \end{lstlisting}
    \caption{IR construct for forwarding from $\readmode$ to $\writemode$}
    \label{fig:FwdRWIR}
\end{figure}

Finally, \texttt{fwdRR} generates code as shown in Figure \ref{fig:FwdRRIR}. In this case, no data needs to be copied around, and we simply replace the session record \texttt{record1} by \texttt{record2} in its continuation environment, and jump to the continuation of \texttt{record1}.

\begin{figure}[H]
    \centering
    \begin{lstlisting}[language=C]
    /* fwdRR(record1, record2) */
    tmp_cont = env->records[record1]->cont;
    tmp_env = env->records[record1]->cont_env;

    tmp_record = env->records[record1];
    tmp_record->cont_env[tmp_record->cont_record] = record2;
    free(tmp_record);

    env = tmp_env;
    goto *tmp_cont;
    \end{lstlisting}
    \caption{IR construct for forwarding from $\readmode$ to $\readmode$}
    \label{fig:FwdRRIR}
\end{figure}

\subsection{CLASS to IR}

In this section we describe the compilation process from a CLASS program to the intermediate representation (IR) we defined in the previous section.

\subsubsection{Buffer Size Calculation}

\todo{Optimize buffers to have the minimum size possible; E.g., $\sendt{A}{\recvt{A}{\sendt{A}{\closet{}}}}$ should have size $S$, not $3S$.}

We denote the size, in bytes, of the buffer necessary for the full execution of a session of type $A$, as $\sizeof A$. This size is computed through pattern matching on the session type, through the rules introduced below.

For an type, its size must be equal to its dual type, as any value written by one end point must be read by the other. Thus, we omit the dual types for simplicity.

$$
    \sizeof{\dual A} = \sizeof A
$$

The unit types, $\closet{}$ and $\waitt{}$, have size $0$, as they do not require any data to be exchanged. They're only there to signal the end of a session.

$$
    \sizeof{\closet{}} = 0
$$

The sum types, $\offert{\dots}$ and $\choicet{\dots}$ have size equal to the maximum size of their components, plus $1$ byte to store the tag of the chosen branch.

$$
    \sizeof{\offert{\labelt a A\ (\dots)\ \labelt z Z}} =
    1 + \max(\sizeof A,\ \dots, \sizeof Z)
$$

The multiplicative types, $\sendt{A}{B}$ and $\recvt{A}{B}$, have size equal to the size of $B$, plus $S$ bytes to store a pointer to the sent session record, where $S$ is the size of a pointer to a session record in the compilation target architecture.

$$
    \sizeof{\sendt A B} = S + \sizeof B
$$

The exponential types, $\bangt A$ and $\whynott A$, have size $E + C + 1$, where $E$ and $C$ are, respectively, the size of pointers to an environment and to a program address in the compilation target architecture.

$$
    \sizeof{\bangt A} = E + C + 1
$$

Finally, if the type is a recursive type, any occurrence of recursive variable $X$ has a size of $0$. When a recursive type is unfolded, the session buffer is reused its beginning, and thus, there's no need to allocate more space.

$$
    \sizeof{X} = 0
$$

\subsubsection{Environment}

First we introduce notation to represent the state of the compiler, which we refer to as the environment. An environment $(\varepsilon, \eta)$ is a pair, where $\varepsilon$ is a mapping from session names to their current modes $m$, and $\eta$ is the a mapping from session names to their session record indices.

We define $\varepsilon[x \mapsto m]$ to be the environment $\varepsilon$ where the mode of session $x$ is updated to $m$, and $\eta[x \mapsto n]$ to be the environment $\eta$ where the session record index of session $x$ is updated to $n$. Additionally, $\eta(x)$ denotes the session record index of $x$.

The mode of a session is either $\readmode$ or $\writemode$, and indicates whether the session was last read from, or written to, respectively.

We denote $\#\eta$ as the number of mappings in $\eta$.
The session record index mapping can be determined for a given process through the function $n(\eta, P)$. This function expands $\eta$ to include space for new bindings in $P$, and is defined by pattern matching on the process $P$.

For the $\cutp$ process, we reserve a new binding for $x$ in $\eta$.

$$
    n(\eta, \cutc{P}{x}{Q}) = n(n(\eta[x \mapsto \#\eta], P), Q)
$$

For the $\sendp$ process, we reserve a new binding for $y$ in $\eta$.

$$
    n(\eta, \sendc{x}{y}{P}{Q}) = n(n(\eta[y \mapsto \#\eta], P), Q)
$$

Similarly, we define $n$ for the $\recvp$ process.

$$
    n(\eta, \recvc{x}{y}{P}) = n(\eta[y \mapsto \#\eta], P)
$$

For the $\parp$ process, we simply join the mappings of the two processes.

$$
    n(\eta, \parc{P}{Q}) = n(n(\eta, P), Q)
$$

We do the same for all branches of $\casep$.

$$
    n(\eta, \casec{x}{\labelc{a}{A},\,\dots,\,\labelc{z}{Z}}) = n(n(\dots n(\eta, A), \dots), Z)
$$

For all other processes of the form $\alpha; P$, we simply recurse on $P$.

$$
    n(\eta, \alpha; P) = n(\eta, P)
$$

Finally, for processes $\emptyp$, $\closep$, $\fwdp$ and $\bangp$, we return just $\eta$:

$$
    n(\eta, \emptyc) = n(\eta, \closec{x}) = n(\eta, \fwdc{x}{y}) = n(\eta, \bangc{x}{y}{P}) = \eta
$$

Notice that the right-hand side of $\bangp$ isn't considered when computing $\eta$. This is due to $P$ operating on a completely separate environment.

\subsubsection{Compilation and Flips}

The compilation of a CLASS process $P$ to the IR on a given environment $\varepsilon$ is represented by $\compiled{P}_\varepsilon$. We define the concept of an action $\mathcal{A}$, as a process which performs some operation on a session's buffer.

Actions are typically processes of the form $\alpha; P$, with the exception of the $\closep$ action, which has no continuation $P$. We denote the subject $s(\mathcal{A})$ of an action $\mathcal{A}$ as the leftmost name occurrence in $\mathcal{A}$. For example, $s(\waitc{x}{P}) = x$.

The remainder $r(\tau)$ of a type $\tau$ is defined as the type which is left after executing the next possible action on a session of type $\tau$. For example, $r(\sendt{A}{B}) = B$. The remainder is not defined for types $\closet{}$ and $\waitt{}$.

Whenever an action $\mathcal{A}$ with subject $s$ of type $\tau$ is compiled, if $\tau$ is a positive type and $r(\tau)$ is a negative type, a flip is generated, as seen in Figure \ref{fig:ReadActionCompilation}.

% TODO: figure out notation for inserting a flip after the command but before the continuation

\begin{figure}[H]

    \begin{compilation}{\mathcal{A}}{\varepsilon}
        \flip{\varepsilon(s(\mathcal{A}))}

This ensures that, for a given session, the currently executing end point executes as many operations as possible without flipping to the other end point. Flips only occur when after writing data, a read operation is performed. In that scenario, the other end point still hasn't written that data, and thus, the session must be flipped to the other endpoint.

\subsubsection{Cut}

We start by defining the compilation of a $\cutp$ process, in Figure \ref{fig:CutCompilation}. We assume, without loss of generality, that $A$ is a positive type, and thus, that $P$ will be writing to $x$ before $Q$.

The process initializes a session record in the environment with a new label \texttt{rhs} as continuation, and then recursively compiles $P$ with the updated environment, with the session in $\writemode$ mode. Finally, it compiles $Q$ in an environment where the session is in $\readmode$ mode, in front of the label \texttt{rhs}.

\begin{figure}[H]
    \centering
    \begin{compilation}{\cutc{P}{x: A}{Q}}{\varepsilon,\eta}
        \initsession{\eta(x)}{\phi(A)}{\texttt{rhs}}
        \recurse{P}{\varepsilon[x \mapsto \writemode],\eta}
        \labelir{rhs}
        \recurse{Q}{\varepsilon[x \mapsto \readmode],\eta}
    \end{compilation}
    \caption{Compilation of a cut process}
    \label{fig:CutCompilation}
\end{figure}

By compiling $P$ with $x$ in $\writemode$ mode, we generate a flip to $Q$ only when data has already been written to the session buffer. Since data has already been written, $Q$ is compiled with $x$ in $\readmode$, making sure that a flip is only generated when reading after $Q$ has also already written data.

\subsubsection{Parallel and Empty}

The compilation of a $\parp$ process is shown in Figure \ref{fig:ParCompilation}. The process starts by generating code to insert a new task for executing $Q$ into the task linked list. Then, it compiles $P$, which will be executed immediately.

\begin{figure}[H]
    \centering
    \begin{compilation}{\parc{P}{Q}}{\varepsilon,\eta}
        \newtask{rhs}
        \recurse{P}{\varepsilon,\eta}
        \labelir{rhs}
        \recurse{Q}{\varepsilon,\eta}
    \end{compilation}
    \caption{Compilation of a parallel process}
    \label{fig:ParCompilation}
\end{figure}

The $\emptyp$ process is compiled as shown in Figure \ref{fig:EmptyCompilation}. The process marks the end of the current task, as it has no continuation. The flow of control is thus simply passed to the next task in the linked list.

\begin{figure}[H]
    \centering
    \begin{compilation}{\emptyc}{\varepsilon,\eta}
        \nexttask
    \end{compilation}
    \caption{Compilation of an empty process}
    \label{fig:EmptyCompilation}
\end{figure}

\subsubsection{Forwarding}

The $\fwdp$ process is compiled conditionally on the modes of its arguments. Here, we assume, without lose of generality, that $x$ is a session of positive type, and $y$ is a session of negative type. The various possible compilations are shown in Figure \ref{fig:ForwardCompilation}.

\begin{figure}[H]
    \centering
    \begin{compilation}{\fwdc{x}{y}}{\varepsilon[x\mapsto\writemode,y\mapsto\writemode],\eta}
        \fwdww{\eta(x)}{\eta(y)}
    \end{compilation}
    \begin{compilation}{\fwdc{x}{y}}{\varepsilon[x\mapsto\writemode,y\mapsto\readmode],\eta}
        \fwdwr{\eta(x)}{\eta(y)}
    \end{compilation}
    \begin{compilation}{\fwdc{x}{y}}{\varepsilon[x\mapsto\readmode,y\mapsto\writemode],\eta}
        \fwdrw{\eta(x)}{\eta(y)}
    \end{compilation}
    \begin{compilation}{\fwdc{x}{y}}{\varepsilon[x\mapsto\readmode,y\mapsto\readmode],\eta}
        \fwdrr{\eta(x)}{\eta(y)}
    \end{compilation}
    \caption{Compilation of a forward process}
    \label{fig:ForwardCompilation}
\end{figure}

\subsubsection{Close and Wait}

The compilation of a $\closep$ process is shown in Figure \ref{fig:CloseCompilation}. The process pushes a close token to the session buffer of record $\eta(x)$, and then flips back to the other end point of the session.

This action doesn't have a continuation, as the session is closed and no more writing operations can be performed on it. The flow of control is passed to the other end point of the session, and won't return.

\begin{figure}[H]
    \centering
    \begin{compilation}{\closec{x}}{\varepsilon,\eta}
        \pushclose{\eta(x)}
        \flip{\eta(x)}
    \end{compilation}
    \caption{Compilation of a close process}
    \label{fig:CloseCompilation}
\end{figure}

The $\waitp$ process is compiled as shown in Figure \ref{fig:WaitCompilation}. The close token is popped from the buffer of the session record $\eta(x)$, the session's resources are freed, and the continuation $P$ is compiled in the environment $\varepsilon$, where $x$ is no longer bound.

\begin{figure}[H]
    \centering
    \begin{compilation}{\waitc{x}{P}}{\varepsilon[x \mapsto \readmode],\eta}
        \popclose{\eta(x)}
        \freesession{\eta(x)}
        \recurse{P}{\varepsilon,\eta}
    \end{compilation}
    \caption{Compilation of a wait process}
    \label{fig:WaitCompilation}
\end{figure}

\subsubsection{Offer and Choice}

The compilation of a $\casep$ process is shown in Figure \ref{fig:OfferCompilation}. The compiler generates code which reads a tag from the session buffer of record $\eta(x)$ and jumps to the corresponding label, and then recurses, generating code for each possible branch, preceded by the respective label.

Additionally, we define $i(\#a)$ as the index of the tag \texttt{a} in the alphabetically sorted list of tags in the offer process.

\begin{figure}[H]
    \centering
    \begin{compilation}{\casec{x}{\labelc{a}{A},\,\dots,\,\labelc{z}{Z}}}{\varepsilon[x \mapsto \readmode],\eta}
        \poptag{\eta(x)}{\{(i(\#a),\texttt{a}),\,\dots,\,(i(\#z),\texttt{z})\}}
        \labelir{a}
        \recurse{A}{\varepsilon[x \mapsto \readmode],\eta}
        \beginir\dots
        \labelir{z}
        \recurse{Z}{\varepsilon[x \mapsto \readmode],\eta}
    \end{compilation}
    \caption{Compilation of an offer process}
    \label{fig:OfferCompilation}
\end{figure}

The compilation of choice processes is shown in Figure \ref{fig:ChoiceCompilation}. Code is generated which writes a tag to the session buffer of record $\eta(x)$ and then recurses for the continuation.

\begin{figure}[H]
    \centering
    \begin{compilation}{\choosec{a}{x}{P}}{\varepsilon,\eta}
        \pushtag{\eta(x)}{i(\#a)}
        \recurse{P}{\varepsilon[x \mapsto \writemode],\eta}
    \end{compilation}
    \caption{Compilation of a choice process}
    \label{fig:ChoiceCompilation}
\end{figure}

\subsubsection{Send and Receive}

The compilation of a $\sendp$ process is shown in Figure \ref{fig:SendCompilation}. The process initializes a session record with a new label \texttt{lhs} as continuation, and generates an instruction to push that new session record, $\eta(y)$, to the buffer of $\eta(x)$. Then, it compiles $Q$ with $x$ in $\writemode$ mode. Finally, it compiles $P$ with the $y$ in $\readmode$ mode, in front of the label \texttt{lhs}.

In $P$, $y$ is set to $\readmode$ mode as the flow will only jump to $P$ after data has been written to the buffer.

\begin{figure}[H]
    \centering
    \begin{compilation}{\sendc{x}{y:A}{P}{Q}}{\varepsilon,\eta}
        \initsession{\eta(y)}{\phi(A)}{\texttt{lhs}}
        \pushsession{\eta(x)}{\eta(y)}
        \recurse{Q}{\varepsilon[x \mapsto \writemode],\eta}
        \labelir{lhs}
        \recurse{P}{\varepsilon[y \mapsto \readmode],\eta}
    \end{compilation}
    \caption{Compilation of a send process}
    \label{fig:SendCompilation}
\end{figure}

The $\recvp$ process is compiled as shown in Figure \ref{fig:ReceiveCompilation}. The process generates code to pop a session record from the buffer of $\eta(x)$ and then simply recurses for the continuation $P$.

In $P$, $y$ is set to $\writemode$ mode, as the flow should only jump to the other endpoint immediately before a read operation is performed.

\begin{figure}[H]
    \centering
    \begin{compilation}{\recvc{x}{y}{P}}{\varepsilon,\eta}
        \popsession{\eta(x)}{\eta(y)}
        \recurse{P}{\varepsilon[x \mapsto \readmode, y \mapsto \writemode],\eta}
    \end{compilation}
    \caption{Compilation of a receive process}
    \label{fig:ReceiveCompilation}
\end{figure}

\subsubsection{Process Definitions and Calls}

The compilation of a process definition is shown in Figure \ref{fig:ProcessDefCompilation}. A label is generated for the process definition and code is generated for the process $P$ with environment $(\varepsilon,\eta)$. $\varepsilon$ contains only the bindings for each argument of the process definition, each one initialized in $\readmode$. $\eta$ is generated from $P$.

\begin{figure}[H]
    \centering
    \begin{compilation}{\procdefc{foo}{x_1:A_1,\,\dots,\,x_n:A_n}{P}}{\emptyset,\emptyset}
        \labelir{proc\_foo}
        \recurse{P}{\emptyset[x_1 \mapsto \readmode,\,\dots,\,x_n \mapsto \readmode],\,n(\emptyset, P)}
    \end{compilation}
    \caption{Compilation of a process definition}
    \label{fig:ProcessDefCompilation}
\end{figure}

To call a process from another process, code is generated which initializes an environment of size $\#n(\emptyset, P)$, where $P$ is the process definition being called, as seen in Figure \ref{fig:ProcessCallCompilation}. The passed arguments are bound to the corresponding session record indices in the new environment, and additionally, a flip is inserted for argument $x_i$ if it's type $A_i$ is a reading type and $x_i$ is in $\writemode$ mode in $\varepsilon$.

\begin{figure}[H]
    \centering
    \begin{compilation}{\proccallc{foo}{x_1,\,\dots,\,x_n}}{\varepsilon,\eta}
        \flip{\eta(x_1)} \note \text{only included if $x_1$ is in $\writemode$ mode in $\varepsilon$ and $A_1$ is a reading type}
        \beginir\dots
        \flip{\eta(x_n)} \note \text{only included if $x_n$ is in $\writemode$ mode in $\varepsilon$ and $A_n$ is a reading type}
        \call{\texttt{proc\_foo}}{n(\emptyset, P)}{\{0 \mapsto \eta(x_1),\,\dots,\, n-1 \mapsto \eta(x_n)\}}
    \end{compilation}
    \caption{Compilation of a process call}
    \label{fig:ProcessCallCompilation}
\end{figure}

\subsection{Future Work}

There are several improvements and optimizations that could be made to the compiler that are not and won't be addressed in this work, but would be interesting to explore in the future. One such improvement would be to change the target language from C to LLVM IR, which is a low-level intermediate representation used by the LLVM compiler infrastructure. This would allow us to take advantage of the more advanced optimizations provided by the LLVM compiler.
