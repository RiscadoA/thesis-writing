
\section{Background and Related Work}

In this section, the theoretical foundations of linear logic, process calculi and session types are introduced, and then the programming language CLASS \cite{Rocha:2021} and the abstract machine SAM \cite{Caires:2024}, on which this work was built on top of, are presented. Finally, some work following the same line of research or with the same goal but in different contexts is discussed.

\subsection{Linear Logic}

Introduced by Girard \cite{Girard:1987} in the 80s, linear logic is a logic where propositions are consumed exactly once, as opposed to classical logic where propositions can be used any number of times. This property makes linear a logic ideal for modeling resources on real-world systems, opening pathways for multiple optimizations, such as in-place updates in functional languages \cite{Hofmann:2000}. More importantly for this work, the propositions-as-types correspondence of linear logic has proven useful for modeling concurrent systems \cite{Caires:2010}.

Connectives of classic linear logic are divided into three groups: multiplicative, additive and exponential. Multiplicative connectives are $\otimes$ (tensor), $\parr$ (par), $1$ and $\bot$. Additive connectives are $\with$ (with), $\oplus$ (plus), $\top$ and $0$. Exponential connectives are $\oc$ (of course) and $\wn$ (why not).

Here we present a definition of linear logic as a sequent calculus \cite{Abramsky:1993}, where a sequent is a list of propositions separated by a comma, and a turnstile $\vdash$ separates the antecedent from the succedent. In linear logic, each connective has a dual connective (or involution), represented by $\dual{A}$, which is defined in Figure \ref{fig:LinearLogicDual}. As such, there's no need for propositions to be placed before the turnstile, as they can be replaced by their involution on the succedent.

\begin{figure}[H]
    \begin{minipage}{0.225\textwidth}
        \begin{align*}
            \dual{A \otimes B} & \equiv \dual{A} \parr \dual{B}   \\
            \dual{A \parr B}   & \equiv \dual{A} \otimes \dual{B}
        \end{align*}
    \end{minipage}
    \hfill
    \begin{minipage}{0.225\textwidth}
        \begin{align*}
            \dual{A \with B}  & \equiv \dual{A} \oplus \dual{B} \\
            \dual{A \oplus B} & \equiv \dual{A} \with \dual{B}
        \end{align*}
    \end{minipage}
    \hfill
    \begin{minipage}{0.225\textwidth}
        \begin{align*}
            \dual{1}    & \equiv \bot \\

    \end{minipage}

    \end{minipage}

\end{figure}

Proofs of sequents can be constructed through inference rules. In linear logic, weakening and contraction rules are not present, as they would allow for the duplication and discarding of resources. The only structural rule that is defined is the exchange rule, as the order of propositions isn't important in linear logic. We also define the initial and cut rules, in Figure \ref{fig:LinearLogicInitialCutRules}. The cut rule allows for the composition of two proofs, and the initial rule allows for the introduction of a proposition and its dual without any premises.

Multiplicative disjunction $\parr$ is the par product of two propositions and it is equivalent to the logical disjunction in classical logic. Since its inception, linear logic has been seen as a good candidate for modeling the foundations of concurrent stateful systems \cite{Wadler:1990}. In fact, through the works of Abramsky \cite{Abramsky:1993}, it has been found that classical linear logic can be interpreted computationally, and since then, this connection has been developed further by multiple authors \cite{Turner:1999}. To exemplify, the cut rule can be interpreted as the composition of two processes, the initial rule as the creation of processes, and the additive and multiplicative rules as communication between processes. We can also extend classical linear logic with a mix rule (Figure \ref{fig:LinearLogicMixRule}), which enables us to model parallel composition of processes.

    \label{fig:LinearLogicMixRule}
\end{figure}

There are many variations of linear logic. One particularly relevant to this project is dual intuitionistic linear logic (DILL) \cite{Barber:1996}, which separates the linear and intuitionistic parts of the contexts, such that a general sequent is of the form $\Gamma; \Delta \vdash A$, where $\Gamma$ is the intuitionistic part, $\Delta$ is the linear part, and $A$ is the succedent. In the intuitionistic part, propositions can be used any number of times, while in the linear part of the context, propositions are consumed exactly once. This distinction allows for a more faithful modeling of servers in concurrent systems.

\subsection{Process Calculus}

Process calculi are formal languages for modeling concurrent systems, where processes interact by sending and receiving messages. One of the most well-known process calculus is CCS (Calculus of Communicating Systems) \cite{Milner:1980}, which introduced the notion of parallel composition, restriction and communication.

In the 90s, Milner et al \cite{Milner:1992:1,Milner:1992:2} introduced $\pi$-calculus, a process calculus that allows for mobility of processes - channels, through which processes communicate, can themselves be sent and received. It unifies data with communication channels, treating them as first-class citizens. This allows for more complex communication patterns, where the topology of the network can change dynamically. $\pi$-calculus can be used to encode various computation paradigms, such as $\lambda$-calculus and Turing machines, and thus, is a universal model of computation.

Processes can be seen as a generalization of functions, where the input and output can be sent over a channel - a function call can be seen as sending the input over a channel, and then receiving the output over the same channel. Additionally, coroutine constructs and generator expressions common in modern languages such as Python can also be easily modeled as a process calculus, where calls to \textit{yield} statements can be seen as sending values over a channel. Channels in $\pi$-calculus can also be replicated, which makes it possible to model services that can be accessed by multiple clients, such as web servers.

In Figure \ref{fig:PiCalculusExample} we present a simple $\pi$-calculus example, where a channel $x$ is created, and two processes are composed in parallel. The first process sends a message over $x$ and then terminates. The second process receives a message $y$ over $x$, prints it, and then terminates.

    \centering

        (\nu x)\,(\, & \overline{x}\langle\texttt{"Hello World!"}\rangle.0 \\
        |\           & x(y).\texttt{print}(y).0\,)
    \end{align*}
    \caption{Simple $\pi$-calculus example}
    \label{fig:PiCalculusExample}
\end{figure}


\subsection{Session Types}

Session types, first introduced by Honda \cite{Honda:1993}, and expanded upon by Honda et al. \cite{Honda:1998}, are a type discipline for communication-based programming that ensures that the communication between two parties is well-typed. Essentially, session types are a type discipline for process calculi, such as $\pi$-calculus, where operations on channels must follow the protocol defined by the session type. While in typed $\lambda$-calculus types are associated with terms, which denote functions and values, session types are associated with channel names.

Operations on session types include sending and receiving, branching and selection and recursion. Session types have been used to model and verify communication protocols, enforcing their correctness. They have been implemented in various programming languages, either as a language feature, such as in Scribble \cite{Yoshida:2014} and Effpi \cite{Scalas:2019}, or as a library, such as in Rust \cite{Jespersen:2015} and Haskell \cite{Pucella:2008}.

More recently, a direct correspondence between session types and linear logic has established \cite{Caires:2010}, where session types can be interpreted as linear propositions, and vice-versa. The connectives of linear logic are enough to describe the communication patterns of finite sessions.

The multiplicative connectives of linear logic can be used to represent the sending and receiving of channels. For example, a session type $A \otimes B$ describes a channel that first sends a channel name of type $A$, and then behaves as a channel of type $B$. The dual of $A \otimes B$ is $\dual{A} \parr \dual{B}$, which describes a channel that first receives a channel name of type $\dual{A}$, and then behaves as a channel of type $\dual{B}$, matching the behavior that the other end point of the channel must follow. The additive connectives can be interpreted as offering and choice. A session type $A \with B$ describes a channel that offers a choice between the channel following type $A$ or type $B$. The dual of $A \with B$ is $\dual{A} \oplus \dual{B}$, which describes a channel that chooses between the channel following type $\dual{A}$ or type $\dual{B}$. Finally, the exponential connective $\oc A$ of linear logic can be interpreted as a session type whose channels may be shared and which serve channels of type $A$.

\subsection{CLASS}

CLASS (Classic Linear Logic with Affine Shared State) is an experimental language for session-based programs \cite{Rocha:2022, Rocha:2021}. It expands on the correspondence between session types and linear logic, adding affine types, reference cells and shared state. In CLASS, well-typed programs are guaranteed to never deadlock on communication or reference cell acquisition, and to not leak any memory. Additionally, programs always terminate, while still allowing for higher-order polymorphic functional code and even recursion.

\subsubsection{\texorpdfstring{$\mu$}{mu}CLL}

We start by presenting the pure fragment of CLASS, dubbed $\mu$CLL. As the name suggests, $\mu$CLL is related, via a propositions-as-types correspondence \cite{Caires:2016}, to classical linear logic, extended with mix and inductive/coinductive types.

As usual in session-typed based programming languages, in $\mu$CLL processes communicate through sessions $x, y, z, \ldots$. Each session has two end points (also referred to as channels), and each end point is associated with a session type, which describes the communication protocol that the end point must follow. We write $x: A$ to denote that the session end point $x$ obeys type $A$. These types describe the direction, order and content of the messages exchanged. For example

$$
    x : \dual{\text{Nat}} \otimes \text{Bool} \otimes \mathbf{1}
$$

describes a session $x$ that must first receive a natural number, then send a boolean, and finally close, after which no more messages can be exchanged. The dual connective $\dual{A}$ is used to represent the dual of a type $A$, and is used to describe the type of the other end point of the session. The dual of the type before, for example, is

$$
    x : \text{Nat} \parr \dual{\text{Bool}} \parr \bot
$$

which describes a session $x$ that must first send a natural number, then receive a boolean, and finally wait for the other end point to close.

Additionally, session types can be seen as dynamic entities which evolve as the communication progresses. For example, after sending a natural number, the session type of the end point $x$ in the previous example would become

$$
    x : \dual{\text{Bool}} \parr \bot
$$

The most fundamental process composition operation in $\mu$CLL is the $\cutp$ operator

$$
    \cutc{P}{x: A}{Q}
$$

which composes two processes $P$ and $Q$ that run concurrently and communicate through a session $x$, where the end point $x$ in $Q$ obeys type $A$, and the end point $x$ in $P$ obeys type $\dual{A}$. This composition corresponds to the cut rule of linear logic, i.e., no session other than $x$ appears simultaneously in both $P$ and $Q$. It thus restricts interactions between $P$ and $Q$ to the session $x$, which is essential to achieve desirable metatheoretical properties such as deadlock freedom.

One other way of composing processes is through the $\parp$ construct, which allows for parallel composition of processes. The process

$$
    \parc{P}{Q}
$$

runs $P$ and $Q$ concurrently, without any communication between them. This composition corresponds to the mix rule of linear logic, i.e., no session appears simultaneously in both $P$ and $Q$. Additionally, there's the $\fwdp$ construct, which allows forwarding messages between sessions, acting as a bridge between two sessions. For example

$$
    \fwdc{x}{y}
$$

redirects messages sent to $x$ to $y$, and vice-versa, where $x$ and $y$ are session end points with dual types.

\subsubsection{Type System}

The types of $\mu$CLL are defined by the following BNF grammar:

\begin{align*}
    A, B ::=\  & X \text{ (type variable)}    &  & |\ \dual{X} \text{ (dual type variable)} \\
    |\         & \mathbf{1} \text{ (one)}     &  & |\ \bot \text{ (bottom)}                 \\
    |\         & A \otimes B \text{ (tensor)} &  & |\ A \parr B \text{ (par)}               \\
    |\         & A \with B \text{ (with)}     &  & |\ A \oplus B \text{ (plus)}             \\
    |\         & \oc A \text{ (of course)}    &  & |\ \wn A \text{ (why not)}               \\
    |\         & \exists X.A \text{ (exists)} &  & |\ \forall X.A \text{ (forall)}          \\
    |\         & \mu X.A \text{ (mu)}         &  & |\ \nu X.A \text{ (nu)}
\end{align*}

Types are formed from type variables ($X$, $Y$, ...), units ($\mathbf{1}$ and $\bot$), multiplicatives ($\otimes$ and $\parr$), additives ($\with$ and $\oplus$), exponentials ($\oc$ and $\wn$), existential and universal second-order type quantifiers ($\exists$ and $\forall$), and inductive types ($\mu$ and $\nu$). Types $\exists X.A$, $\forall X.A$, $\mu X.A$ and $\nu X.A$ all bind type variables $X$ in their bodies $A$. Additionally, types are equipped with a duality operator $\dual{A}$ corresponding to linear logic negation and which captures the symmetry behavior in interaction. The duality operator is defined as follows:

\begin{align*}
    \dual{\mathbf{1}} \equiv \bot    &  & \dual{A \otimes B} \equiv \dual{A} \parr \dual{B} &  & \dual{A \oplus B} \equiv \dual{A} \with \dual{B} \\
    \dual{\oc A} \equiv \wn \dual{A} &  & \dual{\exists X.A} \equiv \forall X.\dual{A}      &  & \dual{\mu X.A} \equiv \nu X.\dual{A}
\end{align*}

We now define typing contexts: a typing context is a finite partial assignment from names to types, denoted by

$$
    \underbrace{x_1 : A_1,\,\dots,\,x_n : A_n}_\Delta\ ;\
    \underbrace{y_1 : B_1,\,\dots,\,y_m : B_m}_\Gamma
$$

where $\Delta$ represents the linear part of the context and $\Gamma$ the unrestricted (exponential) part. The empty context is written as $\emptyset$. We write the disjoint union of two contexts as $\Delta_1, \Delta_2$ (separated by a comma).

Below, we present some typing rules for $\mu$CLL. The inaction process, $\emptyp$, for example, types with an empty linear context, and any unrestricted context. The parallel composition of two processes $P$ and $Q$, $\parc{P}{Q}$, types with the union of the disjoint linear contexts of $P$ and $Q$, and any unrestricted context. The cut composition of two processes $P$ and $Q$, $\cutc{P}{x: A}{Q}$, types with the disjoint union of the linear contexts of $P$ and $Q$ with the session $x$ having type $A$ on the linear context of $P$ and the dual of $A$ on the linear context of $Q$, and any unrestricted context. The full set of typing rules for $\mu$CLL can be found in \cite{Rocha:2022}.

\subsubsection{Syntax of CLASS}

The syntax of CLASS we'll be using on this thesis differs slightly from $\mu$CLL. Additionally, while in $\mu$CLL the typing contexts are separated into linear and unrestricted parts, in CLASS we have one extra division: the affine part. Process constructs and types for affine sessions, reference cells and non-determinism are also added. The types of CLASS follow the correspondence to $\mu$CLL presented in Table \ref{tab:CLASSTypes}, and are defined by the following BNF grammar:

\begin{align*}

The $\classt{affine}$, $\classt{coaffine}$, $\classt{state}$, $\classt{usage}$, $\classt{statel}$ and $\classt{usagel}$ types are not present in $\mu$CLL and are used to define affine sessions and reference cells, which we won't be diving into in this report. Note that recursive types are defined indirectly, through the \texttt{rec} keyword in definitions, as will be shown below. A CLASS program is composed of a collection of type definitions and process definitions, with the following BNF grammar:

\begin{align*}
    \text{Program} ::=\  & \text{ProcDef}\ \text{Program} &  & |\ \text{ProcDef} \\
    |\                   & \text{TypeDef}\ \text{Program} &  & |\ \text{TypeDef}
\end{align*}

A type definition associates a name $X$ to a session type $A$, and can either be a simple type definition, or a recursive type definition. Optionally, type definitions may also receive type variables as parameters, which are bound in $A$. The BNF grammar for type definitions is as follows:

\begin{align*}
    \text{TypeDef} ::=\  & \typedefc{X}{A}                     &  & |\ \rectypedefc{X}{A}                     \\
    |\                   & \typedefgc{X}{X_1,\,\dots,\,X_n}{A} &  & |\ \rectypedefgc{X}{X_1,\,\dots,\,X_n}{A} \\
\end{align*}

A process definition associates a name $\texttt{proc\_id}$ to a process $P$, which receives a list of channels $x_1,\,\ldots,\,x_n$ to be bound in $P$, with types $A_1, \ldots, A_n$, respectively. The BNF grammar for process definitions is as follows:

\begin{align*}
    \text{ProcDef} ::=\  & \procdefc{proc\_id}{x_1: A_1,\ \dots,\ x_n: A_n}{P}                        \\
    |\                   & \procdefgc{proc\_id}{X_1,\ \dots,\ X_n}{x_1: A_1,\ \dots,\ x_n: A_n}{P}    \\
    |\                   & \recprocdefc{proc\_id}{x_1: A_1,\ \dots,\ x_n: A_n}{P}                     \\
    |\                   & \recprocdefgc{proc\_id}{X_1,\ \dots,\ X_n}{x_1: A_1,\ \dots,\ x_n: A_n}{P}
\end{align*}

Finally, processes in CLASS are defined by the following BNF grammar, where $x$ and $y$ are session end points:

\begin{align*}
    P, Q ::=\  & \cutc{P}{x: A}{Q}                                          &  & |\ \parc{P}{Q}                                                 \\
    |\         & \fwdc{x}{y}                                                &  & |\ \emptyc                                                     \\
    |\         & \closec{x}                                                 &  & |\ \waitc{x}{P}                                                \\
    |\         & \casec{x}{\labelc{c$_1$}{P_1}\ \dots\ \labelc{c$_n$}{P_n}} &  & |\ \choosec{c}{x}{P}                                           \\
    |\         & \sendc{x}{y}{P}{Q}                                         &  & |\ \recvc{x}{y}{Q}                                             \\
    |\         & \bangc{x}{y}{P}                                            &  & |\ \whynotc{x}{P}                                              \\
    |\         & \sendtyc{x}{B}{P}                                          &  & |\ \recvtyc{x}{X}{P}                                           \\
    |\         & \unfoldmuc{x}{P}                                           &  & |\ \unfoldnuc{x}{P}                                            \\
    |\         & \proccallc{proc\_id}{x_1,\,\dots\,,x_n}                    &  & |\ \proccallgc{proc\_id}{X_1,\,\dots,\,X_n}{x_1,\,\dots,\,x_m} \\
    |\         & \printc{some\_string}{P}                                   &  & |\ \printlnc{some\_string}{P}                                  \\
    |\         & \affinec{x}P                                               &  & |\ \discardc{x}                                                \\
    |\         & \usec{x}P                                                  &  & |\ \cellc{x}{y}{P}                                             \\
    |\         & \releasec{x}                                               &  & |\ \takec{x}{y}{P}                                             \\
    |\         & \putc{x}{y}{P}Q
\end{align*}

These have a direct correspondence to the process composition constructs in $\mu$CLL and the actions shown in Table \ref{tab:muCLLActions}, with the exception of the process definition calling, print, affine and reference cell constructs. Note that in CLASS the sum/choice type is expanded to allow for an arbitrary number of choices, as opposed to $\mu$CLL, where the sum type is binary. This simplifies the syntax of the language, and all arbitrary sized sums can be trivially encoded as binary sums. Additionally, we have the process definition call construct, similar to a function call in an imperative language, which allows for reducing code duplication, and the print constructs.

\subsubsection{Example Programs}

We now present some example programs in CLASS, starting with a simple program which does nothing but close a session (Figure \ref{fig:CLASSWaitCloseExample}). Its type annotation $x: \closet$ indicates that on the right-hand side of the $\cutp$ the only action that can (and must) be performed is $\closep$. The last example we present, in Figure \ref{fig:CLASSPolymorphismExample}, is a simple demonstration of polymorphism in CLASS. The type definition \texttt{List} is a polymorphic type that receives a type variable $X$, and is defined as a choice between two labels, one for the empty list and another for a list with a head of type $X$ and a tail of type $List\ X$. The inductive process definition \texttt{concatList} operates on lists of a generic type $X$: it receives two lists $x$ and $y$ of type $List\ X$, and concatenates them into a new list $z$ of type $List\ X$. Unfolds have been omitted for brevity, but they are implicit in the example.

The concatenation is done by matching on the first list $x$. If it is $\labelp{nil}$, then the list $y$ is forwarded into $z$ without modification. If it is $\labelp{cons}$, then we extract the head $a$ from $x$, and insert it into $z$, by choosing the $\labelp{cons}$ label on $z$ and sending $a$ to $z$. Finally, the process calls itself recursively with the same type $X$, the tail of $x$, the same list $y$, and the new list $z$.

                \labelc{nil}{\fwdc{y}{z}}
                \labelc{cons}{\iz\z
                    \recvc{x}{a}
                    \choosec{cons}{z}
                    \sendc{z}{b}{\fwdc{a}{b}}
                    \proccallgc{concatList}{X}{x, y, z}
                    \dz
                }
            }
        }
    \end{class}

\end{figure}

\subsection{Linear Session Abstract Machine}

In this section, an overview of Linear Session Abstract Machine (Linear SAM) is given. The Linear SAM, introduced by Luís Caires and Bernardo Toninho in 2024, is a virtual machine for executing session processes typed by (classical) linear logic \cite{Caires:2024}. It provides an ``efficient deterministic execution model for the implicitly sequential
session-typed program idioms'', and a proof-of-concept implementation \cite{Caires:2024:artifact} of it was integrated as an alternative backend for CLASS \cite{Rocha:2022,Rocha:2021:artifact}.

Its most important contribution to this thesis is its specification of formal operational semantics which allows us to sequentially execute CLASS programs, where communication between processes is buffered, in a deterministic manner, while respecting the session types.

The core components of the SAM are session references $x, y$, values $V ::= \checkmark\ |\ \labelp{c}\ |\ \text{clos}(x, P)$, queues $q ::= \text{nil}\ |\ V\ |\ V@q$, session records $R ::= x\langle q,P\rangle y$ and the heap $H ::= x \mapsto R$, where $P$ is a process. Values $V$ can either be the close token $\checkmark$, a label $\#c$, or a closure $\text{clos}(x, P)$, where $x$ is a session reference and $P$ is a process. Queues $q$ are sequences of values, and session records $R$ are tuples of session references $x, y$, a queue $q$ and a process $P$. The heap $H$ maps session references to session records.

\subsubsection{Reduction Rules}

The Linear SAM is a state transition system, where the state is a tuple $(P, H)$, with the heap $H$ and a process $P$. The transition relation is defined by a set of rules, some of which are presented in this section.

The $\cutp$ rule, shown in Figure \ref{fig:SAMCutRule}, inserts a new session record in the heap, associated to the session reference $x$, for executing the continuation $Q$ of the process $P$, assuming, without loss of generality, that $A$ is a positive type, i.e., that $P$ will push values into the session queue, and $Q$ will later pop them. Essentially, the rule transitions to a state where $P$ will be executed immediately, and where $Q$ is delayed to a later time. If $A$ is a negative type, we simply apply the rule but with $P$ and $Q$ swapped.

\begin{figure}[H]
    \centering
    $$
        (\cutc{P}{x: A^+}{Q}, H)
        \Mapsto
        (P, H[x: A^+\langle\text{nil},\{y/x\}Q\rangle y:\dual{A^+}])
    $$
    \caption{SAM Cut Reduction Rule}
    \label{fig:SAMCutRule}
\end{figure}

The $\closep$ rule, shown in Figure \ref{fig:SAMCloseRule}, pushes the close token $\checkmark$ into the session queue, and then transitions to the continuation $P$ previously stored in the session record. $P$ will eventually pop the close token from the queue and free the session record. Note that the queue $q$ might not be empty - other positive actions might have preceded the close action and pushed values into the queue. The close token is appended to the end of the queue, and thus will be the last value to be popped.

\begin{figure}[H]
    \centering
    $$
        (\closec{x}, H[x:\closet\langle q, P\rangle y:B])
        \Mapsto
        (P,H[x:\emptyset\langle q@\checkmark, \emptyp\rangle y:B])
    $$
    \caption{SAM Close Reduction Rule}
    \label{fig:SAMCloseRule}
\end{figure}

The $\waitp$ rule, shown in Figure \ref{fig:SAMWaitRule}, pops the close token $\checkmark$ from the session queue, frees the session record, and transitions to the continuation of the $\waitp$ action.

\begin{figure}[H]
    \centering
    $$
        (\waitc{y}P, H[x:\emptyset\langle\checkmark, \emptyp\rangle y:\waitt])
        \Mapsto
        (P,H)
    $$
    \caption{SAM Wait Reduction Rule}
    \label{fig:SAMWaitRule}
\end{figure}

The choice rule, shown in Figure \ref{fig:SAMChoiceRule}, given an action $\choosec{c}{x}P$, pushes the label $\labelp{c}$ into the session queue and changes the process to $P$. Note that in this rule, we perform a write-to-read adjustment, denoted by $(P,H[x:A\langle q,Q\rangle y:B])^{wr}$. This operation swaps $P$ with $Q$, if and only if $A$ is a negative type. This operation ensures that the next action will be executed by the positive end point of the session. In this specific rule, we perform the write-to-read adjustment because the choice action is a positive action, which means we're pushing values for the other end point to pop later on. If the continuation process $P$ on this end point will next perform a read action on $x$, i.e., $A$ is negative, then, for that action to be executed, the other end point must first perform the corresponding write action.

\begin{figure}[H]
    \centering
    $$
        (\choosec{c}{x}P, H[x:\choicet{\labelt{c}{A},\ \dots}\langle q, Q\rangle y:B])
        \Mapsto
        (P,H[x:A\langle q@\labelp{c}, Q\rangle y:B])^{wr}
    $$
    \caption{SAM Choice Reduction Rule}
    \label{fig:SAMChoiceRule}
\end{figure}

The offer rule, shown in Figure \ref{fig:SAMOfferRule}, performs the dual operation of the choice rule - it pops a label from the session queue, and transitions to the continuation of the $\casep$ action corresponding to the label. The rule performs a read-to-write adjustment, denoted by $[x:A\langle q, Q\rangle y:B]^{rw}$. This adjustment swaps the two end points of the session record, $x:A$ and $y:B$, if and only if $q$ is empty. Since processes are well-typed, then, if $q$ is empty, $P$ should have no more reads to perform. This adjustment then allows $P$ to start writing to the session.

\begin{figure}[H]
    \centering
    $$
        (\casec{x}{\labelc{c}{P_c},\dots}, H[x:A\langle \labelp{c}@q, Q\rangle y:\offert{\labelt{c}{B_c},\dots}])
        \Mapsto
        (P_c,H[x:A\langle q, Q\rangle y:B_c]^{rw})
    $$
    \caption{SAM Offer Reduction Rule}
    \label{fig:SAMOfferRule}
\end{figure}

Finally, we show the $\fwdp$ rule in Figure \ref{fig:SAMForwardRule}, where we assume that, without loss of generality, $B^+$ is a positive type. The rule merges two session records, $(z:A\langle q_1, Q\rangle x:\dual{B^+})$ and $(y:B^+\langle q_2, Q\rangle w:C)$, into a single session record with continuation $P$ and queue $q_2@q_1$. If $B^+$ is a negative type, we swap $x$ and $y$ which gives us the equivalent process $\fwdc{y}{x}$.  Since $x$ is the read end point of the session and $y$ is the write end point, then $Q$ must have written through $z$ the contents of $q_1$. and the current process will have written through $y$ the contents of $q_2$. Thus, $P$ is waiting to read the contents of $q_2@q_1$.

\begin{figure}[H]
    \centering
    $$
        (\fwdc{x}{y}, H[z:A\langle q_1, Q\rangle x:\dual{B^+}][y:B^+\langle q_2, P\rangle w:C])
        \Mapsto
        (P,H[z:A\langle q_2@q_1, Q\rangle w:C])
    $$
    \caption{SAM Forward Reduction Rule}
    \label{fig:SAMForwardRule}
\end{figure}

\subsubsection{Example Execution}

In this section we present two simple examples of iteratively applying the reduction rules shown in the previous section, in order to execute processes. We omit the type annotations for brevity. Consider the process $P$ shown below:

$$
    P \equiv \cutc{\waitc{x}{\emptyc}}{x}{\closec{x}}
$$

The execution of $P$ is shown in Figure \ref{fig:SAMExampleExecutionP}. The initial state of the SAM is $(P, \emptyset)$. We first apply the $\cutp$ rule, which allocates a new session record in the heap, and transitions to $\closep$, as it corresponds to the positive type $\closet$. We apply the $\closep$ rule, which pushes the close token $\checkmark$ into the queue, and transitions to the session record continuation $\waitp$. Finally, we apply the $\waitp$ rule, which pops the close token $\checkmark$ from the queue, and transitions to the continuation $\emptyc$, reaching the final state $(\emptyc, \emptyset)$.

\begin{figure}[H]
    \begin{align*}
        (P, \emptyset)
         & \equiv
        (\cutc{\waitc{x}{\emptyc}}{x}{\closec{x}}, \emptyset)                \\
         & \Mapsto
        (\closec{x}, x\langle nil, \waitc{y}\emptyc\rangle y)                \\
         & \Mapsto (\waitc{y}\emptyc, x\langle \checkmark, \emptyp\rangle y) \\
         & \Mapsto
        (\emptyc, \emptyset)
    \end{align*}
    \caption{Example Execution of Process $P$}
    \label{fig:SAMExampleExecutionP}
\end{figure}

The second example is the process $Q$ shown below:

$$
    Q \equiv
    \cutc{
        \choosec{inl}{x}
        \waitc{x}\emptyc
    }{x}{
        \casec{x}{
            \labelc{inl}{\closec{x}}
            \labelc{inr}{\waitc{x}\emptyc}
        }
    }
$$

We show its execution in Figure \ref{fig:SAMExampleExecutionQ}. We first apply the $\cutp$ rule, which inserts a new session record in the heap. Then, we apply the choice rule, which pushes the label $\labelp{inl}$ into the queue of the session record, after which, we do a write-to-read adjustment, and transition to the continuation $\casep$. Then, we apply the $\casep$ reduction rule, which pops the label $\labelp{inl}$ from the queue, and transitions to the continuation matching the label. After that, this time we do a read-to-write adjustment, which means we swap the session end points. With the end points swapped, we can finally apply the $\closep$ and $\waitp$ rules as in the previous example and reach the final state $(\emptyc, \emptyset)$.

\begin{figure}[H]
    \begin{align*}
        (Q, \emptyset)
         & \Mapsto
        (\choosec{inl}{x}\waitc{x}\emptyc, x\langle nil, \casec{y}{\labelc{inl}{\closec{y}}\labelc{inr}{\waitc{y}\emptyc}}\rangle y)          \\
         & \Mapsto (\waitc{x}\emptyc, x\langle \labelp{inl}, \casec{y}{\labelc{inl}{\closec{y}}\labelc{inr}{\waitc{y}\emptyc}}\rangle y)^{wr} \\
         & \equiv (\casec{y}{\labelc{inl}{\closec{y}}\labelc{inr}{\waitc{y}\emptyc}}, x\langle \labelp{inl}, \waitc{x}\emptyc\rangle y)       \\
         & \Mapsto (\closec{y}, x\langle nil, \waitc{x}\emptyc\rangle y)^{rw}                                                                 \\
         & \equiv (\closec{y}, y\langle nil, \waitc{x}\emptyc\rangle x)                                                                       \\
         & \Mapsto (\waitc{x}\emptyc, x\langle \checkmark, \emptyp\rangle y)                                                                  \\
         & \Mapsto (\emptyc, \emptyset)
    \end{align*}
    \caption{Example Execution of Process $Q$}
    \label{fig:SAMExampleExecutionQ}
\end{figure}

\subsection{Alternative Applications}

In this section, we present some works which apply linear logic and/or session types through different approaches. These works are not directly related to CLASS or to the Linear SAM, nor do we base this work on them, but they are interesting to mention as they show alternative ways of solving the same problems we are addressing.

\subsubsection{Linear Haskell}

Linear Haskell \cite{Bernardy:2017} is an extension of Haskell that introduces linear types to the language in a backwards-compatible way, allowing the programmer to use linear types in their program without changing the existing code. It does so by introducing a new kind of function arrow, that is, a new type of function, called a linear function, which must consume its argument exactly once.

Session types have been implemented in Linear Haskell by Kokke et al. \cite{Kokke:2021} in the form of a small library called \textit{Priority Sesh}. This library allows the programmer to easily define session types and integrate them into their programs. The library also gives the possibility of the user annotating session types with priorities, which can then be used to prove that the program is deadlock-free.

One big disadvantage of the Linear Haskell approach is that it is not able to fully exploit the linearity of the types for compiler optimizations, due to the core compiler being non-linear. In contrast, our approach should in theory be able to do so, as CLASS is a session-typed language from the ground up.

\subsubsection{Rust}

Rust is a systems programming language known for its strong type system. Although it has no linear types, it supports affine types through its ownership system, which forbids variables from being used after they have been moved. References allow the programmer to share data between different parts of the program, but they must follow the strict borrowing rules of the language - there is no limit on the number of immutable references, but there can only be one mutable reference to a given piece of data at a time, and only if there are no immutable references to it.

These rules are enforced at compile time, and the Rust compiler is able to catch many common programming errors, such as use-after-free, data races, and null pointer dereferences, which makes it a very safe language. However, Rust lacks the expressiveness of linear types, which could be used to enforce more complex invariants in the program, such as the order in which functions must be called, or the number of times a function must exactly be called. It also has no built-in support for session types, and therefore, no built-in support for enforcing communication protocols.

Nonetheless, non-linear, i.e., affine session types have been implemented in Rust in the form of libraries by several authors, such as by Jespersen et al. \cite{Jespersen:2015} and Lagaillardie et al. \cite{Lagaillardie:2022}.
