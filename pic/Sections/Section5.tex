
\section{CLASS Compiler}

\subsection{IR to C}

In this section we describe the C programs generated by the compiler, from the intermediate representation (IR) produced by the code generation phase.

The intermediate representation (IR) used by the compiler is an imperative stateful language which closely resembles an assembly language. An IR program is a list of blocks of instructions, which may be labeled. Each block corresponds to a process definition in the source CLASS program.

We start by showing the C type definitions for the data structures generated by the compiler. Then, we give an overview of our intermediate representation (IR), and show how these IR constructs are translated to C code.

\subsubsection{Data Types}

In Figure \ref{fig:RecordType} we show the C type which describes a session record. The fields \texttt{cont}, \texttt{cont\_env} and \texttt{cont\_record} are used on \textit{flips}, i.e., when resuming the opposite end point of a session. Respectively, they store the program address to jump to, the environment to switch to, and the index of the session record on the opposite end point.

The fields \texttt{written} and \texttt{read} are used to keep track of how many bytes have been written and read from the buffer.

Finally, the \texttt{buffer} field is an array of bytes which stores the data exchanged between the two end points of the session. Its size is determined at allocation time, and is at most $255$ bytes.

\begin{figure}[!h]
    \centering
    \begin{lstlisting}[language=C]
struct record {
    void* cont;
    struct environment* cont_env;
    unsigned char cont_record;
    unsigned char written, read;
    unsigned char buffer[];
};
    \end{lstlisting}
    \caption{C type describing a session record}
    \label{fig:RecordType}
\end{figure}

Figure \ref{fig:EnvironmentType} shows the C type which describes an environment. It contains a pointer to the first exponential closure in the environment, and an array of pointers to session records, of at most $255$ elements.

\begin{figure}[!h]
    \centering
    \begin{lstlisting}[language=C]
struct environment {
    struct exponential* exponential;
    struct record* records[];
};
    \end{lstlisting}
    \caption{C type describing an environment}
    \label{fig:EnvironmentType}
\end{figure}

The exponential closures form a linked list, where each closure points to its parent closure, as shown in Figure \ref{fig:ExponentialType}. The \texttt{cont} field stores the program address to jump to, and the \texttt{size} field stores the size of the environment that should be created when the closure is instantiated.

\begin{figure}[!h]
    \centering
    \begin{lstlisting}[language=C]
struct exponential {
    struct exponential* parent;
    void* cont;
    int size;
};
    \end{lstlisting}
    \caption{C type describing an exponential closure}
    \label{fig:ExponentialType}
\end{figure}

Finally, we define a C type for tasks in Figure \ref{fig:TaskType}. Tasks store a program address and an environment to switch to. Additionally, they store a pointer to the next task in the linked list of tasks. These are used to implement the CLASS parallel construct sequentially.

\begin{figure}[!h]
    \centering
    \begin{lstlisting}[language=C]
struct task {
    struct task* next;
    void* cont;
    struct environment* cont_env;
};
    \end{lstlisting}
    \caption{C type describing a task}
    \label{fig:TaskType}
\end{figure}

\subsubsection{Registers}

Translated IR instructions operate on the registers shown in Figure \ref{fig:Registers}. The \texttt{env} register points to the current environment, on which operations are performed. The \texttt{task} registers point to the next task to be executed. The rest of the registers are used to store temporary values.

    \centering
    \begin{lstlisting}[language=C]

struct task *task, *tmp_task;
struct record *tmp_record;
void *tmp_cont;
    \end{lstlisting}
    \caption{Registers used by the IR}
    \label{fig:Registers}
\end{figure}

\subsubsection{Main function}

The main function of the generated C program is shown in Figure \ref{fig:MainFunction}. It initializes the environment, allocates space for the session records, and then jumps to the entry process.

For each process definition, a label of the form \texttt{proc\_X} is generated, where \texttt{X} is the name of the process. The code each for process definition is generated from its IR instructions, immediately after the label.

\begin{figure}[!h]
    \centering
    \begin{lstlisting}[language=C]
int main() {
    /* The last task in the list of tasks finishes the program */
    task = malloc(sizeof(struct task));
    task->cont = &&end;

    /* Initializes the environment, where n is the number of session records
       necessary for the entry process */
    env = malloc(sizeof(struct environment) + /*n*/ * sizeof(struct record*));
    goto proc_entry;

    /* ... process definitions ... */

end:
    return 0;
}
    \end{lstlisting}
    \caption{Main function of the generated C program}
    \label{fig:MainFunction}
\end{figure}



\subsubsection{Instructions}

Sessions are initialized by the \texttt{initSession} instruction. This instruction receives the index \texttt{record} of the session record in the current environment, the \texttt{size} of the session record buffer in bytes, and the initial continuation of the session, referenced by a label \texttt{cont}. The generated C code for this instruction is shown in Figure \ref{fig:InitSessionIR}.

\begin{figure}[!h]
    \centering
    \begin{lstlisting}[language=C]
/* initSession(record, size, cont) */
env->records[record] = malloc(sizeof(struct record) + size);
env->records[record]->cont = &&cont;
env->records[record]->cont_env = env;
env->records[record]->cont_record = record;
env->records[record]->written = 0;
env->records[record]->read = 0;
    \end{lstlisting}
    \caption{IR construct for initializing a session}
    \label{fig:InitSessionIR}
\end{figure}

\subsection{CLASS to IR}

In this section we describe the compilation process from a CLASS program to the intermediate representation (IR) we defined in the previous section.

\subsubsection{Buffer Size Calculation}

We denote the size, in bytes, of the buffer necessary for the full execution of a session of type $A$, as $\sizeof A$. This size is computed through pattern matching on the session type, through the rules introduced below.

For an type, its size must be equal to its dual type, as any value written by one end point must be read by the other. Thus, we omit the dual types for simplicity.

$$
    \sizeof{\dual A} = \sizeof A
$$

The unit types, $\closet{}$ and $\waitt{}$, have size $0$, as they do not require any data to be exchanged. They're only there to signal the end of a session.

$$
    \sizeof{\closet{}} = 0
$$

The sum types, $\offert{\dots}$ and $\choicet{\dots}$ have size equal to the maximum size of their components, plus $1$ byte to store the tag of the chosen branch.

$$
    \sizeof{\offert{\labelt a A\ (\dots)\ \labelt z Z}} =
    1 + \max(\sizeof A,\ \dots, \sizeof Z)
$$

The multiplicative types, $\sendt{A}{B}$ and $\recvt{A}{B}$, have size equal to the size of $B$, plus $S$ bytes to store a pointer to the sent session record, where $S$ is the size of a pointer to a session record in the compilation target architecture.

$$
    \sizeof{\sendt A B} = S + \sizeof B
$$

The exponential types, $\bangt A$ and $\whynott A$, have size $E + C + 1$, where $E$ and $C$ are, respectively, the size of pointers to an environment and to a program address in the compilation target architecture.

$$
    \sizeof{\bangt A} = E + C + 1
$$

Finally, if the type is a recursive type, any occurrence of recursive variable $X$ has a size of $0$. When a recursive type is unfolded, the session buffer is reused its beginning, and thus, there's no need to allocate more space.

$$
    \sizeof{X} = 0
$$
